## 二、重点书籍复盘
### 2.1《系统之美》· 德内拉·梅多斯（进度 13%）
- 核心内容摘要：系统思考的入门指南，讲清系统的三大构成要件（要素、连接、功能或目标）、常见系统结构、8 大陷阱与对策、12 个变革杠杆点。本周读到第 1 章「系统之基础」与两篇导读。
- 阅读心得：本周阅读量最大的一本（21 分钟、9 条划线），关键收获是把「看要素」换成「看连接」：一加一等于二的前提是理解两个「一」之间的关系，而不是知道「一」本身。导读里「专注于事件层面的响应、不触及问题根源」正好解释了日常救火的循环，也让我意识到自己复盘常停在事件层。
- 本周沉淀：划线 9 条 / 想法 0 条

### 2.2《深度学习入门：基于Python的理论与实现》· 斋藤康毅（进度 35%）
- 核心内容摘要：本周读到第 4 章：从数据中学习（端到端、过拟合、特征量）、损失函数（均方误差、交叉熵误差）、以及手写数字识别的完整流程（784 输入、10 输出）。
- 阅读心得：损失函数这一节把「学习」写成了一个可操作的闭环，用「性能的恶劣程度」当指标，取最小即等价于取最优。端到端则解释了为什么这套方法能替代手工设计算法：从原始输入直接得到输出，中间的特征由数据自己学。这两点与本周《图解Skill》里「给方向比给参数更好」是同一个思路。
- 本周沉淀：划线 9 条 / 想法 0 条

### 2.3《图解Skill：AI提效实战指南》· 宝玉（本周读完）
- 核心内容摘要：把个人经验固化成智能体可执行的技能，从单技能模板到组合工作流，再到技能工程方法论与迭代实战。本周读的是结语「从菜谱到厨艺」与 7.4 的三版复盘。
- 阅读心得：读完的落点是「技能装的是你的经验」，做过三次的事情就值得写成技能；不知道怎么做的，就把成品交给智能体反推菜谱。7.4 的两条教训很实用：正面描述负责牵引方向、禁止清单负责兜底，两者必须配套；在模型能力覆盖的领域，给方向比给参数效果更好。
- 本周沉淀：划线 5 条 / 想法 0 条

### 2.4《Effective Python（原书第2版）》· 布雷特·斯拉特金（进度 0%，本周新开）
- 核心内容摘要：90 条 Python 实践原则，本周读到第 2 条 PEP 8 风格指南中的 import 组织、行内否定与真值判断、命名规范三部分。
- 阅读心得：这三条划线都是可以立刻改的习惯，尤其「不要用 len 判断空容器，直接用 if not somelist」和「import 分标准库、第三方、自写三段并按字母序」。风格指南的价值不在于好看，而在于让代码审查的注意力省下来给逻辑。
- 本周沉淀：划线 3 条 / 想法 0 条

### 2.5《工作、消费主义和新穷人》· 齐格蒙特·鲍曼（进度 65%）
- 核心内容摘要：追溯工作伦理如何从「工厂纪律」演变为消费社会的美学，以及被排除在消费能力之外的人如何被重新定义为「新穷人」。本周读到第四章「工作伦理和新穷人」。
- 阅读心得：本周只有 1 条划线，但它的判断很锋利：底层阶级被叙述成「内部的敌人」，承担着维持社会紧张与安全阀的功能。这条与《系统之美》里「症状缓解式对策」可以对照来看，同一个结构问题，一边是系统动力学语言，一边是社会叙述语言。
- 本周沉淀：划线 1 条 / 想法 0 条

## 四、8 条最有价值划线（N = min(round(30×0.25), 15) = 8）
1. **《图解Skill：AI提效实战指南》**（7.4 回顾：三个版本教会我们什么）
   > 在模型能力覆盖的领域，「给方向」往往比「给参数」效果更好。方向明确了，把具体的实现参数交给智能体动态决策，效果常常超出预期。
   - 心得：这条解释了为什么很多调参式提示词越改越僵。参数是替模型做它更擅长的判断决策，方向才是人真正该负责的部分。
   - 行动启发：写提示词先写目标与边界，不预设实现细节。

2. **《图解Skill：AI提效实战指南》**（结语 从菜谱到厨艺）
   > 吃到好菜，就把做法变成自己的菜谱。在日常工作中留个心眼：每次你觉得「这事我做得挺顺」，就停下来想想，这个过程能不能固化成技能？做过三次的事，其做法就值得写成技能。
   - 心得：把「顺手」识别为可沉淀信号，比事后回忆流程有效得多。三次是很好的阈值，既排除了偶然，也避免过早抽象。
   - 行动启发：顺手时刻记一行，攒够三次写成 SKILL。

3. **《系统之美》**（第1章 系统之基础）
   > 对于一个系统来说，整体大于部分之和。任何一个系统都包括三种构成要件：要素、连接、功能或目标。它具有适应性、动态性、目的性，并可以自组织、自我保护与演进。
   - 心得：三要件里最容易被忽略的是连接与目标，而它们恰恰决定了换掉要素后系统行为为何不变。这解释了「换了人问题照旧」。
   - 行动启发：分析问题先写清三要件，再谈改要素。

4. **《系统之美》**（导读 决策者的系统思考）
   > 很多对策并未抓住问题的本质，只是「治标不治本」的「症状缓解」，或者不全面地解决问题，导致「按下葫芦浮起瓢」，到处救火、应接不暇。
   - 心得：症状缓解与根本解在短期内看起来一样有效，区别在于反弹幅度。判断标准是问「这个问题多久后会以别的形式回来」。
   - 行动启发：每个应急对策旁标注它的反弹路径。

5. **《腾讯云开发者》**（AI 接口测试实践）
   > 这里有一个关键硬阻塞点：场景确认报告必须人工确认后，才能进入真实执行。因为报告承载的是「需求预期」，预期一旦错了，后续报告反而更有迷惑性。
   - 心得：错误预期产生的完整报告比明显失败更危险，因为它绕过了人的怀疑。人工闸门应设在「预期确认」而非「结果验收」。
   - 行动启发：自动化流程里给预期确认加一个强制人工卡点。

6. **《腾讯云开发者》**（AI 接口测试实践）
   > 我们要解决的不是「如何让 AI 再多写一点代码」，而是：当 AI 已经把代码生成速度提上来之后，如何帮助开发更快、更稳地判断这段代码是否真的可用。
   - 心得：生成成本下降后瓶颈整体迁移到判断上，这与本周《图解Skill》的技能化、以及代码审查的处境是同一件事。
   - 行动启发：把投入从写代码转向做可执行的验收标准。

7. **《深度学习入门：基于Python的理论与实现》**（4.2 损失函数）
   > 损失函数是表示神经网络性能的「恶劣程度」的指标，即当前的神经网络对监督数据在多大程度上不拟合，在多大程度上不一致。
   - 心得：用「恶劣程度」而非「优良程度」定义指标，好处是所有改进都变成同一个方向的下降，比较和优化都更简单。
   - 行动启发：设计个人指标时优先选可单调下降的坏指标。

8. **《Effective Python（原书第2版）》**（第2条 遵循PEP 8风格指南）
   > 采用行内否定，即把否定词直接写在要否定的内容前面，而不要放在整个表达式的前面，例如应该写 if a is not b，而不是 if not a is b。不要通过长度判断容器或序列是不是空的，而是应该采用 if not somelist 这样的写法。
   - 心得：两条都在说同一件事，让读者少做一次心算。项目里所有约定俗成的写法，本质都是省下审查时的注意力。
   - 行动启发：本周提交前扫一遍自己代码的空值判断。
