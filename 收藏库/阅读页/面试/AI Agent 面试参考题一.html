01基础概念与架构模式

本节提炼
  • 覆盖第 2~20 题，主题是 Agent 基础概念、边界与架构模式
  • 题目来源多为字节、阿里、腾讯、美团等大厂

02什么是 Agent 及其边界

本节提炼
  • Agent 是能自己决定下一步并动手执行的程序
  • 边界看两点：有无行动闭环、能力是枚举还是组合
  • 结果无法验证、失败无法回滚的场景不应端到端自主执行，需 HITL

Agent = 能自己决定「下一步做什么」,并且真的动手去做的程序。

形态本质边界
传统对话系统 / Chatbot输入 → 模板或意图匹配 → 输出无行动能力,状态机是写死的
Siri 类助手语音入口 + 固定意图槽位(定闹钟、打电话)技能是枚举出来的,不能组合,不能自我纠错
LLM 单轮问答输入 → 模型 → 文本只会「说」,不会「做」
AgentLLM 做决策内核 + 工具做手脚 + 循环做推进目标开放、路径不确定、能观察结果再调整

两条核心分界线:

  • 1. 有没有「行动—观察—再决策」的闭环 。Siri 说「我帮你查一下」,查完就结束;Agent 查完发现不对,会换种方式再查。
  • 2. 能力是枚举的还是组合的 。Siri 的技能是人工写的 intent;Agent 的能力是「工具 × 模型推理」动态组合出来的,任务空间不封闭。

加分一句:Agent 的能力边界是「可验证、可回滚」。结果无法验证、失败无法回滚的场景,当前阶段不该让 Agent 端到端自主执行,必须加人工确认(HITL)。

03为什么用 Agent

本节提炼
  • Agent 定义为 LLM 推理内核加工具调用，在感知规划行动观察循环中推进
  • 裸模型三约束：知识截止、不能产生副作用、不能一步到位
  • 路径固定、步骤少、延迟敏感时上 Agent 是过度设计

定义:以 LLM 为推理内核,通过工具调用与外部世界交互,在「感知 → 规划 → 行动 → 观察」循环中自主推进直到达成目标的系统。

为什么要 Agent —— 因为裸模型有三个硬约束:

  • 1. 知识截止 + 看不到私有数据 :不知道你公司今天的库存,也不知道现在几点。
  • 2. 不能产生副作用 :不能下单、不能改代码、不能发邮件。
  • 3. 不可能一步到位 :复杂任务要多步,并且要依赖中间结果修正。

裸模型只能「说」,Agent 让它「做」。本质是把 LLM 从问答组件升级为决策组件,再配一套执行与反馈机制。

什么时候不用 Agent:路径固定、步骤少、延迟敏感、要求确定性 → 单次 Prompt 或 Workflow 就够了,上 Agent 就是过度设计(白送延迟、成本和不稳定性)。

04Agent 与 Workflow 关系

本节提炼
  • Workflow 是人把控制流写死，Agent 是模型把控制流生成出来
  • 判断四问：步骤可预知、分支可穷举、中间结果依赖、错误代价
  • 能用 Workflow 解决就别上 Agent

关系:Workflow 是「人把控制流写死」,Agent 是「模型把控制流生成出来」。二者不是替代关系:Agent 内部往往是一堆 Workflow,企业级系统绝大多数是 Workflow 骨架 + Agent 节点的混合体。

判断依据,问四个问题:

  • 1. 步骤数可预知吗? 可预知 → Workflow;不可预知 → Agent。
  • 2. 分支条件能穷举吗? 能 → Workflow;不能 → Agent。
  • 3. 强依赖中间结果的反馈吗? 强依赖(查完才知道下一步查什么)→ Agent。
  • 4. 错误代价和可观测性要求高吗? 高 → Workflow,Agent 只做「填参 / 判断」这类局部决策。

经验法则:能用 Workflow 解决就别上 Agent。 Agent 的灵活性是用延迟、成本、不确定性换来的,只在路径真的不确定时才值得付。

05常见架构模式

本节提炼
  • 八种模式：ReAct、Plan-Execute、Reflexion、Router、Supervisor、Pipeline、Debate、分层混合
  • 选型原则：控制流越确定越靠 Workflow，目标越开放越靠 Supervisor+ReAct
  • 1. ReAct :交替「思考 → 行动 → 观察」,最基础的模式。
  • 2. Plan-and-Execute :先出完整计划,再逐步执行,可配 Replan。
  • 3. Reflexion / 自我反思 :失败后反思原因,改进后重试。
  • 4. Router 分发式 :一个路由 Agent 把请求分给若干专职子 Agent。
  • 5. Supervisor / Orchestrator-Worker :主 Agent 拆任务、派发、汇总,子 Agent 只干活。
  • 6. Pipeline 流水线 :固定阶段的串行编排,每阶段可以是 Agent。
  • 7. Debate / 多角色讨论 :多个 Agent 扮演不同角色互相质疑收敛。
  • 8. 分层混合 :全局用 Plan-Execute,局部节点用 ReAct(见第 18 题)。

选型原则:控制流越确定,越往 Workflow 靠;越是开放目标,越往 Supervisor + ReAct 靠。

06ReAct 原理与优缺点

本节提炼
  • ReAct 即 Reasoning+Acting，按 Thought→Action→Observation 循环到 Final Answer
  • 优点：实现极简、逐步利用观察、过程可读
  • 缓解：最大轮次、重复调用检测、阶段性重述目标
  • 短视迷失全局、token 消耗高、错误累积、易死循环

ReAct = Reasoning + Acting,让模型在每一步先输出一段思考(Thought),再决定调用哪个工具(Act),拿到结果后(Observation)继续思考,直到输出最终答案(Finish)。

循环:

  • Thought → Action(工具名 + 参数) → Observation(工具返回) → Thought → ... → Final Answer

优点:

  • • 实现极简:一个 while 循环 + 工具描述就能跑。
  • • 每步都能利用最新观察调整,适合信息逐步展开的任务(搜索、排障)。
  • • 过程可读,Thought 天然是调试线索和可观测性素材。

缺点:

  • • 短视 :只看当前一步,容易在长任务里迷失全局目标、绕圈。
  • • token 消耗高 :每轮都要携带完整轨迹,上下文线性膨胀。
  • • 错误累积 :一步幻觉会被后续步骤当事实用。
  • • 易死循环 :反复调用同一工具。

缓解:加最大轮次 + 重复调用检测 + 阶段性重述目标(见第 107、112 题)。

07ReAct 与 Plan-Execute-Replan

本节提炼
  • ReAct 每步现想现做、局部短视；Plan-Execute-Replan 先全局计划、可审查可干预
  • 复杂 Agent 通常 Plan 阶段定骨架，每步内部用 ReAct 执行
维度ReActPlan-Execute-Replan
控制流每步现想现做先出全局计划,再逐步执行
视野局部、短视全局,能看到任务全貌
调整时机随时微调(隐式)阶段性重规划(显式)
token每轮带全轨迹,膨胀快计划外置,执行时上下文更短
可解释性过程清晰但目标不清计划是显式的,人可审查、可干预
容错走错一步可立即纠正走错一步要等到 Replan 才纠正

选型:

  • • ReAct :步骤少、路径高度依赖中间结果、探索型任务(单点问答、实时查询、简单排障)。
  • • Plan-Execute-Replan :步骤多、有明确交付物、需要人审计划、需要并行子任务(写报告、做调研、重构代码、多文件改造)。

实战:复杂 Agent 通常是「Plan 阶段用 Plan-Execute 定骨架,每个 step 内部用 ReAct 执行」。

08为何需要监管 Agent

本节提炼
  • 监管 Agent 负责计划合理性校验、执行偏离检测、重规划触发、收敛兜底
  • Planner 输出是一次性假设而执行环境会变，需监管兜底
  • 不加监管会计划错了照跑到黑，Replan 退化成 ReAct

因为 Planner 的输出是一次性假设,而执行环境会变。监管 Agent(Supervisor / Critic)承担四件事:

  • 1. 计划合理性校验 :目标是否被覆盖、步骤是否冗余、依赖顺序对不对、有没有不存在的工具。
  • 2. 执行偏离检测 :实际结果和计划预期不符时,判断是「继续」还是「重规划」。
  • 3. 重规划触发 :连续失败、出现新信息、子任务失败时决定 Replan 的范围(全量还是局部)。
  • 4. 收敛兜底 :防止 Planner 不停重规划导致死循环,给次数和预算上限。

不加监管,系统就是「计划错了也照跑到黑」,而且 Replan 会退化成 ReAct,失去全局视野的意义。

09项目架构与部署

本节提炼
  • 四层架构：基础设施、能力、编排、接入
  • 框架选型：JVM 用 Spring AI，Python 用 LangGraph 或轻量自研 harness
  • 服务无状态、状态外置，长任务队列异步，金丝雀发布

分层架构(自下而上):

  • 1. 基础设施层 :模型网关(多模型路由、限流、成本统计)、向量库、缓存、消息队列、沙箱、可观测(日志/追踪)。
  • 2. 能力层 :工具集(Function Calling)、MCP Server 集群、Skills 库、记忆服务、RAG 服务。
  • 3. 编排层 :Agent Runtime(ReAct Loop、状态机、Plan 引擎)、多 Agent 调度、HITL 中断恢复。
  • 4. 接入层 :API / SSE 流式 / 前端交互 / 审批工作台。

框架选型:JVM 栈用 Spring AI / Spring AI Alibaba;Python 栈用 LangGraph(要显式状态机与快照)或轻量自研 harness。关键原则:编排逻辑尽量不写在框架 DSL 里,框架只做「模型的适配层 + 状态持久化」,方便替换和自研。

部署流程:

  • • Agent 服务本身是无状态容器,会话状态外置到 Redis / MySQL / PG,才能水平扩缩容。
  • • 模型和工具配置走配置中心,支持灰度、A/B、快速回滚。
  • • 长任务用队列 + Worker 异步执行,前端 SSE 订阅进度。
  • • 发布用金丝雀:先小流量,对比成功率、平均轮次、token 成本三条曲线再放量。

10Agent 与大模型区别

本节提炼
  • 大模型提供能力是原料，Agent 提供结果是产品
  • 模型侧关心效果上限，Agent 侧关心工具成功率、循环控制等工程可靠性
  • • 大模型 :提供 能力 (语言理解、生成、推理),是原料;输出是文本,无状态、无副作用。
  • • Agent :提供 结果 ,是产品;输出是任务完成度,有状态、有副作用、可被评估。

工程关注点完全不同:模型侧关心效果上限(评测集、微调、蒸馏);Agent 侧关心工程可靠性(工具成功率、循环控制、上下文预算、降级兜底、成本与延迟)。

一句话:大模型决定天花板,Agent 工程决定能不能落地。 同一个模型,工程做得好与差,线上成功率能差 30 个点。

11与传统后端差异

本节提炼
  • 控制流、输出、延迟、成本、错误处理、测试、可观测等维度都不同
  • 最被低估的差异是延迟和成本的一次性放大
  • 一次请求可能触发 20 次模型调用，无超时和预算控制会雪崩
维度传统后端Agent 项目
核心逻辑确定性代码概率性推理 + 确定性代码混合
控制流编译期/配置期确定运行时由模型生成,不确定
输出幂等、可精确断言非幂等、需概率评测 + 断言混合
延迟毫秒~百毫秒秒~分钟(多轮 LLM 调用)
成本CPU/内存token 直接等于钱 ,成本是核心指标
错误处理异常 → 重试/回滚幻觉/格式崩坏/死循环,需要语义级兜底
测试单测覆盖率评测集 + LLM-as-Judge + 回归集
可观测日志 + 链路日志 + 链路 + 完整轨迹留存与回放

最被低估的差异是延迟和成本的一次性放大:一次用户请求可能触发 20 次模型调用,任何一环没有超时和预算控制,线上就会雪崩。

12三种方案选型

本节提炼
  • 按「不确定性 × 步骤数」两轴选型
  • 决策顺序：先单次提示词，不行再 Workflow，再不行才 Agent
  • 能用前两者并达标却上 Agent 是错误选择

按「不确定性 × 步骤数」两个轴选:

  • 1. 单次提示词 :一步能完成,输入输出边界清晰(分类、抽取、改写、摘要)。最便宜最快,优先考虑。
  • 2. Workflow :步骤可枚举、有固定顺序或明确分支(审核流、报表生成、多阶段抽取)。可测、可控、延迟可预算。
  • 3. Agent :路径不可预知、需要看中间结果决定下一步、目标开放(排障、调研、多文件改造)。

决策顺序:先试单次提示词 → 不行就 Workflow → 再不行才 Agent。 同时看四个约束:延迟预算、单次成本预算、错误代价、可观测与合规要求。能用前两者并达标,绝不上 Agent。

13固化还是保泛化

本节提炼
  • 高频、路径稳定场景固化成 Skill 或固定 Workflow，长尾探索保泛化
  • 成熟形态是双轨制：通用 Agent 兜底加 Skill Router 路由专用链路

固化(垂直):高频、路径稳定、对准确率与成本极敏感的核心场景。做法是把它沉淀成 Skill / 固定 Workflow + 专用工具集 + 精简 Prompt。收益是延迟降一个量级、准确率可调优、成本可预测。

保泛化:长尾需求、探索性任务、需求还在快速变化的阶段。做法是保留通用 ReAct 内核 + 通用工具/MCP 接入。

判断依据:①调用频次(高频固化,长尾泛化);②路径稳定性;③错误代价;④需求变更速率。

成熟形态是「双轨制」:通用 Agent 作为兜底入口,识别到高频意图就路由到固化好的专用链路(Skill Router)。这样既有长尾覆盖,又有核心场景的确定性。

14最小可用 Agent 模块

本节提炼
  • ReAct Loop 加工具只是骨架，还需预算、防环、治理、持久化、可观测、降级、安全
  • Loop 是心脏，预算、终止、治理、可观测是上线的血管

是,但不只是。 ReAct Loop + 工具调用只是骨架,生产可用还需要:

  • 1. 上下文 / 预算管理 :token 计数、压缩、结果卸载,否则跑几轮就爆窗口。
  • 2. 终止与防环机制 :最大轮次、最大 token、重复调用检测、无进展检测。
  • 3. 工具治理 :参数校验与修复、超时、重试(指数退避)、幂等、异常隔离(一个工具挂了不能拖死整个 Loop)。
  • 4. 状态持久化 :会话/轨迹落库,支持断点恢复与回放。
  • 5. 可观测 :每步的输入输出、耗时、token、工具结果都要留痕。
  • 6. 降级兜底 :模型不可用、连续失败时的兜底回答与人工转接。
  • 7. 安全 :权限校验、危险操作 HITL、注入防护。

一句话:Loop 是心脏,预算、终止、治理、可观测是让它可以上线的四根血管。

15落地瓶颈与弊端

本节提炼
  • 最大瓶颈是可靠性加可评估性加组织配套，不是模型能力
  • 多步复合成功率指数衰减，单步 95% 十步只剩 60%
  • 不确定性、幻觉、成本延迟不可预测、调试困难、安全面变大、过度设计

最大瓶颈:不是模型能力,是「可靠性 + 可评估性 + 组织配套」。

  • 1. 可靠性 :多步任务的复合成功率会指数衰减。单步 95%,10 步就只剩 60%。工程上要靠幂等、检查点、人工兜底把链路救回来。
  • 2. 可评估性 :没有评测集和指标,就没法迭代,只能靠感觉改 Prompt。
  • 3. 数据与权限 :企业数据分散、权限复杂,工具接不通一切白谈。
  • 4. 组织与合规 :谁为 Agent 的错负责?高危操作谁签字?
  • 5. 成本与延迟 :token 成本随轮次线性涨,长任务延迟到用户不可接受。

弊端:不确定性(同输入不同输出)、幻觉、成本与延迟不可预测、调试困难、安全面变大(注入、越权)、容易被当成万能解导致过度设计。

16Agent 与 Siri 差异

本节提炼
  • 差异在意图来源、能力组织、执行模式、状态记忆、可扩展性五方面
  • 根本差异：Siri 流程人写好，Agent 流程模型运行时生成
  • 1. 意图来源 :Siri 靠人工定义的 intent + 槽位;Agent 靠模型对自然语言目标的理解和拆解,覆盖长尾。
  • 2. 能力组织 :Siri 是枚举的封闭技能集;Agent 是工具动态组合,能力空间开放。
  • 3. 执行模式 :Siri 单轮触发、单步执行(失败即结束);Agent 多步循环,观察结果再决策,能自我纠错。
  • 4. 状态与记忆 :Siri 基本无跨轮任务状态;Agent 有任务态、短期记忆、长期记忆。
  • 5. 可扩展性 :Siri 加能力要改代码发版;Agent 加能力只需注册一个工具 / 挂一个 MCP / 加一个 Skill。

根本差异:Siri 的流程是人写好的,Agent 的流程是模型在运行时生成的。

17兼顾全局规划与实时反馈

本节提炼
  • Supervisor 下 Planner 拆 DAG，Executor 内部跑 ReAct，Critic 校验，失败局部重规划
  • 计划粒度适中，经验值每步 3~8 次工具调用
  • 共享上下文分全局区与局部区，统一中断语义

分层组合,而不是二选一:

  • Supervisor(全局)
  • ├─ Planner:把目标拆成有序子任务 DAG(全局视野,Plan-Execute)
  • ├─ 每个子任务由 Executor 执行,Executor 内部是 ReAct Loop(实时反馈、局部自适应)
  • ├─ Critic/Verifier:校验子任务产出是否满足该步目标
  • └─ Replan 决策:失败/偏离/新信息 → 局部重规划(只重规划受影响的子图)

关键设计点:

  • 1. 计划粒度要适中 :太粗退化成 ReAct,太细失去灵活性。经验值是「每步 3~8 次工具调用能完成」。
  • 2. 局部重规划优于全局重规划 :只回退受影响的子任务,已完成的成果不浪费。
  • 3. 共享上下文双区 :全局区(目标、计划、已确认事实,只增不删)与局部区(当前步骤的临时观察,可压缩)。
  • 4. 统一中断语义 :无论哪一层失败,都收敛到同一套「检查点 → 回退 → 上报」流程。

18通俗解释 Agent

本节提炼
  • 比喻：大模型是只能说话的顾问，Agent 给顾问配上手脚和眼睛能办事
  • 区别像照菜谱做菜与请厨师：Agent 说清目标自己想办法

打个比方:

大模型是一个很聪明但只能坐在办公室里说话的顾问,他没有手也没有脚,不知道外面的情况,也不能出去办事。

Agent 就是给这位顾问配了一套「手脚」和「眼睛」:能查资料(搜索)、能读公司系统(数据库/接口)、能动手办事(下单/发邮件/改代码),而且他遇到问题会自己想「那我再换个办法试试」,而不是说完一句话就等你。

和 Siri 的区别在于:Siri 是你教它十件事它只会这十件,一件事要分几步它就不会了;Agent 是你说清目标,它自己想办法,做错了还会自己调整。 就像「照菜谱做菜」和「请了个厨师」的区别——菜谱只能做那几道菜,厨师能根据冰箱里有什么、你今天想吃什么来发挥。

19底层模型选型

本节提炼
  • 选型七维度：任务能力、工具调用、上下文、延迟吞吐、成本、可控性、稳定性
  • 主 Agent 用强模型定方向，子 Agent 用中小模型加专用 Prompt 省成本
  • 分层通常省 50%~70% 成本且端到端成功率几乎不掉
  • 子 Agent 全用大模型是最常见的烧钱姿势

选型维度:

  • 1. 任务能力 :复杂推理/规划 → 强模型;抽取/改写/分类 → 小模型足够。
  • 2. 工具调用能力 :Function Calling 的稳定性和格式遵循度,这是 Agent 的硬指标,选型时必须单独压测。
  • 3. 上下文窗口 :长任务、长文档场景是硬约束。
  • 4. 延迟与吞吐 :交互式(首 token 延迟敏感)vs 后台长任务。
  • 5. 成本 :长任务里 token 成本是决定性的。
  • 6. 可控性 :能否私有化部署、数据合规、是否支持缓存与限流。
  • 7. 稳定性与可用性 :是否有 SLA,多供应商备份。

主/子 Agent 不该用同样大的模型,应该按「职责分层」:

  • • 主 Agent(Planner/Supervisor):用强模型。 它负责全局拆解、路由、冲突裁决,一次调用定方向,错了代价最大,token 占比却不高 → 值得贵。
  • • 子 Agent(Executor):用中小模型 + 专用 Prompt。 任务被拆细后每一步更机械,小模型足够,且调用频次高、占比大 → 必须省。

实测经验:这个分层通常能把成本砍 50%~70%,而端到端成功率几乎不掉;反过来「子 Agent 全用大模型」是最常见的烧钱姿势。另外主 Agent 的 Prompt 要短而通用,子 Agent 的 Prompt 可以长而专,这种非对称设计效果最好。

20Agent 类型划分

本节提炼
  • 按认知分工：Planner、Executor、Critic、Router、Reflector、Memory Manager
  • 还可按系统形态、自主程度、技术路线划分

按认知分工(也是多 Agent 的角色原型):

  • 1. Planner :拆解任务、定计划。
  • 2. Executor / Worker :调工具干活。
  • 3. Critic / Verifier :校验结果、挑错。
  • 4. Router / Dispatcher :意图识别与分发。
  • 5. Reflector :复盘失败、沉淀经验。
  • 6. Memory Manager :读写长短记忆。

按系统形态:单 Agent、Router 型多 Agent、Supervisor-Worker、对等协作(去中心化)、流水线式。

按自主程度:固定 Workflow 中的 Agent 节点 → 半自主(有 HITL 审批)→ 全自主(给定目标长期运行)。

按技术路线:Prompt 驱动(纯提示词)、工具驱动(Function Calling/MCP)、代码驱动(生成并执行代码,Coding Agent)、状态机驱动(LangGraph 类图结构)。
