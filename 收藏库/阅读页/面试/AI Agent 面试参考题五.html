01多智能体协作与编排

本节提炼

02协作模式与优势

本节提炼
  • 多 Agent 是“用组织换能力”，解决上下文装不下、职责隔离、任务并行三类约束
  • 六种协作模式：Router、Supervisor、Pipeline、Debate、P2P、分层混合
  • 本质优势是上下文隔离与并行；上下文装得下、需强一致、缺可观测时不该上多 Agent
  • 任务简单、上下文装得下时盲目上多 Agent，单 Agent 更简单更快更便宜

先给一个清醒的定位(这比罗列优势更重要):

多 Agent 不是「更强的单 Agent」,而是「用组织换能力」的架构选择。 它解决的不是「智能不够」,而是**「上下文装不下、职责要隔离、任务能并行」**这三个结构性约束。多 Agent 的代价是:通信成本、状态一致性、错误传播、编排复杂度、成本翻倍。

协作模式(六种):

  • 1. Router 分发 :一个路由 Agent 按意图分给专职 Agent,子 Agent 之间无交互。 最简单、最常用 。
  • 2. Supervisor / Orchestrator-Worker :主 Agent 拆任务、派发、汇总,子 Agent 只干活不回话。 生产主流。
  • 3. Pipeline 流水线 :固定顺序的多阶段(如 抽取 → 审核 → 格式化),每个阶段可以是一个 Agent。
  • 4. Debate / 多角色讨论 :多个 Agent 扮演不同角色(支持方/质疑方)互相辩论后收敛。 适合提高判断质量,但成本高。
  • 5. 对等协作(P2P / 去中心化) :Agent 之间自由通信、协商。 灵活但难以控制和观测,生产少用 。
  • 6. 分层混合 :全局 Supervisor + 局部 ReAct + 若干专职子 Agent(见第 17 题)。

相比单 Agent 的优势(要讲「只有多 Agent 才能做到」的):

  • 1. 上下文隔离(最本质的优势) :每个子 Agent 有独立窗口,避免「一个巨大的上下文」。做文献调研时,50 篇文档的原文不可能全放进一个窗口,但可以分给 5 个子 Agent 各读 10 篇,只回结论。 这是单 Agent 无论多强的模型都做不到的。
  • 2. 并行提速 :独立子任务可并发执行,墙钟时间显著下降。
  • 3. 职责与权限隔离 :财务 Agent、运维 Agent 各自权限独立,事故面收窄(也是安全需求)。
  • 4. 专业化优化 :每个子 Agent 可以用不同的模型(强/弱)、不同的提示、不同的工具集和评测集,针对领域深度优化。
  • 5. 独立演进与可观测 :单个子 Agent 可独立评测、灰度、回滚、替换,不牵动全局。
  • 6. 抗上下文污染 :子任务的噪声不会污染主线。

什么时候不该用多 Agent(必须说,否则显得盲从):

  • • 任务本身不复杂、上下文一个窗口装得下 → 单 Agent 更简单、更快、更便宜 ;
  • • 需要强一致性的任务(如事务性操作)→ 多 Agent 的一致性成本很高;
  • • 团队没有做好可观测和调度的准备 → 多 Agent 会变成无法调试的黑盒。
  • • 经验:能用单 Agent + 好工具解决,就别上多 Agent。 多 Agent 是「上下文与职责」逼出来的,不是「效果更好」选出来的。

03多 Agent 选型决策树

本节提炼
  • 选型决策树五问：上下文装得下吗、子任务强依赖吗、可枚举吗、需多视角吗、要并行吗
  • 五个依据：上下文压力、可枚举性、并行收益、一致性与错误代价、观测与调试能力
  • 落地：从单 Agent 起步，遇上下文墙才拆，首选 Router 或 Supervisor

(架构模式清单见第 5 题;这里给选型决策树,这才是这题的重点。)

选型决策树:

  • 1. 一个上下文窗口装得下全部信息吗?
  • ├─ 装得下 → 单 Agent(ReAct 或 Workflow+Agent 节点)
  • └─ 装不下 → 需要「隔离」→ 走多 Agent
  • 2. 子任务之间高度依赖、串行、需要频繁共享中间状态吗?
  • ├─ 是 → 不要多 Agent;改为「单 Agent + 工具化封装」或 Workflow
  • └─ 否 → 多 Agent 可行
  • 3. 任务类型是否可预先枚举?
  • ├─ 可枚举(如客服意图分类)→ Router 分发(最轻)
  • └─ 不可枚举、需动态拆解 → Supervisor-Worker
  • 4. 是否有明显的多视角判断需求(评审、论证)?
  • ├─ 是 → Debate/Critic 模式(成本高,慎用)
  • └─ 否 → 保持 Supervisor-Worker
  • 5. 子任务需要并行吗?
  • ├─ 是 → Supervisor + 并行子 Agent + 结果聚合
  • └─ 否 → 串行执行即可

选型的五个依据:

  • 1. 上下文压力 :这是第一驱动力。装不下才拆。
  • 2. 任务可枚举性 :可枚举 → Router(便宜、可靠);不可枚举 → Supervisor + 动态拆解(灵活、贵)。
  • 3. 并行收益 :子任务独立性越强,并行的收益越大。
  • 4. 一致性与错误代价 :需要强一致 → 减少 Agent 数量,增加确定性编排;错误代价高 → 加 Critic 与 HITL。
  • 5. 观测与调试能力 :没有轨迹追踪和状态可视化的能力,就不要上复杂多 Agent。

落地建议(加分):「从单 Agent 起步,只在遇到上下文墙或权限隔离需求时才拆;拆出来的第一个模式几乎总是 Router 或 Supervisor-Worker,而不是 Debate/P2P。」

04子 Agent 通信协议

本节提炼
  • 三种通信方式按耦合度：结构化消息（推荐）、共享状态黑板、文件/工作区引用传递
  • 协议要素：任务契约、状态机、超时心跳、幂等、错误契约、权限收窄、版本兼容
  • 串并行取舍：有依赖必须串行，无依赖尽量并行，并行前提是结果可合并且设并发上限
  • 用自然语言或 Markdown 直接传任务，解析不一致且约束易在转述中丢失

通信方式(三种,按耦合度排序):

  • 1. 结构化消息(推荐) :JSON schema 定义的 Task/Result 对象。字段:task_id、目标、输入、约束、期望输出格式、deadline、预算、父任务 id。 可校验、可回放、可审计。
  • 2. 共享状态(黑板模式) :所有 Agent 读写同一状态存储(LangGraph 的 shared state / 数据库 / 消息队列)。 耦合度最高,适合需要频繁共享中间结果的场景,但容易产生竞争与污染。
  • 3. 文件 / 工作区传递 :用文件系统或对象存储传递大产物(报告、代码、数据集),消息里只放引用。

不推荐:用自然语言/Markdown 直接传任务(第 95 题会详述其漂移问题)。

协议设计的十个要素(这是本题的核心):

  • 1. 任务契约(schema) :目标、输入、约束、期望输出格式、成功标准。 必须结构化。
  • 2. 任务状态机 :CREATED / RUNNING / BLOCKED / NEEDS_INPUT / DONE / FAILED / CANCELLED。父 Agent 订阅状态而不是靠猜。
  • 3. 同步/异步双模 :短任务同步返回,长任务异步 + 事件推送/回调/轮询。
  • 4. 超时与心跳 :明确 deadline;长任务定期心跳上报进度(父 Agent 才能区分「在跑」和「卡死」)。
  • 5. 幂等与去重 :task_id 唯一,重复投递幂等,重试不产生重复副作用。
  • 6. 错误契约 :失败要返回结构化信息(错误类型、可重试性、部分结果、已完成的部分),便于父 Agent 决策。
  • 7. 上下文传递策略 :默认传「必需最小集」,不传全量上下文(隐私 + token + 污染三重考量)。
  • 8. 能力发现 :Agent Card / 注册中心,支持动态发现新 Agent。
  • 9. 身份与权限 :跨 Agent 调用带身份,权限沿调用链收窄(下游不能比上游权限更大)。
  • 10. 版本与兼容 :协议带版本号,能力协商。

串行 vs 并行的取舍:

维度串行并行
依赖有前后依赖时必需无依赖才能并行
延迟累加取最慢的一个
状态一致性简单需要合并策略(去重、冲突仲裁)
成本相同相同(但更快完成)
失败处理简单(前一步失败即停止)复杂(部分成功、部分失败怎么办)
上下文合并顺序追加需去重、排序、冲突消解

取舍原则:

  • 1. 有依赖必须串行 ——不要为了并行引入「猜测前置结果」的假并行。
  • 2. 无依赖尽量并行 ——延迟收益明显(O(n) → O(max))。
  • 3. 并行的前提是「结果可合并」 :如果并行结果的合并本身很复杂(需要仲裁冲突),可能串行反而更省心。
  • 4. 并行要有并发上限 :子 Agent 数量受模型限流、成本预算、下游系统承受力约束,必须设 slot 上限。
  • 5. 部分失败的语义要提前定义 :是「任一失败则整体失败」还是「允许部分成功 + 说明缺失」? 必须在设计时明确,而不是运行时碰运气。
  • 6. 并行度与上下文预算联动 :并行子 Agent 的结果要合并回主上下文,主上下文会骤增 → 合并时 必须做摘要压缩,只回结论 。

05子 Agent 动态选择

本节提炼
  • 规则优先命中高频意图，模型判断兜底
  • Function Calling 把子 Agent 包装成工具，复用校验、超时、重试、观测
  • description 写能力边界、输入输出与“何时不该选”
  • 必须有“都不选”、限次数回退、决策可观测
  • 路由 Prompt 式让模型直接输出 Agent 名，格式容易崩

先回答问题:「两者结合」,而且是分层结合的。

Router 层(Router Agent 或规则):

  • 1. 规则优先(降本增效) :高频、明确的意图用规则/正则/关键词/分类器直接路由—— 确定性、零延迟、零成本、可解释 。这是生产系统的第一道。
  • 2. 动态判断兜底 :规则未命中或置信度低时,交给模型的 Router 判断。

模型动态选择的实现方式(三种):

  • 1. Function Calling 式(最常用) :把每个子 Agent 包装成一个「工具」(name = delegate_to_xxx ,description = 它擅长什么),主 Agent 通过 Function Calling 决定调用谁。 这是工业界最主流的做法 ,因为复用了工具调用的全部基础设施(校验、超时、重试、观测)。
  • 2. 路由 Prompt 式 :给模型子 Agent 清单 + 任务描述,让它输出选中的 Agent 名。简单但格式容易崩。
  • 3. 检索式 :把子 Agent 的能力描述向量化,检索匹配 Top-K 候选,再做小范围选择。 子 Agent 数量多时(几十上百)必须这么做 (呼应第 60 题的检索思路)。

选择的关键依据(子 Agent 的 description 怎么写):

  • • 能力边界 :擅长什么、不擅长什么;
  • • 输入要求 :需要什么前置信息;
  • • 输出形式 :返回什么;
  • • 何时不该选它 (负向描述,最能降低误选)。

固定工作流 vs 动态判断的判断标准:

场景选择
意图可枚举、边界清晰、高频固定工作流 / 规则路由
意图长尾、表达多样、需要语义理解动态判断
错误代价高(如资金操作)固定工作流 + 人工确认
需要组合多个子 Agent 能力动态判断(Supervisor)

工程实践(最有说服力的答法):

  • 规则层(0 延迟) → 命中率约 60~70%(高频意图)
  • ↓ 未命中
  • 小模型分类器 → 候选集缩小到 3~5 个
  • 主模型 Function Calling 决策 → 最终选定(可带并行调用)
  • 执行 + 校验(结果是否符合该 Agent 的预期输出)→ 不符合则可回退重选

三个重要设计点:

  • 1. 必须有「都不选」的选项 :允许模型判断「没有合适的子 Agent」,而不是硬选一个—— 这是降低误选最有效的手段之一 (也可以设计成「兜底 Agent」)。
  • 2. 可回退 :子 Agent 返回不符合预期(输出格式错、明显不相关)时,允许主 Agent 重新选择; 但要限制重选次数 (防止路由振荡)。
  • 3. 决策可观测 :记录「候选集、选中项、理由、结果质量」,持续优化 description 与路由规则。

06结论冲突处理

本节提炼
  • 不一致分四类：事实性冲突、判断性分歧、信息不对称、错误，处理方式不同
  • 七种机制按优先级：权威数据源、依据加置信度、仲裁、辩论、投票、HITL、保守策略
  • 预先定义裁决规则，区分“必须一致”与“允许多样”，分歧显式化并留痕
  • 投票法在所有 Agent 共享同一错误前提时会一致地错
  • 为了和谐而妥协，迁就出四不像方案比明确分歧更糟

先分类:不一致有四种性质,处理方式完全不同。

  • 1. 事实性冲突 (A 说订单金额 100,B 说 200)→ 可验证 ,去查权威数据源裁决。
  • 2. 判断性分歧 (A 认为方案可行,B 认为有风险)→ 不可直接验证 ,需要仲裁机制。
  • 3. 信息不对称 (A 掌握的信息比 B 新/全)→ 补齐信息后往往自然收敛。
  • 4. 错误 (A 明显错了)→ 校验识别并剔除错误结论。

处理机制(七种,按优先级):

  • 1. 权威数据源裁决(最优先) :能用事实核查解决的,绝不靠「讨论」解决。 先查数据再争论 ——这是最重要的一条。
  • 2. 结构化输出 + 依据(reason + evidence) :要求每个 Agent 不只给结论,还要给 依据和置信度 。有了依据,冲突就变成了「谁的证据更强」,可比较。
  • 3. 仲裁 Agent(Judge/Arbiter) :专门的角色,输入是各方结论 + 依据,输出是裁决结果 + 理由。 仲裁 Agent 要有独立的评判标准 (如「以官方文档为准」「以最新数据为准」),而不是凭偏好。
  • 4. 多轮辩论(Debate) :让冲突方看到对方论据后重新论证,通常 1~2 轮就能收敛(前提是分歧源于信息不对称或推理疏漏,而不是价值判断)。 注意成本,要设轮次上限。
  • 5. 加权投票 / 多数表决 :多个独立 Agent 同题作答取多数。 前提是错的分布要分散 ——如果所有 Agent 共享同一个错误前提(比如都读了同一份被注入的文档),投票会一致地错(这是投票法的致命弱点,要主动说出来)。
  • 6. 升级人工(HITL) :判断性分歧且代价高(资金、合规、对外发布)→ 不纠结,直接升级人工。 「不确定就找人」是成熟系统的标志,不是失败。
  • 7. 降级为保守策略 :无法裁决时选择 最保守/最安全的方案 (如「暂不执行,先报告」),或给出「存在分歧」的明确提示,而不是随便选一个。

关键设计原则:

  • 1. 预先定义裁决规则 ,而不是运行时临时决定:谁在什么情况下有优先权(如「安全 Agent 有一票否决权」)。
  • 2. 区分「必须一致」和「允许多样」 :事实类必须收敛;创意/方案类可以保留多选项呈现给用户。 不要为了「一致」而抹掉有价值的多样性。
  • 3. 冲突本身是有价值的信号 :冲突往往意味着「这个任务本身有歧义或信息不足」——可以把它转化为「向用户澄清」的动作。
  • 4. 防「为了和谐而妥协」 :多个 Agent 互相迁就产出一个四不像的方案,比明确的分歧更糟。 要求分歧必须显式化。
  • 5. 记录全过程 :分歧点、各方依据、裁决理由都要留痕,这是复盘和审计的依据。

07完成感知与结果回收

本节提炼
  • 感知完成四机制：同步调用、异步事件/回调、异步轮询、状态机加检查点
  • 结果回收六要素：结构化契约、大产物走引用、摘要回传、校验后接受、部分失败语义、合并去重
  • 用 task_id 幂等防旧结果覆盖新结果；子任务 trace 挂主 trace 保证可观测
  • 把不完整结果伪装成完整，必须用 status/partial 显式标注缺失

「怎么知道完成」的四种机制:

  • 1. 同步调用(最简单) :主 Agent 调子 Agent 是一个阻塞调用,返回即完成。 适合短任务,但会阻塞主循环、无法并行。
  • 2. 异步 + 事件/回调 :子 Agent 完成后发布事件(消息队列 / 回调 / 状态变更通知),主 Agent 订阅。 生产主流,支持并行与长任务。
  • 3. 异步 + 轮询 :主 Agent 定期查询任务状态接口。 简单但延迟高、浪费请求;可接受低频轮询(如 5s)配合事件加速。
  • 4. 状态机 + 检查点 :任务状态持久化,主 Agent 从共享状态读取(CREATED/RUNNING/DONE/FAILED)。 最可靠,天然支持断点恢复。

超时与心跳(关键,回答「怎么区分在跑和死了」):

  • • 子 Agent 必须 定期上报心跳 + 进度 (如「已处理 3/10 篇文档」)。
  • • 主 Agent 依据「最后一次心跳时间 > 阈值」判定卡死,而不是只等 deadline。
  • • 区分三种超时 :单步超时、子任务整体超时、主任务整体超时,层层收敛。
  • • 卡死要能 主动取消 (发取消信号,子 Agent 优雅退出并返回已完成部分)。

结果回收(这是本体的重点,六个要素):

  • 1. 结构化结果契约 :子 Agent 返回的不是自由文本,而是 {task_id, status, result, evidence/sources, confidence, artifacts, error, partial} 。 有 status 才能判断是「完成」还是「部分完成」。
  • 2. 大产物走引用 :子 Agent 产生的大产物(报告、代码、数据集)写到工作区/对象存储,只把 引用 + 摘要 回收给主 Agent。 主上下文绝不能被子 Agent 的全量输出灌满。
  • 3. 摘要而非原文 :回收时对结果做压缩(结论 + 关键依据 + 出处),原文留在工作区可按需取回。
  • 4. 校验后再接受(重要) :主 Agent / Critic 校验子 Agent 的产出是否满足该子任务的 成功标准 (格式、完整性、是否偏离目标),不合格则:重试、换子 Agent、或局部重规划。
  • 5. 部分失败的处理语义 :明确「允许部分成功」还是「全有或全无」。允许部分成功时,结果里必须有 partial 标记 + 缺失说明, 绝不能把不完整的结果伪装成完整的 。
  • 6. 合并与去重 :并行子任务结果回收后要去重、排序、冲突仲裁(多个子 Agent 可能有重叠结论)。

幂等与去重: 结果回收可能重复(重试、超时后迟到返回),要用 task_id 幂等处理,迟到的结果要丢弃或按版本取最新,否则会出现「旧结果覆盖新结果」。

可观测: 每个子任务都要有独立的 trace(起点、心跳、工具调用、结束),主 Agent 的 trace 里挂子 trace 的引用——跨 Agent 的链路追踪是多 Agent 系统可调试的前提。

08异步消息与兜底

本节提炼
  • 消息设计：类型化、幂等键、trace 追溯、deadline、预算、错误契约、鉴权
  • 兜底七层：退避重试、死信队列、超时取消、任务重派、降级兜底、补偿事务、告警熔断
  • 关键认知：“消息已投递”不等于“任务已完成”，要有端到端状态确认
  • 依赖 MQ 投递成功当业务成功，接收方处理失败无人知晓
  • 没有持久化队列，进程重启丢任务

消息设计(典型的任务消息结构):

  • "msg_id": "uuid", // 消息唯一 id,用于幂等去重
  • "task_id": "uuid", // 任务 id
  • "parent_task_id": "uuid", // 父任务,支持树状追溯
  • "trace_id": "uuid", // 全链路追踪
  • "type": "TASK_ASSIGN", // TASK_ASSIGN | PROGRESS | RESULT | ERROR | CANCEL | HEARTBEAT
  • "from": "supervisor-1", // 发送方身份(用于鉴权与审计)
  • "to": "research-agent-2", // 目标 Agent(或 topic)
  • "version": "1.0", // 协议版本
  • "timestamp": 1732353600000,
  • "deadline": 1732357200000, // 硬截止
  • "payload": {
  • "goal": "调研 X 技术在企业落地的风险",
  • "inputs": { "scope": "...", "max_sources": 20 },
  • "constraints": ["只采信近 12 个月的资料", "必须给出来源链接"],
  • "expected_output_schema": { ... }
  • "context_ref": "ws://session-1/brief.md", // 大上下文走引用,不塞进消息
  • "budget": { "max_tokens": 50000, "max_steps": 30, "max_cost": 1.0 },
  • "retry": { "attempt": 1, "max_attempts": 3 }

设计要点(十条):

  • 1. 消息类型化 :任务、进度、结果、错误、取消、心跳各有明确类型与 schema。 不要用同一种消息兼职所有用途。
  • 2. 幂等键 : msg_id + task_id 做去重,消费者侧维护已处理集合(或数据库唯一索引)。 这是防「重试导致重复执行」的根本手段。
  • 3. 可追溯 :trace_id + parent_task_id 串起调用树,便于追踪与可视化。
  • 4. 上下文引用化 :大上下文用 ref 传递,不塞进消息体(消息会经过 MQ/网络,体积即成本)。
  • 5. 超时与截止 :deadline 在消息里显式声明,而不是靠调用方默认值。
  • 6. 预算传递 :token/步数/成本预算随任务下发, 子 Agent 不能超预算 ,这是防成本失控的关键。
  • 7. 错误契约 :错误消息要带错误码、类型、可重试性、已完成部分、建议动作。
  • 8. 版本协商 :协议带版本,接收方不支持时明确拒绝(而不是静默错误解析)。
  • 9. 传输选择 :MQ(Kafka/RabbitMQ/Redis Stream)保证可靠投递与削峰;需要低延迟可用 gRPC + 异步回调。 关键:必须有持久化队列 ,否则进程重启丢任务。
  • 10. 鉴权 :消息要带发送方身份,接收方校验权限; 防止 Agent 伪造消息或越权委派 。

通信失败的兜底机制(六层):

  • 1. 重试(带退避与上界) :指数退避 + 抖动,最多 3 次;幂等保证重复安全。
  • 2. 死信队列(DLQ) :超过重试次数的消息进 DLQ, 不丢 ;由人工或补偿任务处理。这是「消息不丢」的最后一道。
  • 3. 超时检测与主动取消 :超过 deadline 或心跳中断 → 主 Agent 取消该任务并标记失败。
  • 4. 任务重派(Reassign) :子 Agent 无响应/崩溃 → 把任务派给另一个实例(前提是任务幂等或能从上个检查点续跑)。
  • 5. 降级(本地兜底) :子 Agent 不可用时,主 Agent 用简化方式自己完成或返回「该部分不可用」的明确说明。
  • 6. 整体事务语义 :如果任务不能部分完成(需要原子性),要定义补偿动作(Saga/Best-effort 补偿),而不是让主 Agent 带着半成品继续。
  • 7. 告警与熔断 :连续通信失败要告警并熔断该 Agent(不再派任务给它),避免浪费预算。

一个易漏的关键点(加分):「消息已投递」不等于「任务已完成」。异步通信里最危险的是「消息成功发出,但接收方处理失败」——所以必须有端到端的任务状态确认(接收方确认收到 + 定期进度 + 最终结果确认),而不能依赖 MQ 的投递成功作为业务成功的依据。

09Markdown 传任务防漂移

本节提炼
  • Markdown 风险：格式无约束、约束转述丢失、无 schema 无法校验、嵌套拆分误差放大
  • 核心机制：Markdown 给人看加 JSON 给机器用双轨，机器可读部分以 JSON 为准
  • 约束原文不可变传递、拆分后立即做覆盖/冲突/依赖/可执行校验、接收方复述确认
  • 验收标准前置并硬性校验，限制拆分深度 2~3 层，关键节点加人工检查点
  • 下游用自己的话转述上游约束，“必须不修改”变成“尽量少改”

先承认 Markdown 传任务的合理性与风险:

  • • 合理性 :可读性好、人能审查、天然适合作为「人类可读的中间产物」,适合轻量场景和 HITL。
  • • 风险 :①格式无约束,接收方解析方式不一致(同样一段文字,不同 Agent 理解不同);② 关键约束容易在转述中丢失或软化 (「必须不修改对外接口」→ 变成「尽量少改」);③无 schema,无法校验,错误静默传播;④嵌套拆分时每层都无损转述一次,误差逐层放大(类似「传话游戏」)。

防传播的八道机制(按重要性):

  • 1. 双重表示:Markdown 给人看,JSON 给机器用(最核心) 。Markdown 保留作为可读的说明与依据,但 任务的机器可读部分(目标、输入、约束、输出 schema、验收标准)必须有 JSON 副本 ,Agent 之间以 JSON 为准。 这是从根上解决问题的做法。
  • 2. 任务契约的强约束字段 :任务拆分产物必须包含:
  • • goal (可验证的完成定义,避免「写一份报告」这种模糊描述);
  • • inputs (明确的数据来源,而不是「相关资料」);
  • • constraints (硬约束清单, 逐条列出,不可改写 );
  • • acceptance_criteria (怎么算完成,最好可自动校验);
  • • out_of_scope (明确不做什么, 防止范围蔓延 );
  • • output_schema (结构化输出要求)。
  • 3. 原始约束的「不可变传递」 :父任务的硬约束要以 引用的方式原样传递 (甚至原文附在最前面), 禁止下游用自己的话转述上游约束 。转述是信息损失的主要来源。
  • 4. 拆分后立即校验(最关键的一步) :
  • • 覆盖性检查 :所有子任务的并集是否覆盖父任务的目标?有没有漏掉的子目标?
  • • 冲突检查 :子任务之间有无矛盾(如 A 要改接口、B 要保证接口不变)?
  • • 依赖检查 :顺序和依赖是否合理,有没有循环依赖?
  • • 可执行性检查 :每个子任务是否信息充分(缺输入的要标出来)? 让一个独立的 Critic/校验 Agent 做这件事 ,而不是靠拆分的 Agent 自检(自检盲区很大)。
  • 5. 双向确认(Ack + 复述) :接收方在开工前 用自己的话复述「我要做什么、不做什么、验收标准是什么」 ,由父 Agent 校验一致后才开工。 这能挡住绝大多数理解偏差 ,而且成本很低。这是「传话游戏」的标准解法。
  • 6. 验收标准前置 + 结果校验 :每个子任务的 acceptance_criteria 在拆分时就定义好;子任务完成后 按标准自动校验 (格式、字段、覆盖度),不合格就打回, 不允许把不合格产物往上合并 。 质检点必须是硬性的,否则错误会自动上流。
  • 7. 隔离与沙箱 :让子任务在受限范围内工作(只能改指定文件、只能查指定表), 即使理解错了也不会造成大范围破坏 。同时保留原始输入的快照,便于回溯。
  • 8. 可观测与回放 :每次传递保留「父任务原文 → 拆分产物 → 复述 → 结果」的完整链路, 出错时能定位是哪一层的问题 (是拆分错、理解错、还是执行错)。这是持续优化的前提。

其他补充手段:

  • • 限制拆分深度 :嵌套超过 2~3 层,误差放大就难以控制;深层嵌套应改为「平铺的子任务 + 明确的依赖图」。
  • • 关键任务加重人工检查点(HITL) :在拆分产物进入执行前让人类审一眼—— 这是成本最低、效果最好的兜底 。
  • • 统一模板 :所有任务用同一套 Markdown/JSON 模板,减少格式歧义。
  • • 数值与专有名词原样保留 :数字、ID、接口名、参数名禁止改写(压缩和转述中最容易出错的地方)。

一句话总结:Markdown 给人看、JSON 给机器用来做双轨;约束原文传递不复述;拆分后必做覆盖/冲突/依赖校验;接收方必须复述确认;验收标准前置并硬性校验;限制嵌套深度 + 关键节点上人工。

10三层隔离与统一存储

本节提炼
  • 上下文隔离：独立会话/线程，只传必需最小集，大数据走引用，强隔离用独立容器
  • 权限隔离：独立身份不共享凭证，权限降级传递，数据行级在数据层强制
  • 存储隔离：命名空间前缀、独立凭证、工作区路径系统生成、默认私有
  • 跨 Agent 传输优先引用加服务化取数加统一 schema 加全程鉴权，而非共享存储直读
  • 共享凭证等于没有隔离；引用不做鉴权会变成绕过权限的后门

三层隔离的实现:

1. 上下文隔离(最基础)

  • • 独立会话/线程 :每个 Agent 实例有独立的 thread 与消息历史(LangGraph 的 thread_id / 独立 Session)。
  • • 只通过消息传「必需最小集」 :不共享内存对象、不共享对话历史, 跨 Agent 传递的是结构化的任务与结果 ,而不是上下文本身。
  • • 上下文引用而非内容 :需要共享大数据时,传工作区引用(路径/url + 摘要),各 Agent 各自读取, 物理上不共享上下文 。
  • • 进程/容器级隔离(强隔离场景) :每个 Agent 独立容器,内存与上下文完全不可见—— 这是唯一能称为「完全」隔离的方式 ,牺牲的是通信开销。

2. 权限隔离

  • • 独立身份 :每个 Agent 有独立的服务身份(client_id / 服务账号 / mTLS 证书), 不共享凭证 (共享凭证等于没有隔离)。
  • • 权限降级传递(核心原则) :跨 Agent 调用时, 下游 Agent 的权限 ≤ 上游 × 职责 ;不能出现「A 委派给 B,B 反而获得 A 没有的权限」。
  • • 工具/数据权限按 Agent 绑定 :在 MCP / 工具注册中心维护「Agent × 工具 × 操作 × 数据范围」矩阵(见第 63 题)。
  • • 数据行级隔离 :同一工具,不同 Agent 看到的数据范围不同(按租户/区域/业务线过滤)—— 在数据访问层强制,不能靠 Agent 自觉 。
  • • 审计 :每个 Agent 的每次调用独立留痕(身份 + 时间 + 参数 + 结果摘要),能回答「谁在什么时候访问了什么」。

3. 存储隔离

  • • 命名空间隔离 : tenant_id / agent_id / session_id / task_id 作为存储路径或表分区的前缀, 所有读写强制带命名空间 。
  • • 每 Agent 独立凭证访问存储 :用不同的数据库账号/角色,靠数据库自身的权限体系兜底,而不是靠应用层过滤。
  • • 工作区隔离 :文件系统的会话工作区按 Agent + 会话分目录, 路径必须由系统生成 (禁止模型拼接路径,防穿越)。
  • • 大对象隔离 :对象存储的 bucket/prefix 隔离 + 预签名 URL 的时效与范围限制。
  • • 泄漏防护 :跨租户/跨 Agent 的数据必须有显式的「共享」声明才可读, 默认私有 。

跨 Agent 场景下统一存储怎么通信和传输(这是难点,五种方案):

方案机制适用
引用传递(最推荐)消息里只放 ref(路径/ID),接收方用自己的凭证去取大对象、跨信任域、绝大多数场景
共享存储 + 命名空间共享同一套存储,靠命名空间与凭证隔离同信任域内的多个 Agent,成本最低
数据服务化(API 层)不直接共享存储,而是通过统一的数据服务 API 访问,服务内做鉴权与过滤权限要求高、需要统一审计
消息传递数据体数据直接放消息里仅适合小数据(几 KB),大数据会让 MQ 与上下文都崩
事件溯源/同步任务通过事件流把变更同步到各自的本地存储需要各 Agent 有独立数据副本的场景

关键设计点:

  • 1. 引用传递时必须有鉴权 :接收方用 自己的凭证 取数据,由存储层/数据服务校验它是否有权访问该 ref。 否则「引用」就变成了绕过权限的后门。
  • 2. 优先「服务化」而非「共享存储」 :直接共享存储的耦合与风险都高,通过 API 访问能插入鉴权、限流、审计。
  • 3. schema 统一 :跨 Agent 传递的数据结构要有统一契约(同一份 schema 演进),否则会出现「字段理解不一致」的静默错误。
  • 4. 传输加密 + 完整性 :跨进程/跨网传输要 TLS,重要数据加签名防篡改。
  • 5. 生命周期与清理 :共享数据必须有 TTL 与清理策略, 尤其是含敏感信息的工作区 。
  • 6. 一致性策略 :共享存储天然带来一致性问题—— 明确是「强一致」还是「最终一致」 ;需要强一致的操作用事务或统一服务,不要让多个 Agent 各自写同一份数据。

一句话总结:上下文靠「独立会话 + 引用传递」隔离,权限靠「独立身份 + 权限降级传递 + 数据层强制过滤」隔离,存储靠「命名空间 + 独立凭证 + 默认私有」隔离;跨 Agent 数据交换优先用「引用 + 服务化取数 + 统一 schema + 全程鉴权」,而不是共享存储直读。

11调研类调度选型

本节提炼
  • 调研类系统几乎总选中心化，因需全局去重、冲突仲裁、预算控制、统一收敛
  • 回退靠检查点、失败粒度化、分级重试、降级、局部重规划，语义是回退而非全量重跑
  • 进度可观测：任务树、心跳进度、状态机、中间产物、成本预算、人工干预
  • 设“提前收敛”：信息增益低于阈值或预算用掉 80% 即汇总
  • 去中心化难观测、调试难度极高、有死锁与循环风险

第一问:中心化 vs 去中心化

结论:调研类系统几乎总是选中心化(Supervisor/Orchestrator),理由充分。

可控性强(全局视野,可控预算)弱(涌现行为难预测)
可观测好(单一入口,调用树清晰)差(无全局视图)
一致性好(统一仲裁)难(无权威裁决者)
扩展性中心有瓶颈(可分层缓解)扩展性好
死锁/循环风险低高(相互等待、无限对话)
调试难度低极高
适合场景绝大多数生产系统需要高度自治、对等协商的场景(罕见)

调研类为什么必须中心化:

  • 1. 需要全局去重与覆盖控制 :调研最容易出现「多个子 Agent 反复查同一批资料」和「重要方向没人查」—— 只有中心化的调度者能维护「已覆盖 / 待覆盖」的全局视图 。
  • 2. 需要冲突仲裁 :不同子 Agent 的结论冲突时要有统一的裁决者(见第 92 题)。
  • 3. 需要预算控制 :调研很容易发散(无限查下去),中心才能设总预算与收敛条件。
  • 4. 需要统一收敛 :调研的终点是「一份报告」,必须有统一的汇总者。

去中心化唯一有优势的是规模:子任务极多、中心成为瓶颈时,可以用分层中心化(顶层 Supervisor → 若干个二级 Supervisor → 叶节点 Worker)来缓解,而不是纯 P2P。

第二问:子任务失败可回退

  • 1. 检查点(Checkpoint) :每个子任务完成后把状态(结果 + 产出物引用)持久化。 回退 = 回到上一个检查点,而不是从头开始。
  • 2. 失败粒度化 :子任务要拆得足够细,细到「单个子任务失败不影响其他子任务」。 粒度是回退能力的前提。
  • 3. 重试策略分级 :瞬时错误自动重试(带退避);语义错误(结果不合格)换策略重试(换检索词、换数据源、换子 Agent);超过次数则标记失败并上报。
  • 4. 替代方案(降级) :某个子任务失败 → 用更弱但可行的手段(如用摘要代替全文分析),并在报告里明确标注「该部分方法降级」。
  • 5. 局部重规划 :失败后只重规划受影响的子图,已完成的成果保留( 这是「回退」的正确语义,不是全量重跑 )。
  • 6. 部分交付 :调研场景允许部分成功—— 输出已有的结论 + 明确列出未完成的调研方向与失败原因 ,而不是整体失败。诚实标注缺失比伪装完整重要。
  • 7. 幂等 :重试和回退都不能产生重复副作用(重复写入、重复计费)。

第三问:进度可观测

  • 1. 任务树可视化 :调用树(task_id + parent_task_id)实时展示,能点开看每个子任务的输入输出与状态。
  • 2. 心跳与进度百分比 :子 Agent 定期上报「已处理 X/Y」(如 3/10 篇文档、已调用 5 次检索)。
  • 3. 状态机暴露 :每个任务的状态(CREATED/RUNNING/BLOCKED/DONE/FAILED)实时可见,并对用户呈现为可理解的阶段(而非技术术语)。
  • 4. 中间产物可见 :让用户能看到「目前已收集到的要点/来源列表」—— 既提升信任,也让用户能及早纠偏 (这是调研类产品最重要的体验设计)。
  • 5. 成本与预算进度 :已消耗 token / 轮次 / 成本 vs 预算,达到阈值告警或强制收敛。
  • 6. 终止与干预入口 :用户可以随时停止、追加要求、指定方向( HITL 贯穿全程 )。
  • 7. 完整轨迹留存 :全链路 trace,支持事后回放与问题定位。

一个实操建议(加分):调研类系统一定要设计**「提前收敛」机制**——不能等到子任务全部完成才输出。做法:当「新增信息增益低于阈值」(连续 N 次检索无新结论)或预算用掉 80% 时,就触发汇总,"足够的证据"比"全部的证据"更符合用户预期。

12协作方式与动态分发

本节提炼
  • 除路由外还有八种协作，如 Supervisor、Pipeline、Critic、Handoff 等
  • Agent Team 核心：角色化、共享任务列表、自主领取、DAG 依赖管理、Owner 协调
  • 动态分发：任务队列加状态机加原子领取，能力标签匹配，支持动态插单
  • 分解阶段用静态，执行阶段用动态
  • 原子领取做不好会两个 Agent 领同一任务，是最容易出 bug 的地方

除路由之外的协作方式(回顾并展开第 88 题的清单,重点讲特色):

  • 1. Supervisor-Worker(编排-执行) :中心拆解 + 派发 + 汇总。 生产最主流。
  • 2. Pipeline(流水线) :多阶段串行,如「检索 → 抽取 → 校验 → 汇总」,每阶段独立 Agent。 适合有明确阶段划分的任务。
  • 3. Reflection / Critic-Refine(评审-改进) :一个 Agent 产出,另一个 Critic 挑错,产出方修订,可多轮。 这是「提高质量」的协作,不是「扩大能力」的协作。
  • 4. Debate(辩论) :多角色互相对抗后收敛(见第 92 题)。
  • 5. Hierarchical / 分层团队 :Supervisor → Team Lead → Worker,分层中心化。
  • 6. Handoff(交接/接力) :一个 Agent 完成阶段性任务后 把整个会话控制权交给下一个 Agent (OpenAI Agents SDK 的 Handoff 就是这个模型)。特点是会话连续、上下文随交接传递, 适合「专家接力」场景 (客服 → 技术支持 → 售后)。
  • 7. Shared Blackboard(黑板模式) :所有 Agent 读写同一个共享状态,适合需要频繁共享中间产物的协作。
  • 8. Market / Bidding(竞价分配) :任务广播后 Agent 各自报价(基于能力与当前负载),调度者选最优。 理论上优雅,实践中很少用 (成本高、收益不明显)。

Agent Team(团队式协作)的核心概念:

  • • 角色化 :每个 Agent 有明确的角色定义(名字、职责、能力边界、输出风格),像团队分工。
  • • 共享任务列表(Task List / Backlog) :团队共享一个任务队列,而不是由主 Agent 逐个点名。
  • • 自主领取(Self-claiming) :空闲的 Agent 从共享队列中 主动领取 可执行的任务。这区别于「指挥式分发」。
  • • 依赖管理 :任务之间有依赖关系(DAG),只有前置完成的任务才可被领取。
  • • 共享产物区 :团队成员产出的成果放在共享工作区,彼此可见可用。
  • • 协调机制 :需要一个协调者做冲突处理、依赖仲裁、最终汇总(即使是 Team 模式,也需要一个 Owner)。

动态任务分发机制(这是重点,四个关键部分):

  • 1. 任务队列 + 状态机 :任务有 todo/doing/done/blocked 状态;分发即「把 todo 变成 doing」,要 原子化领取 (用乐观锁 / SELECT ... FOR UPDATE SKIP LOCKED / Redis 原子操作), 防止两个 Agent 领同一个任务 。这是最容易出 bug 的地方。
  • 2. 能力匹配 :任务带所需能力标签(如 capability: web_search ),Agent 带自己的能力标签, 只有匹配的 Agent 才能领取 。能力标签就是权限与准入控制。
  • 3. 依赖与拓扑 :任务图(DAG)管理,前置未完成的任务不可领取;前置失败则下游任务转为 blocked 并上报。
  • 4. 动态插单 :运行中发现新的子任务(见第 100 题)→ 插入任务列表,重新计算可执行集合。 这是动态分发的价值所在 ——不需要重写整个计划。

动态 vs 静态分发的取舍:

  • • 静态(指挥式) :主 Agent 显式指定谁做什么。 优点 :可控、可预测、可审计。 缺点 :主 Agent 是瓶颈,负载不均,无法自适应。
  • • 动态(领取式) :Agent 按能力和负载自主领取。 优点 :负载均衡、容错好(一个 Agent 挂了任务被其他 Agent 领走)、扩展性好(加机器就加吞吐)。 缺点 :需要可靠的队列与并发控制,调试更复杂,全局规划能力弱。

实践建议:“分解阶段用静态(需要全局规划与依赖设计),执行阶段用动态(需要吞吐与容错)”——两者结合是最现实的方案。

13多 Agent 效率与评估

本节提炼
  • 效率分四维：墙钟时间、质量、成本、可靠性，多 Agent 成本几乎总上升
  • 独特价值只有上下文隔离、并行、权限合规隔离是结构性的，专业化可被同模型采样替代
  • 评估：同模型 A/B 加四指标，成本归一化，分难度分层，失败模式分析，人工盲评
  • 结论：装得进一个窗口的任务多 Agent 常是负收益，拆 2~5 个而不是几十个
  • A/B 不固定同模型，测的是模型差异而非架构差异
  • 忽略 token 成本：每个 Agent 都有系统提示与上下文，重复开销大

回答要诚实且量化——这题考的是批判性思维,一味道好会扣分。

先说结论:「能提升」是有条件的,而且「效率」要分维度看。

效率的四种定义(分开衡量):

维度多 Agent 的表现
墙钟时间有并行收益时可显著下降(子任务独立时接近 1/n);调度与通信开销会侵蚀收益
质量/准确率在「上下文装不下」「需要多视角」时有提升;在简单任务上通常下降(错误传播、协调偏差)
成本(token)几乎总是上升 (每个 Agent 都有自己的系统提示与上下文,重复开销大)——这是最容易被忽略的代价
可靠性双刃:容错更好(可重试、多路验证);但链路更长,复合成功率可能更低(0.95^10 ≈ 0.6)

多 Agent 的独特价值(单 Agent 原理上做不到的):

  • 1. 上下文隔离(唯一真正的「结构性」价值) :信息量超过任何单窗口的容量时,只有隔离能解决。 这是最强也最难反驳的论证。
  • 2. 并行(唯一真正的「时间」价值) :独立子任务的真并行,单 Agent 无法做到。
  • 3. 权限与合规隔离(硬需求) :不同数据域必须物理隔离,单 Agent 做不到。
  • 4. 专业化(有条件的价值) :同构问题、独立判断的集成(多路采样 + 投票)能提升准确率; 这一点也可以被「同一模型采样多次」部分替代 ,所以价值有限。

怎么证明(评估方法,这是核心答案):

  • 1. 严格 A/B / 消融实验(黄金标准) :
  • • 同一个评测集,同一底层模型, 单 Agent vs 多 Agent 对照 ;
  • • 同时测四个指标:任务成功率、延迟(P50/P95)、token 成本、失败模式分布。
  • • 必须同模型 ——否则测的是模型差异而不是架构差异(最常见的实验设计错误)。
  • 2. 成本归一化比较 :多 Agent 通常用更多 token, 必须做「成功率/成本」和「成功率/延迟」的归一化对比 ,否则结论会失真。 「多花 3 倍成本提升 5 个点」是不是值得,才是真问题。
  • 3. 分难度分层评测 :把任务按「单窗口能否装下」「是否需要并行」「是否多视角」分层, 证明多 Agent 的收益只出现在特定层 ——这比总体平均更有说服力。
  • 4. 失败模式分析(最有价值) :统计多 Agent 的失败有多少来自「协调失败/错误传播/通信丢失」,多少来自「任务本身难」。 如果大量失败源于协调,那多 Agent 就是负收益。
  • 5. 可控变量实验 :固定子 Agent 数量、固定并行度,分别测收益曲线; 防止「Agent 越多越好」的错觉 。
  • 6. 人工盲评 :对开放性任务(报告、方案)用人类盲评打分,弥补自动指标的不足。

我的判断(面试表态,要有观点):

多 Agent 的价值主要在「上下文隔离」和「并行」,而不是「更聪明」。 对于能装进一个窗口的任务,多 Agent 通常是负收益(更贵、更慢、更容易出错)。所以正确的姿势是:先穷尽单 Agent + 好工具 + 好上下文管理的可能性,只在遇到上下文墙或硬性隔离需求时才拆多 Agent;而且要拆得尽量少(2~5 个,而不是几十个),并且用可观测与评测持续证明它值得。

加分的一句:「多 Agent 是一个架构成本很高的方案,面试里我更想证明的是——我知道它什么时候不值得用,而不是它有多好。」

14计划外任务流转

本节提炼
  • 四问分类：是否在原目标范围内、是否有副作用/可逆、是否超授权预算、是否阻塞
  • 流转：结构化上报→父 Agent 裁决→入队更新 DAG→子 Agent 安全暂停
  • 范围蔓延、风险性动作、与决策冲突必须审批；范围内无副作用可自动追加
  • 护栏：限制次数与嵌套深度、共享总预算、批量上报、默认拒绝、留痕
  • 新任务无限制扩张：1 变 2 变 4，成本指数爆炸

这是「计划外任务」问题,是动态规划的核心难点。

第一步:判定新任务的性质(必须分类,否则无法决定流转方式):

类型例子处理方式
子目标(属于原目标范围)调研时发现需要查另一个资料自动追加 ,由父 Agent 分发
前置依赖(不解决就无法继续)发现需要先修复一个数据问题自动追加但阻塞当前任务,标记依赖
范围蔓延(超出原目标)子 Agent 顺手想做一个额外优化必须上报审批 ,默认不做
风险性动作(有副作用/需权限)需要重启服务、需要写库、需要付费 API必须审批(HITL)
与已定决策冲突新任务要求改接口,但约束是不能改必须上报 ,由父 Agent 重规划或拒绝

判定标准(四条,是这题的答案核心):

  • 1. 是否在原目标范围内? 在 → 可自动;不在 → 上报。
  • 2. 是否有副作用/是否可逆? 有副作用或不可逆 → 必须审批(不看范围)。
  • 3. 是否超出当前授权/预算? 超出 → 必须审批。
  • 4. 是否阻塞当前任务? 阻塞 → 优先处理并标记依赖;非阻塞 → 可入队后置。

第二步:流转机制(工程实现):

  • 1. 上报通道 :子 Agent 通过结构化消息上报「新任务请求」(NEW_TASK_REQUEST),包含:动机(为什么要做)、属于原目标的哪一部分、预期成本、是否有副作用、不做的后果。
  • • 「不做的后果」这一项很重要 ——它让父 Agent / 人能判断紧急性和必要性。
  • 2. 父 Agent 裁决 :
  • • 在范围内且无副作用 → 自动批准,插入任务列表(动态分发,见第 98 题);
  • • 需要重规划 → 触发局部重规划(只调整受影响的子图);
  • • 超范围 / 有风险 → 升级人工决策。
  • 3. 人工审批(HITL) :审批界面要展示:原始目标、新任务请求、动机、影响范围、成本。 审批人需要足够上下文才能做判断 ,不能只给一句话。
  • 4. 任务入队与依赖更新 :批准后写入共享任务列表, 更新 DAG ,重新计算可执行集合。 注意并发安全 (原子领取)。
  • 5. 状态回传 :子 Agent 提交请求后进入 NEEDS_INPUT / BLOCKED 状态, 必须能安全暂停 (见第 119 题:状态暂存 + 恢复),而不是空转等待。

第三步:防滥用的护栏(必须有):

  • 1. 次数限制 :单个子 Agent 提交的新任务请求有上限(如 ≤ 3 次),防止「无限扩张」。
  • 2. 深度限制 :新增任务的嵌套深度限制; 防止任务树无限生长 (1 个变 2 个变 4 个,成本指数爆炸)。
  • 3. 总预算约束 :所有新增任务共享父任务的总预算(见第 94 题:预算随任务下发), 预算耗尽即强制收敛 。
  • 4. 批量上报 :同一子 Agent 的多个请求合并上报,减少审批打扰。
  • 5. 默认拒绝 :超时未审批的新任务请求 默认拒绝 (或按保守策略处理),不能让任务无限期等待人工。
  • 6. 可审计 :所有新增任务(含自动批准的)全量留痕,便于事后复盘成本构成。

一句话总结:先按「是否在范围内 + 是否有副作用 + 是否超预算 + 是否阻塞」四问分类;范围内的自动追加,有副作用/超范围的走审批;实现上要有结构化上报、父 Agent 裁决、任务入队更新 DAG、子 Agent 安全暂停;护栏上必须限制次数与嵌套深度、共享总预算、默认拒绝、全程留痕。

多模块集成的七条设计原则:

  • 1. 统一抽象(最关键) :所有 Agent Runtime、工具、模型都通过 平台标准接口 接入(见第 31 题)。新模块接入 = 写一个适配器 + 能力声明,业务零改动。
  • 2. 注册中心化 :工具、MCP Server、Skill、Agent、模型 全部注册到统一注册中心 ,带元数据(能力、权限、SLA、版本、负责人)。平台从注册中心动态装配,而不是硬编码。
  • 3. 配置驱动而非代码驱动 :Agent 的模型、提示、工具集、权限、预算通过配置(配置中心/Nacos)管理,支持热更新、灰度、A/B、快速回滚—— 这是平台和「写死代码」的根本区别 。
  • 4. 编排与执行分离 :编排(图/状态机/任务流)描述「做什么」,执行引擎负责「怎么跑」(重试、超时、恢复)。编排产物可视化、可版本化。
  • 5. 横切关注点统一收口 :权限、审计、可观测、成本、限流 做在平台层而不是每个 Agent 里 。业务 Agent 不重复实现这些,这是平台价值的核心。
  • 6. 多租户与隔离 :租户级的资源隔离、配额、数据隔离、权限域。企业平台的必备能力。
  • 7. 可观测是一等公民 :统一的 trace/事件模型,跨 Runtime、跨 Agent、跨工具的全链路追踪 + 轨迹回放 + 指标体系。 没有这个,平台就无法治理。

集成方式(三类模块的接入手段):

  • • 模型 :统一网关(OpenAI 兼容协议 / 各家适配器),平台侧做路由、降级、限流、成本统计、缓存。
  • • 工具与数据 :MCP 为主(标准协议),平台做注册、权限过滤、审计、健康检查;非标工具用适配器包装成统一接口。
  • • Agent / 工作流 :通过统一 Runtime 契约(invoke/stream/cancel/resume + 统一事件模型)接入;外部平台(如各低代码平台)用 Adapter 桥接。

一个关键取舍(体现深度):平台要在「统一管控」和「不阻塞业务创新」之间平衡。做法是**「薄平台 + 插件化能力」**:平台只提供最必要的契约(接口、注册、观测、权限)和基础设施,具体能力(Skill、工具、领域 Agent)完全由业务侧以插件形式提供与迭代。平台越厚,业务越慢——这是很多内部平台失败的根源。

16核心组成与执行链路

本节提炼
  • 六大组成：模型层、规划决策层、工具能力层、记忆上下文层、编排运行时层、治理安全层
  • 执行链路 12 步：鉴权、路由、上下文装配、Plan、Agent Loop、HITL、落库、计费
  • 最易忽略的四环节：预算检查、工具结果处理、检查点、终止检查
  • 终止检查只设最大轮次，缺无进展检测和重复调用检测

核心技术组成(六大块):

  • 1. 模型层 :推理模型、Function Calling 能力、结构化输出、多模型路由与降级。
  • 2. 规划与决策层 :任务理解、任务分解(Plan)、工具选择、ReAct 循环、重规划。
  • 3. 工具与能力层 :工具定义(JSON Schema)、MCP 接入、执行器(超时/重试/幂等/熔断)、Skill 库。
  • 4. 记忆与上下文层 :短期记忆(会话态)、长期记忆(向量库 + 检索)、上下文装配与压缩、工作区卸载。
  • 5. 编排与运行时层 :Agent Loop 驱动、状态机/图编排、多 Agent 调度、检查点与恢复、HITL 中断。
  • 6. 治理与安全层 :权限与身份、沙箱、注入防护、审计、可观测(轨迹/指标/回放)、评测体系、成本控制。

执行链路(一次请求的完整生命周期,共 12 步):

  • 1. 接入与鉴权:认证、租户识别、配额检查
  • 2. 意图理解与路由:分类 + 选择 Agent 链路(规则优先,模型兜底)
  • 3. 上下文装配:
  • - 静态区:系统提示 + Rule + Skill 元数据 + 工具 schema(可缓存)
  • - 动态区:长期记忆召回 + RAG 检索 + 会话历史(压缩后)+ 当前输入
  • - 预算检查:token 计数,超限则卸载/压缩
  • 4. Plan(如需要):任务分解为子任务 DAG,校验计划合理性
  • 5. Agent Loop 每轮:
  • a. 模型推理(Thought)
  • b. 决策:输出最终答案 or 发起工具调用
  • c. 工具调用:
  • - 白名单校验 → schema 校验 → 权限校验 → 参数归一化
  • - 执行(超时/重试/幂等/熔断/隔离)
  • - 结果处理:大结果卸载 + 摘要 + 结构化错误
  • d. 记录检查点(状态 + 轨迹)
  • e. 终止检查:目标达成 / 达到最大轮次 / 预算耗尽 / 检测到死循环
  • 6. 中间态更新:任务状态区更新(目标/进度/待办/已确认事实)
  • 7. HITL(如触发):暂停 + 持久化 + 通知人工 → 审批后从检查点恢复
  • 8. 结果校验:格式校验 + 事实性校验(可选 Critic)
  • 9. 输出后处理:格式化、脱敏、引用来源、用户体验层加工
  • 10. 结果落库:轨迹、产物、指标
  • 11. 记忆写入(异步):提炼 → 去重 → 冲突消解 → 落库
  • 12. 可观测与计费:token/成本/延迟埋点,失败分类统计

这条链路上最容易被忽略但最关键的四个环节(加分):

  • 1. 第 3 步的预算检查 :不在这里卡住,后面全是坑。
  • 2. 第 5c 步的结果处理 :工具结果如何优雅进上下文,决定了上下文质量的走势。
  • 3. 第 5d 步的检查点 :没有检查点就没有恢复和回放能力,长任务无法生产化。
  • 4. 第 5e 步的终止检查 :除最大轮次外,必须有「无进展检测」和「重复调用检测」(见第 112 题)。
