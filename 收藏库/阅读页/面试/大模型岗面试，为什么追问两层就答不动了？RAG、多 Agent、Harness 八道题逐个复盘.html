引言

大家好，我是吴师兄。

面试官全程只围绕这两个项目往下追，没有出一道脱离简历的八股题。

结果很典型。

文档解析、混合检索、RRF 融合、Reranker、MRR 评测、Query 改写、Agent Harness、State 传递，这些技术点候选人都碰过，第一层都答得出来。每一个再往下追两层，就开始含糊。

面试官最后只给了一句总评：“你现在做的东西其实都比较浅，我看重的不是你现在有多少能力，而是你的成长性。”

这句话我读了两遍。候选人准备了“我做了什么”，没有准备“为什么这么做、什么情况下不成立、我怎么知道它有效”，这三问，恰好是面试官往下追的三个方向。

下面我把这场面试的八道题按原顺序重走一遍，每题标出答到了哪一层、丢在哪、补什么。

手里有 RAG 或 Agent 项目、准备秋招社招的朋友，可以拿自己的简历对着看。

AGENT FIELD NOTE 0101 / 11

八道题为什么都停在同一个地方？

先说结论。八道题的丢分，可以归到三个模式，后面每一段拆解都能对回其中一条。

模式一，追问一层就见底。表格解析、混合检索、RRF，第一层都答得出来，第二层的“为什么”就开始含糊。BM25 怎么算分、向量检索到底漏掉什么、Reranker 为什么不能全量跑，这三个是典型。

模式二，数字没有配套材料。简历上写了 MRR 从 0.72 提到 0.92，面试官连问三次才问到点上，评测集规模和划分方式完全没答。写在简历上的每一个数，都要备好归因表和消融表，否则这个数会变成负资产。

模式三，不肯放弃预设答案。场景题里面试官已经明确排除了解析这个方向，候选人还是绕回去。听到熟悉的关键词就启动准备好的回答，没有真的在听题。

▲ 面试官往下追的三个方向：为什么这么做、什么情况下不成立、怎么知道有效。

三个模式指向同一件事：技术点只备了一层。第一层是“我们做了什么”，第二层是“为什么这么做、什么情况下会不成立”。能把“我们选了 A”和“A 在什么情况下不如 B”一起说出来，可信度完全不同。

AGENT FIELD NOTE 0202 / 11

开场三分钟，项目该怎么说？

面试官的开场要求说得很细：业务目标是什么，整个链路怎么走，你自己负责哪个模块，上线后印象最深的成果是什么，团队共同完成的部分去掉。

候选人从“文档解析、切分、召回我都有参与”开始，直接进了技术细节。业务目标没说，成果没说，“我负责哪一块”用“都有参与”带过。

面试官问“印象最深的成果”，是想知道你能不能用业务语言描述价值，以及你有没有对结果负过责。一开口就进技术，把最有信息量的部分挤掉了。

开场用四句话打底就够。业务目标和用户是谁；链路一条线拉过去，解析、切分、索引、召回、重排、生成、引用溯源；自己负责哪几段，边界要清楚；成果带一个数和一个业务含义。说完主动挑一个技术点展开，把主动权拿回自己手上。

按这个项目，开场可以这样说：

给研究员做研报问答，替代人工在几千份 PDF 里翻数据，把单次查数从十几分钟压到一分钟内。解析和召回这两块是我从零到一做的，切分参与设计，生成部分是同事负责。

这段话比“都有参与”可信得多，也不会给后面的追问挖坑。你说“从零到一做的”，面试官就会往解析和召回追，而这两块正是你准备最充分的地方。

AGENT FIELD NOTE 0303 / 11

PDF 表格解析，这题为什么拿了满分？

第二题是整场唯一的满分项。面试官问：你说 PDF 表格解析有问题，具体是什么问题？对比了哪些框架，为什么最后选 MinerU？

候选人的回答有对比，PyMuPDF、DeepDoc、MinerU 三个都试过；有取舍理由，DeepDoc 基于 OCR，对中文友好，普通表格准确率高，但无边框表格不行；有工程折中，MinerU 慢，所以按文档类型路由，只把难啃的文档送给重模型，没有全量上。

还有一个加分动作。候选人主动说“印章水印的方案我们评估过，但收益比不划算所以没做”。主动交代“评估了但没做，因为不划算”，说明你做过成本判断。

这题能再深两层。一层是难在哪。无边框表格的难点本质是版面分析问题：有框线的表格可以靠线检测直接切单元格，无框线只能靠文字块的坐标做行列聚类，列对齐一旦判错，整张表的语义就错位。说到这一层，面试官才能确认你理解的是问题本身，换库只是顺带的结果。

另一层是怎么判定。路由的规则分类具体看什么信号？页面里有没有检测到足够长的水平、垂直线段，文字块坐标是否呈规则网格分布，页面是不是纯图像。把判定依据说出来，比“做了规则分类”具体得多。

AGENT FIELD NOTE 0404 / 11

模型上下文都几百 K 了，RAG 还有什么理由？

第三题是一道价值观题：现在大模型能力这么强，Wiki 或者文档为什么不能直接扔给模型？

候选人答的是“上下文有限，几十页研报放不进去”，加上 Citation 可以溯源。可上下文窗口一直在涨，拿“放不下”当理由，面试官下一句就可以说，现在都几百 K 了。

更站得住的理由至少有四条，量级各不相同。

成本和延迟。每次都塞全量，token 成本和首字延迟按文档量线性涨，检索把这笔成本摊到了离线索引阶段。

有效性随长度衰减。放得进去，未必用得好，长上下文里精确查找的准确率明显更低。

数据是动态的。文档每天增删改，检索层可以增量更新，长上下文每次都要重新组装。

权限。不同用户能看的文档范围不一样，检索层天然是做行级权限过滤的地方。

回答这类“为什么不用更简单方案”的问题，准备两三条量级不同的理由，别把宝押在一条上。可溯源这条候选人说到了，而且说得对，Citation 需要定位到具体 chunk 和原文位置，检索链路里天然带这个信息。

还可以主动补一句。RAG 和长上下文并非二选一，成熟做法是检索先把候选压到少量高相关片段，再交给长上下文模型做综合。检索管“找得准”，长上下文管“读得全”。能说出这层关系，比单纯论证“为什么不用长上下文”更显成熟。

AGENT FIELD NOTE 0505 / 11

向量检索比 Elasticsearch 差在哪？

第四题问得很直接：你觉得 RAG 里的向量搜索，相比 Elasticsearch 有什么优点和缺点？

候选人的回答是“当时也用了 ES，向量存在 Milvus，后面做了混合检索，效果比较好”。这是答非所问。面试官紧接着又问了一次“向量搜索容易漏掉什么”，才拿到“无法很好地通过关键词召回”这一句。

向量的长处在语义。同义改写、口语化提问、跨语言、概念相近但用词完全不同的内容，BM25 完全召不回来，向量可以。

向量的短板全在精确性，可以逐条报出来。

●罕见词与专有名词。公司简称、基金代码、产品型号、人名，embedding 的区分度很低。
●数字与编号。8.3 和 8.4 的向量距离，可能比 8.3 和“行业分析”还近。
●否定与限定。“不含 A 的 B”和“含 A 的 B”在向量表示上非常接近。
●不可解释。BM25 能告诉你哪个词命中、贡献多少分，向量只给一个相似度。
●更新成本。换 embedding 模型要全量重建索引。
●严格过滤。按时间、机构、权限做硬过滤，倒排天然支持，向量库过滤后召回质量会掉。

BM25 反过来，短板是纯字面匹配，用户换个说法就召不到。所以混合检索是必然的。面试里要说清楚的是“为什么必然”，“我们上了两路效果好”只交代了结果。

AGENT FIELD NOTE 0606 / 11

两路结果怎么融合，Reranker 为什么不能全量？

第五题面试官连问三层：两路检索是串行还是并行，两组结果怎么融合，为什么不直接加分数。后面又追了 Rerank 放在哪一步，文档量不大能不能全量 rerank。

候选人答了并行、RRF、分数尺度不一样需要归一化，还说“我们对比过，加权平均效果没有 RRF 好”。“对比过”这三个字是关键。面试官问“为什么不用加权平均”，最想听的就是你实际比过。

RRF 的计算很短，可以直接写出来。每一路只贡献排名，一个文档在某一路排第 r 位，就得到 1 除以 k 加 r 的分数，几路加起来得到融合分。

PYTHON

# 吴师兄学大模型：wushixiongai.comfrom collections import defaultdict defrrf(rankings, k=60):"""每一路是按相关度降序的文档 ID 列表。""" scores =defaultdict(float)for ranked in rankings:for rank, doc inenumerate(ranked,1): scores[doc]+=1.0/(k + rank) by_score =sorted(scores, key=scores.get)return by_score[::-1]

可以再补 RRF 的代价。RRF 只用排名，丢掉了分数的强度信息。如果某一路的第一名分数遥遥领先，RRF 感知不到这个差异，一律按名次算。所以在一路明显更可信的场景下，归一化加权反而更好。k 值也是可调项，k 越大越平滑、各路越均等，k 小则更看重头部。

Reranker 这一段，候选人位置说对了，理由说反了。候选人说“如果全部交给 Reranker，前面的召回阶段就没必要了”。结论对，但真正的原因是计算量。Reranker 通常是 cross-encoder，query 和每个 chunk 拼起来过一遍模型，是 N 次前向；召回阶段只是一次编码加近似最近邻查找。几十万个 chunk 全量过 cross-encoder，延迟上根本不可行。

▲ 两路并行召回，RRF 融合后取前 50 到 100 进 Reranker，最后前 3 到 5 进上下文。

标准配置是召回 top 50 到 100，rerank 之后取 top 3 到 5 进上下文。召回给多了 rerank 延迟涨，给少了 rerank 再准也捞不回漏掉的。召回阶段看 recall，rerank 阶段看精度，两个阶段的优化目标不一样。

AGENT FIELD NOTE 0707 / 11

简历上的 0.72 到 0.92，要配哪三份材料？

第六题问的是那个数字：这个 MRR 用了多少 query，结果怎么标注，测试集和调参集分不分开？它原来为什么低，你改了什么才提到 0.92？

前两次回答都在讲“业务部门人工加 LLM 标注、每周持续标注”。第三次面试官直接说：我问的不是 MRR 怎么算出来的，是它原来为什么低、你改了什么才提上去。

写在简历上的每一个数，都要配三份材料。

评测集本身。多少条 query，怎么来的，线上真实 query 采样还是业务同学构造，标注规则是什么，一致性怎么保证，调参集和测试集怎么分。测试集和调参集不分离，0.92 这个数就没有意义。面试官问这个，是在验这个数可不可信。

归因。0.72 的时候，错的那 28% 是怎么分布的？把 bad case 分桶：解析错的多少，切分把答案切断的多少，召回压根没进 top10 的多少，进了但排序靠后的多少。有这张分桶表，你才能解释为什么优先做表格解析，没有先换 embedding。

消融。每一项改动贡献了多少，哪怕粗略也行。有这张表，面试官问“最关键的改动是什么”，一句话就能答，还顺带证明了你是按数据决策的。没有这张表，简历上的提升就只是一个数字。

配不齐的数字，不如不写。

AGENT FIELD NOTE 0808 / 11

8.3 条查不到，为什么不该回到解析？

第七题是场景题。用户要查某基金 2024 年报告第 8.3 条里的数值，向量搜索只返回了行业分析。假设原文肯定存在、用户只是不记得章节，你怎么分析和改进？

题面已经锁死了前提：原文肯定存在，用户是专业人员，知道内容在那儿，只是不记得章节，现在的问题是检索没搜到。候选人两次都回到“先看文档有没有被准确解析”。场景题里对方主动排除的方向，硬要回去只会浪费时间。

正确的入手方式是拆 query 里的信号。

▲ 一条 query 拆成四类信号：专有名词精确匹配、年份走 metadata、章节编号走字面、数值才是语义部分。

基金名称是专有名词，要精确匹配，还要处理简称与全称的映射。2024 年是结构化属性，走 metadata 过滤，不该参与语义相似度计算。8.3 是章节编号，向量空间里基本没有区分度，必须靠字面匹配或结构化字段。“具体数值”才是真正的语义部分。

为什么会返回行业分析？整条 query 编码成一个向量之后，最强的语义信号是“基金”“报告”“数值”这些通用词，行业分析段落在这些维度上相似度很高，而 8.3 这个真正的定位信息在向量里几乎被抹平了。

改进方向顺着信号来。索引阶段把结构信息存成 metadata，文档 ID、年份、机构、章节路径都进去。query 阶段抽实体和结构，转成过滤条件，剩下的语义部分才送去向量检索。chunk 里保留标题路径。检索用小 chunk，送模型时带上父块。BM25 一路兜底，前提是分词别把 8.3 切碎。

遇到追问先停两秒，确认对方锁死了哪些前提，再开口。听到熟悉的关键词就启动准备好的答案，是这场面试里代价最大的习惯。

AGENT FIELD NOTE 0909 / 11

不用 LangGraph，Harness 到底要管什么？

第八题问得最深。面试官问：不用 LangGraph、改用原生 SDK，除了模型本身，Harness 要负责什么？多轮改代码、测试一直失败、反馈给模型还是改错，怎么组织上下文、怎么防死循环？

候选人只答到了超时、最大重试次数和 Checkpoint。

Harness 要管的事可以逐条报出来。

●循环控制：什么时候进下一轮，什么时候停。
●上下文组装：每一轮给模型看什么。
●工具注册与调度。
●状态管理与检查点。
●错误处理与升级路径。
●预算控制：token、时间、次数、金额。
●观测：每步输入输出落盘，能事后归因。

反复改错的场景，核心在上下文组装。失败信息不能原样堆叠。十轮下来上下文里堆了十份 stacktrace，模型会被淹没，而且会在相似的错误之间来回横跳。正确做法是维护一份压缩的失败摘要：试过哪些方案，每个方案的错误类型，已经排除了什么可能。历史尝试保留结论，不保留原始过程。

怎么检测“无进展”？判定信号很具体。连续两轮生成的 diff 相同或高度相似，报错的错误码和位置完全一样，修改的文件和行号在打转。命中就说明模型陷在局部，继续同样的循环没有意义。

升级有阶梯。先让模型显式反思为什么前几次都失败，把失败摘要作为输入，要求先归因再给方案。还不行就缩小范围，一次只改一个地方。再不行就回滚到最后一个测试通过的状态换条路。最后停下来交给人，并把已经排除的方案一起交出去。最大重试次数只是兜底，它只解决“不会无限烧钱”，不解决“怎么把任务做成”。

AGENT FIELD NOTE 1010 / 11

“State 其实就是文本”，被连抓三次抓的是什么？

同一道题的后半段，问串行 Agent 之间输出怎么传，候选人答“用 State”。追问 State 怎么保存，答“State 其实就是文本”。面试官立刻抓住：文本是不结构化的，下一个模型读错怎么办？改口说用 Schema 之后，又追一层：如果模型少输出一个括号，或者结构有误但不报错、继续跑然后逐渐跑偏，怎么办？

一次到位的答法分三段。State 用 schema 定义，Pydantic 之类，定死字段、类型、枚举、必填。生成侧优先用原生结构化输出或约束解码，从源头让非法 JSON 出不来，别事后补括号。校验放在写入 State 的那一刻，不合法直接拒绝，绝不让脏数据流到下游。

“不报错但跑偏”考的是语义错误。JSON 完全合法、字段类型也对，但内容是错的。这靠 schema 挡不住，要靠下游节点的前置断言：执行前先检查输入满足前置条件，比如表格必须有 date 和 amount 两列，引用的文件 handle 必须存在，不满足就抛结构化错误往回传。另外，大段内容别直接放进 State，存成 artifact，State 里只放引用和摘要。

裁判问题的原则是减少需要“相信模型”的地方。能用规则验的就别用模型判：代码能不能编译，单测过不过，JSON 合不合 schema，引用的原文在不在源文档里。Citation 校验是这类项目里最值钱的一条，完全不依赖第二个模型。规则表达不了的，才交给评判模型，而且要先跟人工标注对齐过一致率。

AGENT FIELD NOTE 1111 / 11

反问和薪资，也别裸奔

技术题之外还有两段。反问环节问了公司做什么、自己负责哪部分，中规中矩没问题。

薪资这段答得被动。面试官说可以根据能力定，候选人沉默很久后答“在区间内取平均值”，等于把定价权交了出去。稳的处理是给一个有依据的区间，依据可以是当前包、其他 offer、岗位市场价，再补一句数字之外你更在意什么。

回到面试官那句总评。它说得挺准：每道题头一层都答得出，再往下追就开始含糊。这类具体到细节的反馈，比一封拒信有用得多，因为它把该补的地方一个个点了出来。

拿自己的简历对一遍。每个技术点往下备两层，每个数字配齐评测集、归因表和消融表，场景题先停两秒确认前提。三件事都做到，面试官再往下追，你也接得住。

做过和搞懂之间的差距，在追问里藏不住。

这篇拆的是面试怎么答。要把混合检索、Reranker、Harness 和 State 校验真正写进自己的项目，训练营的 Agent 后端项目会把它们做成可验收的代码，配套项目练习与验收要求。适合有编程基础、想拿大模型岗 offer 的朋友，安排见2026吴师兄大模型/Agent 1v1求职陪跑营。
