02三层工程区别

本节提炼
  • 三代演进：Prompt 管指令、Context 管 token、Harness 管运行时
  • 模型超阈值后，上下文与 harness 收益远大于 prompt 调优
  • 生产看几百次调用的复合成功率

三代演进关系,一层比一层外延:

层次管什么核心问题典型动作
Prompt Engineering单次调用的指令文本怎么把话说明白Few-shot、CoT、角色设定、格式约束
Context Engineering进模型的全部 token怎么在有限窗口里放最有用的信息检索、筛选、压缩、排序、分隔、卸载、缓存
Harness Engineering模型之外的整套运行时怎么让不可靠的模型产出可靠的系统循环控制、工具治理、状态与沙箱、权限、可观测、评测、恢复

一句话区分:Prompt 是「说什么」,Context 是「给它看什么」,Harness 是「让它怎么干、干错了怎么办」。

关键洞察:当模型能力超过某个阈值后,上下文和 harness 的收益远大于 prompt 调优。因为 prompt 调的是「一次调用」,而 harness 调的是「几百次调用的复合分布」——复合成功率才是生产系统真正的指标。

03Agent Engineering vs Harness

本节提炼
  • Agent Engineering 是方法论全流程，Harness 是运行时设施
  • Harness 是 Agent Engineering 最重最硬的工程产出
  • • Agent Engineering(智能体工程) :偏 方法论与全流程 ,指把 Agent 从需求做成产品的工程实践:任务建模、架构选型(单/多 Agent)、工具设计、记忆与上下文策略、评测体系、上线运维。是「怎么造一个好 Agent」。
  • • Harness(马具/挽具,喻「套住模型的笼子」) :偏 运行时的具体设施 ,指模型外面那层壳:循环驱动、工具执行器、上下文装配、状态持久化、沙箱、权限、中断恢复、可观测钩子。是「Agent 跑起来的那个容器」。

关系:Harness 是 Agent Engineering 里最重、最硬的一块工程产出。用一个比喻——模型是匹马,harness 是马具+缰绳+车厢;Agent Engineering 是你设计整条运输业务。

04harness 为何火

本节提炼
  • 三个原因：重心转移、Chain 变工具循环、横切关注点变多
  • LangChain 管怎么拼，Harness 管怎么管住

先承认:LangChain 确实在做 harness 的一部分——工具调用、链式编排、记忆抽象,这些都在做。

但概念现在才火,有三个真实原因:

  • 1. 模型变强了,编排的重心转移了。 模型弱的时候,价值在「怎么拼 prompt、怎么串 Chain」,所以框架以 Chain/Agent 抽象为中心;模型强了之后,模型自己会规划、会调工具, 框架该管的从「编排逻辑」变成了「运行时可靠性」 ——循环、预算、沙箱、恢复、权限,这些 LangChain 早期没当核心。
  • 2. 范式从「Chain」变成「工具循环」。 现在是「一个模型 + 一堆工具 + 一个循环跑很久」,不再是「一串预设节点」。长时运行的 Loop 带来了 Chain 抽象里不存在的问题:上下文膨胀、死循环、跨会话状态、进程重启恢复。
  • 3. 横切关注点变多了。 权限、审计、沙箱、成本、可观测,这些是 基础设施关注点 ,不属于「编排框架」的范畴。让业务代码里塞满这些,框架帮不上忙,于是需要一层专门的 Harness。

区别(和 LangChain 式框架的核心差异):

LangChain 式框架Harness
定位编排与抽象(怎么做流程)运行时与治理(怎么跑得稳)
状态主要在内存链上显式持久化,可快照可恢复
关注组件复用、链路拼装循环控制、预算、隔离、审计、降级
与模型关系强绑定抽象层尽量不侵入,薄适配

本质:LangChain 是「怎么把 LLM 拼起来」,Harness 是「怎么把 LLM 管住」。前者是开发期问题,后者是生产期问题。

05新范式与论文

本节提炼
  • Harness 内核：解耦、可恢复、薄抽象
  • Hermes 强调自我描述、自我修正与消息契约
  • 论文按推理/技能/工具/记忆/评测五条线索回答
  • Hermes 是产品，Harness 是支撑它的基础设施
  • 不要背论文标题，讲清解决了什么问题

回答思路:先讲范式内核,再讲论文线索,最后给判断。不要背论文标题,讲清「它解决了什么」更重要。

Harness 范式的内核:

  • • 把「模型」和「运行时」解耦:模型只负责一次决策,harness 负责循环、状态、工具、隔离、恢复。
  • • 强调 可恢复性 :每一步都是检查点,进程挂了能从中间续上。
  • • 强调 薄抽象 :不藏 prompt、不藏工具调用,便于调试与替换模型。
  • • 代表实践:Claude Code、各类 coding agent 的运行时。

Hermes 类范式的内核(自省/通信方向):

  • • 强调 Agent 自我描述与自我修正 :用结构化的自我反思和对外通信协议,让多个 Agent 之间传递「意图 + 状态 + 置信度」,而不是裸文本。
  • • 强调 消息契约 :Agent 间通信有 schema,可校验、可回放,降低「Markdown 传任务」的漂移问题。

论文线索方向(选自己真读过的讲):

  • • ReAct、Reflexion、Tree of Thoughts、Self-Refine —— 单 Agent 推理与自我改进的奠基工作。
  • • Voyager —— 技能库持续增长的开放式 Agent。
  • • Toolformer / ToolLLM —— 工具学习。
  • • Generative Agents —— 记忆、反思、规划的经典三件套。
  • • SWE-bench / AgentBench / τ-bench —— 评测范式(τ-bench 特别强调「同一任务多次采样」的 pass^k 指标)。
  • • Anthropic 的 Building effective agents 与上下文工程相关工程博客 —— 工程侧的权威表述。

收尾判断(面试加分):这些范式共同指向一个结论——模型越强,harness 越像「操作系统」而非「胶水」。价值会从 prompt 层上移到运行时层。

Hermes和Harness理解

Hermes：一个会“自我进化”的 AI 员工

Hermes 是由 Nous Research 团队在 2026 年 2 月推出的开源自主 AI 智能体，国内开发者常昵称它为“爱马仕”或“马”。

它和之前的同类产品（如 OpenClaw）最大的区别在于，它试图让 AI 拥有“自主进化”的能力，像一个会积累经验的员工，而不仅仅是一个需要你反复输入指令的高级工具。它的核心特点包括：

自动生成与优化技能：当 Hermes 完成一个复杂任务后，它会自动总结步骤，生成一个可复用的“技能”文件。下次遇到类似问题，它能直接调用，甚至在使用中自己改进这个技能，不需要人工编写。

选择性长期记忆：它会主动整理对话，提炼出你的偏好、工作模式等关键信息存入长期记忆，而不是把所有聊天记录都塞进去。这能让它越用越懂你，同时避免记忆膨胀导致的效率下降。

定位：可以把它理解为一个装在你自己电脑或服务器上、能通过微信等工具随时召唤的“数字员工”，适合处理深度分析和跨场景的复杂任务。

Harness：驾驭 AI 的“缰绳”与“操作系统”

Harness 的本意是“马具、缰绳”。在 2026 年的 AI 行业讨论中，它被赋予了特殊的含义：它指的不是某一个具体软件，而是围绕大模型构建的一整套让它能稳定、可靠、安全运行的工程系统。

行业里流传着一个公式：Agent = Model + Harness。如果说大模型（Model）是一匹动力强劲但桀骜不驯的“千里马”，那么 Harness 就是马具、缰绳、马车底盘的总和，负责把模型的能力转化为可靠的生产力。

一个完整的 Harness 通常包含这些看不见的工程细节：

上下文与记忆管理：如何高效利用有限的“脑容量”（上下文窗口），记住该记的，忘掉该忘的。

工具调用与执行循环：如何规划任务、调用外部工具、在出错时重试。

安全与权限控制：确保 AI 不会执行危险操作，符合企业规范。

评估与验证：判断任务是否真的完成，而不是 AI 自己“觉得”完成了。

这个概念之所以在 2026 年变得火热，是因为行业发现：决定一个 AI Agent 好不好用，模型本身的能力只是一部分，外面这圈“工程护栏”和“执行系统”才是落地的关键。许多头部公司（如 DeepSeek）也开始将自己的 Harness 框架开源，使其成为类似“操作系统底盘”的公共设施。

两者的关联

简单来说，Hermes 是一个产品，而 Harness 是支撑这类产品的技术理念或基础设施。Hermes 之所以显得“更聪明”，正是因为它内置了一套更先进的 Harness 设计（比如它的可写运行时和技能蒸馏机制），来管理记忆、调度技能。你可以把 Hermes 看作一个在“自我进化”这个特定方向上，把 Harness 做得很有特色的具体实践。

06主流框架盘点

本节提炼
  • Python 九大框架，LangGraph 是多 Agent 主流
  • TS/JVM 各有对应，Claude Code 是 harness 标杆
  • 选型三句话：显式状态机、企业治理、读代码学内核

按语言和定位分:

Python:

  • • LangGraph :图结构状态机,显式状态与检查点、支持 interrupt/恢复、多 Agent 编排能力强,是目前生产级多 Agent 的主流选择之一。
  • • LangChain :组件库,生态最大。
  • • LlamaIndex :偏 RAG 与数据编排,Agent 能力较薄。
  • • AutoGen / AG2 :多 Agent 对话协作,GroupChat、辩论范式。
  • • CrewAI :角色化多 Agent,上手快、抽象轻。
  • • OpenAI Agents SDK (原 Swarm 演进):轻量、Handoff 机制清晰,适合读代码学 harness 内核。
  • • Pydantic AI :强类型,输出的结构与校验做得好。
  • • Smolagents :极简,主打 code-as-action(让模型写代码当动作)。
  • • Google ADK :Google 官方 Agent 开发套件,A2A 协议生态。

TypeScript: Mastra、VoltAgent、LangChain.js、Vercel AI SDK(后者偏前后端一体的流式应用)。

JVM: Spring AI / Spring AI Alibaba(企业 Java 栈首选)、LangChain4j(轻量,含 LangGraph4j 图编排)。

自研 / 产品级 harness(值得借鉴设计):

  • • Claude Code —— 上下文管理、Skills、Subagent、权限模型,是当代 harness 的标杆样本。
  • • OpenHands / SWE-agent —— 开源 coding agent,沙箱与轨迹回放值得看。

我会怎么看选型:要显式状态机与恢复 → LangGraph / LangGraph4j;要企业 Java 治理 → Spring AI Alibaba;要读代码学内核 → Agents SDK / Smolagents。

07Claude Code 上下文管理

本节提炼
  • 五层机制：缓存、卸载、压缩、隔离、长期记忆
  • 卸载优先于压缩，前缀稳定换缓存，隔离优于共享
  • 压缩保留目标、事实、待办三类结构化信息

讲五层机制,这是最实际的答案:

  • 1. 系统提示分层 + Prompt Caching :稳定不变的部分(工具定义、系统规则、项目 CLAUDE.md)放前面并缓存,动态部分放后面。缓存命中能大幅降本降延迟,这也是「为什么前缀要稳定」的工程原因。
  • 2. 工具结果的卸载(offload) :大输出(长文件、大 JSON、长日志)不直接塞进上下文,落到磁盘,上下文里只留摘要或引用,需要时再读。这是控制上下文的 第一道闸 ,比压缩更有效。
  • 3. 自动压缩(auto-compact) :接近窗口阈值时对历史做摘要压缩,保留最近若干轮原文 + 前面摘要。压缩时保留的结构化信息一般是:当前任务目标、已确认事实/决策、未完成的待办、关键文件路径。
  • 4. 子 Agent 上下文隔离 :Subagent 有独立上下文窗口,只把「结论」返回主线程,不把搜索过程中读过的几十个文件内容带回来。这是「上下文不被污染」的关键设计。
  • 5. 结构化长期记忆 :CLAUDE.md / memory 文件做跨会话事实沉淀,按需召回,不常驻上下文。

我认可的设计思想:①能不进上下文就不进(卸载优先于压缩);②前缀稳定换缓存;③隔离优于共享(子任务上下文别污染主线);④压缩要保留「目标 + 事实 + 待办」三类结构性信息,而不是无脑摘要。

08LangGraph vs Deep Agents

本节提炼
  • LangGraph 胜在显式状态机、可恢复、HITL、生态
  • Deep Agents 不稳：黑盒多、隐式压缩、迭代快、错误不透明
  • 节点副作用不幂等、隐式压缩漂移、错误被吞

选 LangGraph 的理由:

  • 1. 显式状态机 :状态、转移、检查点都在代码里看得见,生产上可测可审,出问题能定位到节点。
  • 2. 可恢复性 :checkpointer 支持中断续跑、时间旅行回放,长任务必备。
  • 3. HITL 原生支持 :interrupt / resume,审批类场景友好。
  • 4. 生态与成熟度 :文档、案例、社区问题解决率高,踩坑成本低。
  • 5. 不被单家模型/产品绑定 :换模型、换工具成本低。

Deep Agents 类框架不稳定的可能原因(讲机制,不针对具体产品):

  • 1. 抽象过厚,黑盒多 :内置的子 Agent、文件系统、规划器都由框架托管,行为难预测,出问题只能猜。
  • 2. 隐式压缩/摘要 :上下文被框架悄悄改写,导致行为漂移,且不可观测。
  • 3. 迭代太快 :API 语义频繁变动,升级即回归。
  • 4. 默认策略激进 :默认很长的最大轮次、默认启用自动重规划,在边界场景放大不确定性。
  • 5. 错误处理不透明 :工具失败、模型格式错误时框架内部吞掉异常,业务层拿不到真实原因。
  • 6. 提示词强耦合 :框架内置 prompt 针对特定模型调优,换模型效果陡降。

核心判断标准:生产选框架,看它的状态是否显式、失败是否可解释、能不能恢复,而不是看 demo 有多惊艳。

09Runtime 统一适配

本节提炼
  • 收敛到一层抽象，差异下沉到适配器
  • 统一接口/网关/注册中心/状态/可观测/能力路由七项
  • 验收：新增 Runtime 只写 Adapter，业务零改动

核心思路:收敛到一层抽象,把差异下沉到适配器。

  • 1. 统一接口层 :定义 Runtime 契约——invoke / stream / cancel / resume、统一事件模型(thought / tool_call / tool_result / final)、状态与检查点接口。所有 Runtime 都实现这套契约。
  • 2. 适配器模式 :每个 Runtime 一个 Adapter,负责协议翻译(事件映射、错误码归一、状态格式转换),业务侧只见统一 API。
  • 3. 统一模型网关 :Runtime 差异最大的往往是模型调用,抽到网关(路由、限流、成本、缓存、降级),Runtime 只当客户端。
  • 4. 统一工具与 MCP 注册中心 :工具 / Skill / MCP Server 集中注册、版本化、灰度、权限挂载,任何 Runtime 都从注册中心取。
  • 5. 统一状态存储 :会话、轨迹、检查点用统一 schema 落同一套存储,才能跨 Runtime 迁移和回放。
  • 6. 统一可观测 :事件标准化的价值就在这——不同 Runtime 的轨迹能进同一个链路追踪与评测平台。
  • 7. 能力矩阵 + 路由 :维护「哪个 Runtime 擅长什么」,按任务类型/成本/合规动态路由;新 Runtime 先跑影子流量对比。

验收标准:新增一个 Runtime 只需写一个 Adapter + 一套能力声明,业务代码零改动。

10Super 还是 Host+Sub

本节提炼
  • 长期是强 Host 加窄 Sub 加工具生态的混合形态
  • Sub 本质是上下文隔离，权限合规必须分域
  • 终局哑铃型，半专业 Agent 层消失

我的判断:长期是「一个强 Host + 大量窄 Sub + 工具生态」的混合形态,而不是单一通吃。

理由:

  • 1. 上下文是硬约束。 任何单一 Agent 的窗口都有限,而专业任务(写代码、做财务、跑运维)需要的领域上下文互相冲突且体量巨大。Sub Agent 的本质是 上下文隔离 ,这是物理必要,不是架构偏好。
  • 2. 专业化的收益来自「工具 + 提示 + 记忆」的组合 ,不只是模型智力。窄 Agent 能针对领域做深度优化(专用工具集、专用 Skill、专用评测集),通吃型做不到那么深。
  • 3. 权限与合规必须分域。 财务 Agent 和运维 Agent 的权限必须切分,合并成超级 Agent 就等于把所有权限堆在一个进程里,事故面爆炸。
  • 4. 可运维性 :窄 Agent 能单独评测、单独灰度、单独回滚;Super Agent 只能整体发布。

但要看到合流趋势:Host 本身会越来越强(模型能力 + 长上下文 + 记忆),很多原来需要 Sub Agent 的场景会被 Host 直接吃掉(简单检索、简单改写)。最终是哑铃型:一端越来越强的 Host,一端越来越专的 Sub Agent 与工具生态,中间那些「半专业」的 Agent 层会消失。

11LangGraph 状态快照

本节提炼
  • LangChain 解决怎么拼，LangGraph 解决怎么跑与恢复
  • 快照粒度是 super-step，thread_id 串版本链
  • 恢复从 checkpoint 的 next 节点续跑，不重放历史
  • 恢复重跑 next 节点，节点副作用必须幂等

LangChain vs LangGraph:

LangChainLangGraph
抽象Chain / Runnable 线性组合图 :节点 + 边 + 共享状态
控制流以链式为主,循环靠 AgentExecutor显式循环、条件边、并行分支
状态主要在内存中随链传递显式 State + 检查点持久化
恢复/中断弱强 :interrupt、resume、time travel
多 Agent需上层封装原生 Supervisor、Handoff、子图
定位组件库与抽象层有状态编排运行时

一句话:LangChain 解决「怎么拼」,LangGraph 解决「怎么跑、跑挂了怎么办」。 官方现在的方向也是把复杂 Agent 都引导到 LangGraph。

状态快照(checkpointer)实现思路:

  • 1. Shared State :每个图有一个 TypedDict 风格的状态对象,节点函数接收状态、返回「增量更新」。更新语义由 reducer 决定——默认覆盖,也可定义为追加(如消息列表用 operator.add )。这是「多个节点并发写同一字段如何合并」的关键。
  • 2. Super-step 与 checkpoint :执行按 super-step 推进(一批可并行的节点算一个超级步), 每个 super-step 结束后把完整状态序列化,写成一条 checkpoint 。所以快照粒度是「步」,不是节点内部。
  • 3. 线程与版本链 :用 thread_id 标识一条会话线;每个 checkpoint 有唯一 id 与父子指针(记录「下一步待执行的节点」),串成可回溯的版本链。同一线程保留多份历史 → 这就是 time travel 的基础。
  • 4. 存储后端 :MemorySaver(内存,调试)、SqliteSaver、PostgresSaver(生产)。存的是序列化状态 + 元数据(待执行节点、各 channel 的版本号)。
  • 5. 中断与恢复 :节点内 interrupt() 抛中断信号,此时状态已落盘,进程可退出;之后用 Command(resume=...) 继续同一 thread,引擎从 最后一个 checkpoint 记录的 next 节点 接着执行。因为状态是完整快照,恢复 不需要重放历史 。
  • 6. 并发与合并 :同一 super-step 内多节点写同一 channel 时按 reducer 合并;检测到版本冲突则重新调度。channel 版本号支持增量更新,避免全量写。
  • 7. 幂等性要求 :恢复是从 checkpoint 重跑 next 节点,所以 节点内的副作用必须幂等 ,或加「已执行标记」跳过——这是生产最容易踩的坑。

12Java 选 Spring AI

本节提炼
  • 与 Spring 生态原生融合，接入成本几乎为零
  • 统一抽象切换模型只改配置，治理能力齐备
  • Spring AI Alibaba 补齐 Graph 编排与国内适配

选 Spring AI 的核心理由:

  • 1. 与 Spring 生态原生融合 :自动配置、依赖注入、Actuator 度量、配置中心、事务、AOP——企业 Java 系统这些设施都是现成的,接入成本几乎为零。
  • 2. 可移植性抽象 : ChatClient / ChatModel / EmbeddingModel / VectorStore 一套统一抽象,切换模型供应商只改配置,不动业务代码。
  • 3. 企业级治理能力 :重试、超时、限流、可观测(Observation / Micrometer)、结构化输出转换。这些是生产必需,Spring 体系天然有位置挂。
  • 4. 团队与运维成本 :Java 团队不用引入 Python 服务,不用维护双语言技术栈和跨进程调用;发布、监控、安全流程完全复用。
  • 5. Spring AI Alibaba 补齐了 Agent 侧 :Graph 编排、Nacos 配置、通义/百炼适配、Function Calling 与 MCP 支持,国内落地顺畅。

LangChain4j 的优点(要客观说):轻量、迭代快、AI Service 声明式接口写起来很爽、社区活跃。

选型结论:本来就是 Spring 技术栈 + 企业治理要求高 → Spring AI(代价是抽象更重、文档偏少、迭代保守);小工具、独立服务、快速验证 → LangChain4j 也合适。

面试加分:明确说「框架选择的核心不是功能多少,而是它能不能复用你现有的治理能力(配置、监控、发布、安全)」,这体现企业视角。

14执行链与降级

本节提炼
  • 执行链分层：校验、路由、装配、Loop、汇总、观测
  • 降级按能力层级设计，七类失败各有三级兜底
  • 幂等优先、预算全局化、降级可观测、兜底诚实
  • 不幂等操作禁止自动重试，只允许重试查询类

执行链分层设计:

  • 请求 → 入口校验/鉴权 → 意图路由 → 上下文装配 → Agent Loop
  • ├─ 模型调用(网关:重试/换模型/降级)
  • ├─ 工具执行(超时/重试/幂等/熔断)
  • └─ 校验(输出结构 + 事实性)
  • → 结果汇总 → 输出后处理 → 落库/观测

降级要按「能力层级」设计,而不是只有一个 catch:

失败点一级降级二级降级兜底
主模型超时/不可用换同级备用模型换小模型 + 简化 Prompt模板答案 / 排队重试
工具失败指数退避重试(仅幂等)换备选工具或数据源标记该步不可用,继续或终止
单工具连续失败熔断该工具并从候选摘除用缓存/历史结果替代上报人工
输出 JSON 崩坏带错误信息让模型修复重试一次宽松解析 / 字段补默认值结构化模板兜底
上下文超限压缩重跑卸载大结果重跑截断并明确告知丢失范围
多步任务中途失败从最近检查点续跑局部重规划(只重做失败子任务)交付部分成果 + 人工接管
循环不收敛强制终止 + 强制总结降级为固定 Workflow转人工

关键原则:

  • 1. 幂等优先 :不幂等的操作禁止自动重试,只允许重试查询类。
  • 2. 预算全局化 :一次请求的总 token / 总时长 / 总工具调用数要有硬上限,而不是各环节各自限制。
  • 3. 降级也要可观测 :降级事件必须打点,否则你以为成功率 95%,其实 30% 是降级答案。
  • 4. 兜底必须诚实 :降到人工或模板时明确告知用户「这是简化结果」,不要伪装成正常结果。
