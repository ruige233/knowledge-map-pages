四、记忆管理与上下文工程(第 68 ~ 86 题)

01短长期记忆实现与区分

本节提炼
  • 区分标准是生命周期+作用域+存储位置，不是'存哪'的区别
  • 短期=全量进窗口靠压缩管理；长期=先筛再放靠检索管理
  • 长期记忆写用异步提炼四类条目，读按任务检索并标注来源时间
  • 治理要点：冲突消解、TTL、置信度、人工可编辑，防错误记忆固化
  • 把长短期误当成'存哪'的区别

区分标准:生命周期 + 作用域 + 存储位置。

短期记忆长期记忆
生命周期单次会话 / 单次任务跨会话、长期
内容当前对话历史、工具观察、当前计划、临时状态用户画像、偏好、事实知识、经验教训、历史结论
实现上下文窗口(消息列表) + 会话级缓存(Redis)外部存储 :向量库 + 关系库 + KV
容量受窗口限制,必须压缩可以无限增长,必须索引与遗忘
读写频率每轮都读都写按需检索、异步写入
失效会话结束即失效(可落库回放)有 TTL / 置信度 / 淘汰机制

短期记忆实现:

  • 1. 消息列表 + 窗口策略 :保留最近 N 轮原文,更早的压缩或摘要。
  • 2. 任务状态区 :单独维护「目标、计划、已完成步骤、待办、关键事实」的结构化区,比纯对话历史更可靠(不受压缩影响)。
  • 3. 会话缓存 :Redis 存会话态,支持水平扩缩容。

长期记忆实现:

  • 1. 写 :任务结束后(或每轮之后) 异步提炼 ,不是原始对话全存。提炼出「用户偏好 / 事实 / 结论 / 经验」四类,带元数据(来源、时间、置信度、作用域)。
  • 2. 存 : 向量库 (语义检索,存 embedding)+ 关系库/KV (结构化字段、精确过滤)。通常两者配合:先用结构化条件过滤(用户 id、时间、类型),再做向量召回。
  • 3. 读 :每轮开始按当前任务做检索召回,去重、排序、限数量后注入上下文,并 标注来源与时间 (防止过期信息被当成事实)。
  • 4. 治理 :冲突消解(新信息覆盖旧的)、TTL/衰减、置信度、人工可编辑—— 长期记忆最怕的是错误记忆被永久固化 。

关键认识:长短期不是「存哪」的区别,而是「谁负责挑选」的区别。短期是「全都放进去,靠压缩管理」,长期是「先筛再放,靠检索管理」。长上下文能力提升不会消灭长期记忆——因为筛选的成本、隐私边界、跨会话一致性这些问题是窗口大小解决不了的。

02记忆架构与数据库选型

本节提炼
  • 四层架构：写入、存储、检索、治理
  • 选库按需求分层：Redis 会话态、PG/MySQL 结构化、pgvector/Milvus 语义、对象存储轨迹
  • 六个选型维度：检索模式、规模、延迟、一致性、运维成本、合规删除
  • 推荐组合：Redis+PostgreSQL/MySQL+pgvector/Milvus+对象存储
  • 试图选一个'万金油'数据库

整体架构(四层):

  • 写入层:对话流 → 提炼器(LLM 抽取用户偏好/事实/结论) → 去重 → 冲突消解 → 落库
  • 存储层:向量库(语义) + 关系库(结构化/权限/时间) + KV(热数据/画像) + 文件/对象存储(附件与原始轨迹)
  • 检索层:查询改写 → 结构化过滤 → 向量召回 + 关键词召回 → 重排 → 压缩 → 注入
  • 治理层:TTL/衰减、置信度、审计、编辑、删除(合规)、评测

数据库选型(按需求分层,不是选一个万金油):

用途选型依据
会话状态 / 热记忆Redis (+ Hash/Stream)低延迟、有 TTL、会话级数据天然易失
向量语义检索Milvus / PG pgvector / ES kNN / Qdrant数据量、是否需要与业务库同源、运维成本
结构化记忆(带权限/时间/类型)PostgreSQL / MySQL事务、复杂条件过滤、权限关联、审计
用户画像 / KV 记忆Redis / MongoDB灵活 schema、高频读写
原始轨迹 / 大对象对象存储 + ES成本低、可全文检索、用于回放
图记忆(实体关系)Neo4j 等图库 (可选)多跳关系推理场景才值得,成本高

选型依据(六个维度,答这些显得专业):

  • 1. 检索模式 :只需语义相似 → 纯向量库;需要「语义 + 精确条件过滤」→ 向量库要支持元数据过滤,或 PG(vector + 关系同库, 这是中小规模最省事的选择 )。
  • 2. 数据规模与增长 :百万级以下 pgvector/ES 足够;千万级以上考虑专用向量库(分片、量化、索引类型 HNSW/IVF)。
  • 3. 延迟要求 :交互式强依赖 → 内存/SSD;后台任务可放宽。
  • 4. 一致性要求 :记忆冲突消解、多写并发 → 需要事务能力 → 关系库优先。
  • 5. 运维成本与团队栈 :能复用现有 PG/ES 就别引新组件,这是最现实的考量。
  • 6. 合规与删除 :必须支持「按用户彻底删除」(GDPR 类需求)→ 选支持行级删除、可按用户维度清理的方案,图库和多向量库在这点上会很痛苦。

我的推荐落地组合(可背):「Redis(会话态)+ PostgreSQL 或 MySQL(结构化记忆与权限)+ pgvector/Milvus(语义检索)+ 对象存储(轨迹与原文)」。理由是复用度高、事务可控、删除和权限好做;只有在检索规模真的上量时才引入独立向量库。

03长期记忆 vs RAG

本节提炼
  • RAG 回答'世界上有什么'，记忆回答'我经历过什么、你是谁'
  • 分长短期三原因：成本延迟、窗口效果、隐私合规
  • 架构差异在触发、处理、存储、召回、一致性、治理
  • 长期记忆难点是记什么、信不信、新旧冲突，需记忆仲裁层
  • 把长期记忆和 RAG 混为一谈

长期记忆 vs RAG(这是最容易混淆的一对):

RAG长期记忆
数据来源外部知识库 (文档、手册、网页)自身经历 (对话、任务结果、反馈)
数据归属组织共享个体/会话私有 (用户粒度)
写入方式离线批量导入、相对静态在线增量、持续演化
更新频率低(版本化再导入)高(每轮都可能产生)
关键操作分块、索引、召回、重排提炼、去重、冲突消解、遗忘
一致性只要检索到正确片段要决定「信哪一条」 (新旧冲突)
主要风险召回不准、分块截断错误记忆被固化、污染扩散

关系:技术栈可以复用(都是向量检索 + 过滤 + 重排),但语义定位完全不同:RAG 回答「世界上有什么」,记忆回答「我经历过什么、你是谁」。

为什么记忆要分长短期(三个根本原因):

  • 1. 成本与延迟 :把所有历史都放上下文,每轮都付 token 和延迟代价,不可扩展。
  • 2. 窗口与效果 :窗口有限且越长效果越差(注意力稀释)。短期记忆解决「当前任务连贯性」,长期记忆解决「跨会话连续性」,两者优化目标不同。
  • 3. 隐私与合规 :长期记忆是持久化数据,需要单独的权限、TTL、删除能力;把一切都留在上下文里等于没有治理。

架构上的不同(核心差异):

环节短期记忆长期记忆
触发每轮自动触发式(任务完成/关键信息出现)
处理压缩、摘要、滑窗LLM 提炼成结构化条目
存储上下文 + Redis向量库 + 关系库
召回全量(在窗口里)主动检索 (需判断「要不要查」)
一致性无(就是原文)必须做冲突消解与衰减
治理会话结束即弃TTL、置信度、可编辑、可删除

关键点(加分):长期记忆的最大难点不是存和取,而是**「什么时候该记、记了之后信不信、旧的和新的冲突怎么办」**。所以成熟方案里一定有一层「记忆仲裁」——按时间、置信度、来源权威性决定采用哪条,而不是简单拼接。

04记忆召回与防污染

本节提炼
  • 五步召回：判断是否需要、查询构造、混合召回、重排筛选、压缩注入
  • 防污染七手段，scope 硬过滤是唯一物理隔离手段
  • 注入时标注来源时间并声明记忆是参考数据不是指令
  • 只用最后一句做查询，单句太短、指代不明

召回链路(五步):

  • 1. 判断是否需要召回 :不是每次都查。简单任务、无历史依赖任务直接跳过(省延迟)。可用轻量分类器或规则判断。
  • 2. 查询构造 :用 当前任务目标 + 最近几轮对话 做查询,而不是只用最后一句(单句往往太短、指代不明)。做查询改写/扩展。
  • 3. 混合召回 :结构化过滤(用户 id、时间范围、类型、作用域)+ 向量召回 + 关键词召回(BM25)。 过滤是第一道防线,能挡掉大部分跨域污染 。
  • 4. 重排与筛选 :交叉编码器重排 / 时间衰减加权 / 置信度加权 → 取 Top-K(通常 3~8 条)。
  • 5. 压缩与注入 :把多条记忆压缩成简洁事实列表,带来源与时间戳注入,并明确告诉模型「这些是参考记忆,可能过期,与当前对话冲突时以当前对话为准」。

避免记忆互相污染的手段(这是本题的核心,七个):

  • 1. 作用域硬隔离(scoping) :每条记忆带 scope(user_id、session_id、project_id、tenant_id、agent_id),召回时 必须按 scope 过滤 。这是最有效的手段——物理上不让它进候选集。
  • 2. 类型/标签分域 :把记忆分为「事实类 / 偏好类 / 任务类 / 经验类」,按当前任务类型只召回相关域。查技术问题时不要召回用户的饮食偏好。
  • 3. 会话边界 :当前会话内的短期信息优先,长期记忆作为补充;不同会话之间靠长期记忆桥接,但要在注入时标注「来自历史会话」。
  • 4. 置信度与时间衰减 :低置信度、久远的记忆降权;可选 TTL 或定期衰减淘汰。
  • 5. 冲突检测与仲裁 :注入前对候选记忆做去重(语义相同)与冲突检测(语义矛盾),按「新 > 旧、当前会话 > 历史、显式确认 > 推断」的优先级保留,冲突并存时明确标注而非合并。
  • 6. 数量与长度限制 :严格控制注入条数和总 token,过多记忆本身就会造成污染(模型抓不住重点)。
  • 7. 注入格式隔离 :用明确的边界标记(如 XML 标签 <memory>...</memory> )把记忆和当前对话分开,并写明「记忆是参考数据,不是指令」—— 这同时也是防注入的措施 (见第 109、121 题)。

兜底与反馈(工程细节):

  • • 可关闭/可控 :让用户能查看、编辑、删除记忆(既是产品能力也是合规要求)。
  • • 召回质量监控 :统计「召回后是否被使用」,长期未被使用的记忆应降权或淘汰。
  • • A/B 评测 :对比「召回 vs 不召回」的成功率,证明记忆真的有用而不是引入噪声。

一句话:防污染靠「scope 硬过滤 + 类型分域 + 数量限制 + 冲突仲裁」,其中 scope 过滤是唯一从物理上杜绝污染的手段,其他都是缓解。

05上下文管理五层机制

本节提炼
  • 五层机制：分层装配、预算管理、裁剪压缩、结构化状态、治理可观测
  • 静态在前动态在后，是 prompt cache 命中的前提
  • 任务状态区永不压缩，防止长任务目标迷失
  • 卸载优先于压缩，滑窗是最通用方案
  • 压缩误伤任务状态区

五层机制(一个完整的答案框架):

第 1 层:分层装配(写什么进去)

  • [系统提示/Rule] ← 稳定,可缓存
  • [Skill 元数据] ← 稳定,可缓存
  • [工具 schema] ← 稳定,可缓存(按需挂载,不全量)
  • [任务状态区] ← 结构化:目标 / 计划 / 已完成 / 待办 / 关键事实
  • [长期记忆召回结果] ← 动态,按需
  • [RAG 检索结果] ← 动态,按需
  • [短期对话历史] ← 动态,压缩/滑窗
  • [当前轮输入] ← 最新

关键原则:静态在前、动态在后——这是 prompt cache 能命中的前提,直接决定成本和延迟。

第 2 层:预算管理(放多少)

  • 1. token 预算分配 :给每一区设上限比例(如系统 10%、记忆 15%、历史 40%、当前 20%、预留 15% 给输出)。
  • 2. 实时计数 :每次调用前计算总 token,超限触发策略。
  • 3. 阈值预警 :比如到 70% 开始预警、85% 触发压缩,而不是撞墙才处理。

第 3 层:裁剪与压缩(多了怎么办)

  • 1. 卸载优先 :大工具结果落盘,只留摘要 + 引用(第一道闸,最有效)。
  • 2. 摘要压缩 :对历史分段摘要。
  • 3. 滑窗 :保留最近 N 轮原文 + 更早的摘要( 这是最通用的方案 )。
  • 4. 折叠 :把冗余的中间轮次(如连续的工具调用细节)折叠成一句结论。
  • 5. 去重 :重复出现的工具结果、重复检索内容去重。

第 4 层:结构化状态(压缩不能伤的东西)

  • • 单独维护任务状态区 :目标、约束、已确认事实、已做决策、待办。 这个区永不压缩 (或只增不删),压缩只作用于对话历史和原始观察。
  • • 这是防止「长任务目标迷失」的关键设计(见第 81 题)。

第 5 层:治理与可观测

  • 1. 缓存 :稳定前缀 + prompt caching。
  • 2. 可观测 :每轮记录 token 占用、压缩次数、卸载次数、召回条数。
  • 3. 评测 :对比不同上下文策略的成功率与成本,用数据选策略而不是拍脑袋。
  • 4. 隔离 :子任务用 Subagent 独立上下文,只回结论。

一句话总结:上下文管理 = 分层装配(静态在前、动态在后)+ 预算分配 + 卸载/压缩/滑窗 + 不可压缩的结构化状态区 + 缓存与观测。

06检索 Agent 上下文管理

本节提炼
  • 检索结果先落工作区，上下文只放摘要+编号+关键字段
  • 渐进式检索、结构化压缩，保留结论而非原文
  • 子 Agent 隔离检索，主上下文只收结论+出处
  • 把上下文增长从 O(检索量) 压到 O(结论数)
  • 把检索结果全量入上下文

检索 Agent 的特殊性:它的上下文会被大量检索片段快速灌满,而且是所有 Agent 类型里膨胀最快的。所以策略要围绕「检索结果」做文章。

六个针对性策略:

  • 1. 检索结果的卸载 :一次检索召回 20 条 × 500 token = 10,000 token。 绝不全量入上下文 。做法:检索结果先落到「工作区」(文件/临时表),只把 摘要 + 编号 + 关键字段 放进上下文,模型判断需要哪几条再按编号取全文。这是检索 Agent 最关键的优化。
  • 2. 渐进式检索(由粗到细) :先只取标题/摘要级别的信息,确定方向后再取正文;而不是一开始就拉全文。多个检索轮次之间只保留「已确认的事实与出处」。
  • 3. 检索结果的结构化压缩 :每次检索后立即把结果压缩成结构化事实列表(结论 + 出处 + 置信度),丢弃原始长文本。 保留「结论」而不是「原文」 ——后续推理只需要结论。
  • 4. 子 Agent 隔离检索 :让检索子 Agent 在独立上下文里做多轮搜索,只返回「结论 + 出处」给主 Agent。主 Agent 上下文里永远只有结论,不承载搜索过程。这是多 Agent 做调研的标准做法。
  • 5. 来源与去重管理 :维护一个「已检索来源清单」,避免重复检索;对重复内容去重;对冲突结论标注而不是合并。
  • 6. 状态区承载「研究进展」 :把「已确认结论 / 待验证假设 / 下一步检索方向」放在结构化状态区,不随对话压缩而丢失—— 这解决了长调研任务的目标迷失问题 。

一个具体的落地形态(可以说这个):

  • 主 Agent 上下文:
  • 目标 + 研究大纲 + 已确认结论表(带出处)+ 待办问题 + 下一步方向
  • 检索工作区(不进上下文):
  • 原始网页 / 文档全文 / 中段结果(按 id 可检索)
  • 检索 Subagent:
  • 独立上下文,负责多轮检索,只回传「结论 + 出处 + 置信度」

一句话:检索 Agent 的上下文管理核心是「结论进上下文,原文留在工作区」,配合子 Agent 隔离,把上下文的增长从「O(检索量)」压到「O(结论数)」。

07上下文工程六环节

本节提炼
  • 六环节：选择、装配、压缩、卸载、隔离、治理
  • 最重要是 Select，能不进就不进
  • 选择是源头止损，压缩卸载都是补救

上下文工程的六个环节(完整闭环):

  • 1. 采集/选择(Select) :从所有可能的信息源(系统提示、Skill、工具 schema、记忆、RAG、历史、当前输入)里决定 哪些进上下文 。核心是「不进比进更重要」。
  • 2. 组织/装配(Assemble) :排序与分层。静态在前动态在后(缓存友好)、重要信息放 首尾 (中间容易被忽略,见第 78 题)、用明确的分隔标记区分信息源。
  • 3. 压缩(Compress) :摘要、折叠、去重、结构化提炼。
  • 4. 卸载(Offload) :大内容外置,只留引用。
  • 5. 隔离(Isolate) :用 Subagent / 子会话把不该污染主线的信息隔离出去。
  • 6. 治理(Govern) :token 预算、缓存、可观测、评测、权限与注入防护。

最重要的是哪一环?

我的答案:第 1 环——「选择(Select)」,即决定什么信息不该进上下文。

理由:

  • 1. 其他环节都是补救 。压缩和卸载是「已经进来了才处理」,而选择是从源头减少泄漏—— 省下的 token 远超压缩能省的 。
  • 2. 上下文质量决定效果上限 。模型效果对「上下文里有什么」的敏感度远高于「上下文里有多少」。塞满无关信息,再强的模型也会被稀释注意力、被误导。
  • 3. 成本结构决定 :选择做得好,压缩、卸载、治理的工作量和成本都同步下降。
  • 4. 一条准则可以贯穿整题 : 「能不进就不进,进来的必须有用」 。压缩是在浪费发生后止损,选择是根本不浪费。

补充(如果被追问):如果场景是「无法避免的长上下文」(如必须读一个巨大文件),那么最重要的是卸载 + 隔离,因为它们能把「线性增长」变成「按需增长」。

面试加分:主动提一句——「上下文工程的本质不是塞满窗口,而是在有限预算里最大化信噪比」,以及「上下文越长效果越差的根本原因是注意力稀释,所以『精简』本身就是效果优化,不只是省钱」。

08压缩与向量化顺序

本节提炼
  • 区分运行期上下文压缩与索引期文档压缩
  • 上下文压缩在装配前、卸载后，滚动增量做
  • RAG 侧先向量化原文，压缩是检索后的后处理
  • 先摘要再向量化，看似省存储实则降召回率

这是问「压缩和向量化的顺序」的经典题,答案是「分场景,不能一刀切」。

先明确两个不同的「压缩」概念,不要混淆:

  • 1. 上下文压缩 :对 已进上下文的历史/观察 做摘要——发生在 Agent Loop 的运行期。
  • 2. 文档压缩 / 分块 :对 待入库的文档 做处理——发生在 RAG 索引期。

对于上下文压缩(运行期):

  • • 位置 :在 上下文装配之前 做,即「先压缩历史,再组装本轮输入」。因为在装配时才知道剩余预算是多少,而且压缩后的文本才是这轮要发给模型的内容。
  • • 时机 :不是撞到阈值才做,而是 滚动式 ——每轮结束/每 N 轮做一次增量摘要,保持上下文处于「健康的长度区间」。 突然的大段压缩会打断体验 (见第 79 题)。
  • • 顺序 : 先卸载大对象,再压缩 。因为卸载能直接把 token 归零(大结果外置),而压缩是把 token 变少。先卸载能大幅减少需要压缩的内容量。

对于 RAG 文档处理(索引期)——「先压缩再向量化,还是反过来?」:

答案是:先向量化(用原文分块做 embedding),压缩/摘要是检索结果的「后处理」,不是索引的前置。 理由:

  • 1. embedding 需要原文语义 :预先摘要会丢失细节和实体,导致召回质量下降—— 摘要是有损的,而有损的信息不该进入索引 。
  • 2. 检索时才知道什么相关 :压缩必须针对「当前查询」才有意义。索引期的压缩是「无查询的压缩」,必然丢失长尾信息。
  • 3. 正确顺序 :
  • 索引期:原文 → 智能分块 → 向量化 → 入库(保留原文与元数据)
  • 检索期:查询 → 召回 Top-N 原文 → (可选)按查询做上下文压缩 → 注入

唯一的例外:如果存储成本极高或文档极长,可以做双层索引——索引期存摘要向量(粗召回)+ 原文向量(精召回),但原文必须保留,否则无法还原细节。

一个常见的误区(答出来加分):「先摘要再向量化」看起来省存储,实际会显著降低召回率,因为用户的问题往往匹配的是细节而非摘要。有损操作要放在检索之后,且要针对查询。

一句话:上下文压缩放在「装配前、卸载后」,采用滚动增量方式;文档侧则是「先向量化原文,再在检索结果上按查询压缩」。压缩永远针对「已知用途」,而不是「事前猜测」。

09滑窗+摘要落地

本节提炼
  • 三段式窗口：固定区+摘要区+滑动区+当前轮
  • 按 token 触发(70%~85%)，增量摘要合并进已有摘要
  • 摘要 prompt 结构化保留目标/事实/决策/待办
  • 被滑出原文落库可回溯，按完整轮次或工具交互切分
  • 一次性重新摘要全部历史，导致信息逐次丢失

先给方案全景(从轻到重,按优先级):

  • 1. 卸载(Offload) :大结果外置,最优先。
  • 2. 滑动窗口 + 摘要 :最通用。
  • 3. 结构化状态区 :压缩不了的核心信息。
  • 4. 子 Agent 隔离 。
  • 5. RAG 化历史 :历史存库,按需检索而不是全量携带。
  • 6. 分层摘要(多级摘要) 。
  • 7. KV Cache / 长上下文模型 :硬件/模型层面的解法。

滑动窗口 + 摘要的具体落地(核心部分,要讲细):

窗口结构(三段式):

  • [固定区] 系统提示 + Rule + Skill 元数据 + 工具 schema + 任务状态区(永不压缩)
  • [摘要区] 对更早历史的滚动摘要(压缩产物)
  • [滑动区] 最近 N 轮(或 M token)的完整原文(不压缩,保证近因准确)
  • [当前轮]

落地的六个关键决策:

  • 1. 触发条件 :按 token 数 触发,不按轮数(轮数不可控)。阈值设为窗口的 70%~85%,留出输出余量。
  • 2. 压缩粒度与增量 :每次只压缩「滑出滑动区的部分」,并且 合并进已有摘要 (增量摘要:摘要 + 新滑出的内容 → 新摘要),而不是每次重新摘要全部历史——避免信息逐次丢失和成本爆炸。
  • 3. 摘要 prompt 的设计(最关键) :必须结构化,明确要求保留:
  • • 当前任务目标与约束
  • • 已确认的事实与决策(带出处)
  • • 已完成的步骤与结论
  • • 未完成的待办与下一步
  • • 用户的偏好与关键要求
  • • 丢弃:寒暄、重复内容、已被结论替代的中间过程
  • 4. 原文落库 :被滑出的原文不能丢,写入数据库/文件, 标注 id ,并提供「按 id 回溯原文」的工具。这样压缩有损时仍可恢复—— 这是防止压缩失真的核心兜底 。
  • 5. 保留边界的完整性 :不要切断一个「工具调用 + 结果」对,也不要在对话中途切断——按「完整轮次」或「完整工具交互」滑出。
  • 6. 用户可见性 :压缩发生时给用户一个轻提示(「已整理较早的对话内容」),而不是静默,避免用户困惑于「它忘了」。

还要处理的两个难点:

  • • 压缩时机的体验问题 :不要一次性大幅压缩 → 用 滚动式小步压缩 (每轮或每几轮压一点),用户感知平滑(见第 79 题)。
  • • 压缩失真的缓解 :①摘要结构化 + 保留原文可回溯;②压缩后做一次「一致性校验」(让模型对比摘要与关键事实是否矛盾);③关键约束永不进摘要区,而是提升到固定区。

一句话落地公式:三段式窗口 + 按 token 触发 + 增量结构化摘要 + 原文可回溯 + 小步滚动压缩。

10工具结果压缩三方式

本节提炼
  • 方式A原地规则压缩默认首选；方式B小模型摘要；方式C卸载+按需取回
  • 模型压缩串行加延迟，须用便宜快模型且带任务上下文
  • 阈值分流：小结果直接进，中等规则+小模型，超大结果卸载
  • 用主模型做摘要，既慢又贵
  • 不带任务上下文做摘要，丢失任务相关信息

三种处理方式,各有取舍:

方式 A:原地压缩(确定性规则,不调模型)

  • • 做法:截断、取字段(只保留关键 JSON 字段)、去重、按行采样、正则提取。
  • • 优点:零额外延迟、零成本、结果确定可预测。
  • • 缺点:可能截断关键信息;不擅长语义压缩。
  • • 适用:结构化的、可预知的大结果(日志、列表、表格)。 这是默认首选 。

方式 B:交给另一个模型压缩(LLM 摘要)

  • • 做法:把工具结果交给小模型摘要/提炼。
  • • 优点:语义保持好,能提炼结论、能过滤噪声。
  • • 缺点: 额外一次 LLM 调用 → 增加延迟(通常几百 ms 到数秒)和成本 ;有失真风险(摘要幻觉);对小结果不划算。
  • • 适用:非结构化的大文本(网页、文档、长日志、大段代码)。且 用便宜快的小模型 (这是关键——用主模型摘要既慢又贵)。

方式 C:卸载 + 按需取回(最优但工程量最大)

  • • 做法:结果整体落盘,上下文里只放「摘要 + 引用 id」,模型需要细节时用工具按 id / 按行范围取回。
  • • 优点:上下文成本最低,信息不丢失,可按需精确取。
  • • 缺点:需要工作区设施;模型要会用「取回」工具(有额外的调用轮次)。
  • • 适用:超大结果(几十 KB 以上)。 对超大结果,这个方案严格优于前两者。

对执行效果的影响:

原地压缩模型压缩卸载取回
信息损失可能丢关键字段(硬伤)语义级损失(软伤,可能幻觉)无损
上下文占用中低最低
效果风险截断导致误判摘要幻觉引入错误结论模型忘记取回细节

对耗时的影响:

  • • 原地压缩:几乎无感。
  • • 模型压缩: 串行增加 1 次 LLM 调用 ,在长链路里叠加明显(20 步 × 1s = 20s)。可用 并行 (多个工具结果并行摘要)缓解。
  • • 卸载取回:主链路省时间(上下文短 → 模型推理也更快),但需要额外的取回轮次时才付代价。

我的实践策略(组合拳,这是最好的答案):

  • 1. 先规则(方式 A) :能结构化提取的就规则提取,尤其是表格/日志类(取关键行、关键字段、前 N 行 + 后 N 行)。
  • 2. 阈值分流 :小结果(< 1~2K token)直接进; 中等结果用规则 + 小模型摘要 ;超大结果 卸载 ,只留摘要 + id。
  • 3. 摘要用最便宜的快模型 ,不用主模型。
  • 4. 摘要 prompt 要「带任务上下文」 :告诉摘要器当前任务目标是什么,让它保留相关部分—— 无目标的摘要必然丢失任务相关信息 ,这是模型压缩效果差的主要原因。
  • 5. 保留原始结果的引用 ,方便回溯与审计。
  • 6. 可观测 :记录压缩前后 token、压缩耗时、是否被回溯取回,据此调阈值。

一句话总结:优先规则压缩,大结果卸载,只有在非结构化且无法卸载时才用模型摘要——且必须用小模型、带任务上下文、可回溯。

11长上下文不稳定的原因

本节提炼
  • 四大机制：注意力稀释、中间遗失、干扰冲突、噪声累积
  • 位置影响来自位置编码衰减、首因/近因偏好、训练分布
  • 应对：关键信息放首尾、结构化分隔、精简、任务拆分
  • 指望更长窗口解决稳定性，而非精简与拆分

第一个问题:为什么越长越不稳定(四个机制):

  • 1. 注意力稀释(Attention Dilution) :Softmax 注意力是归一化的,分母越大,每个 token 分到的权重越小 → 关键信息的信号被大量无关内容平摊。 这是最本质的原因。
  • 2. 中间遗失(Lost in the Middle) :模型对 首尾位置 的信息利用明显更好,长上下文中间部分的信息容易被忽略。这是被反复验证的实证现象。
  • 3. 干扰与冲突 :上下文中存在重复、矛盾、相似但不相关的信息时,模型容易混淆(「哪一条才是当前要求?」),产生相互矛盾的输出。
  • 4. 噪声累积与错误传播 :长上下文里往往包含前序步骤的错误、被污染的观察,模型会把错误当事实继续推导。
  • 5. （补充）位置偏置与训练分布 :模型训练时的有效长度往往短于宣称的支持长度,超长上下文下的行为是外推,稳定性下降。

第二个问题:为什么位置影响效果(三个原因):

  • 1. 位置编码的衰减 :相对位置编码使得距离越远,注意力分数越低,远处信息影响弱。
  • 2. 注意力分配的天然偏好(首因/近因) :开头的系统指令定义了「角色与规则」,模型对它有强锚定;末尾的内容紧邻生成的起点,直接影响下一个 token 的分布。
  • 3. 训练数据的分布 :训练语料中「重要内容在前(背景/指令)+ 关键内容在后(问题)」的形态最常见,模型学到了这种位置先验。

工程应对(这是面试官真正想听的):

  • 1. 重要信息放首尾 :关键指令、当前任务、输出格式要求在 开头和结尾各强调一次 (首尾夹击)。
  • 2. 结构化分隔 :用清晰的标记( <rules> , <context> , <task> )划分区块,降低混淆。
  • 3. 精简上下文 :减少无关内容是最有效的改善(呼应「选择比压缩重要」)。
  • 4. 中间放摘要而非原文 :长内容的中间部分放压缩后的关键点。
  • 5. 重复关键约束 :在每轮的当前输入里重申输出格式与硬约束,而不是只靠开头的系统提示。
  • 6. 减少矛盾信息 :冲突内容必须仲裁后再注入,不要并存。
  • 7. 短任务拆分子 Agent :把长链路拆成短的独立调用,每个子调用上下文都短—— 这是最根本的解法 ,因为单次调用的上下文短了,稳定性的问题从源头消失。

一句话:长上下文不稳定源于注意力稀释与位置偏置,这是架构性质而非模型缺陷——所以应对方法是「精简 + 分位置放置 + 关键信息重复 + 任务拆分」,而不是指望更长的窗口。

12避免大段压缩打断体验

本节提炼
  • 滚动增量压缩，多级阈值(60/75/85/95%)提前触发
  • 异步压缩不阻塞响应，卸载优先让用户无感
  • 压缩可回看、可干预，透明比静默好
  • 结构化区保护核心诉求，压缩边界落在完整轮次
  • 在工具调用中间或用户等待时压缩

核心思路:把「事件式的突发压缩」改成「常态化的渐进收敛」。

六个具体手段:

  • 1. 滚动增量压缩(最核心) :不要等到 85% 才压缩,而是 每轮结束或每 N 轮做一次小额压缩 ——比如每次压缩掉最旧的 2~3 轮,合并进摘要区。这样上下文长度 始终维持在健康区间 ,永远不会有「突然大段消失」的时刻。
  • 2. 提前触发 + 多级阈值 :
  • • 60%:开始「轻压缩」(折叠冗余的工具调用细节、去重)。
  • • 75%:压缩旧轮次。
  • • 85%:压缩近期轮次(用户开始感觉到,但已是渐进过程)。
  • • 95%:硬截断 + 明确告知。 每一级都是小步,用户感受是平滑的。
  • 3. 异步压缩,不阻塞响应 :压缩在上一轮响应结束后 后台异步进行 ,不占用用户等待的时间。用户下次提问时,压缩已经完成。
  • 4. 卸载代替压缩 :大结果直接落盘外置, 用户完全无感知 (因为它本来就不该在上下文里)。这是「无感」的关键—— 最好的压缩是用户不知道发生过的压缩 。
  • 5. 明确的用户可见性(反而提升信任) :当确实发生影响记忆的压缩时:
  • • 给一个 轻量、非阻塞的提示 (如状态栏「已整理较早的对话」),而不是弹窗打断。
  • • 提供可回看入口 :用户能点开看到原始对话(因为原文落库了)。
  • • 让用户能干预 :如「保留这段」「从这里重新开始」。 透明比静默好——用户最怕的是「它悄悄忘了我刚说的要求」。
  • 6. 结构化区保护用户体验的关键点 : 把「用户的核心要求、当前目标、未完成待办」提升到不可压缩的固定区 。这样即使历史被压缩,用户的核心诉求也不会丢——这是「压缩不影响体验」的根本保障。

还要避免的两个坑:

  • • 不要在工具调用中间压缩 :压缩边界必须落在完整轮次/完整工具交互上,否则会出现「调用没有结果」的畸形上下文,直接导致模型行为异常。
  • • 不要在用户正在等待时压缩 :压缩要放在空闲窗口,不要增加首 token 延迟。

产品侧的设计建议(加分):

  • • 长任务场景提供**「会话分叉/新开会话」**的显式入口,并自动带上「任务状态摘要」—— 与其在旧会话里挣扎,不如优雅地开新会话并继承状态 。这是很多产品的正确做法(见第 82 题)。

一句话总结:用「多级阈值 + 滚动增量 + 异步执行 + 卸载优先 + 结构化区保护 + 透明可回看」把压缩从突发事件变成持续过程,用户不会有被「切断」的感觉。

13规避窗口限制与卸载实现

本节提炼
  • 除压缩外六类方案：卸载、RAG 化、Subagent、状态区、缓存、模型侧
  • 卸载=上下文与工作区分离，上下文只放摘要+引用
  • 写入路径：判大小→落工作区→摘要→只注入引用；取回支持局部取
  • 安全：路径由系统生成防穿越，配额与 TTL 管理
  • 取回只支持全文取回，把上下文再次塞满

除了压缩,还有六类方案:

  • 1. 卸载(Offload) :大结果外置,上下文只留引用。 性价比最高。
  • 2. 检索化(RAG 化) :历史/知识不入上下文,按需检索召回。
  • 3. 隔离(Subagent) :子任务独立上下文,只回结论。
  • 4. 结构化状态区 :用结构化的「目标 + 事实 + 待办」代替原始对话,信息密度高几个数量级。
  • 5. 缓存与复用 :KV cache / prompt cache 降低重复前缀的成本(不解决容量,但解决成本与延迟)。
  • 6. 模型与架构侧 :长上下文模型、KV cache 压缩(如 GQA、量化)、外部记忆模块。这些是模型侧的事,工程上只需选型。
  • 7. （产品侧）会话分叉 :开新会话 + 状态继承摘要。

大结果卸载的工程实现(本题重点,要讲细):

核心思想:把「上下文」和「工作区」分离。上下文放索引与摘要,工作区放全量数据。

实现要素:

  • 1. 存储介质选择 :
  • • 会话工作区目录 (文件系统/对象存储):每个会话一个目录,按 session_id/step_id/tool_call_id 组织。适合文本、日志、JSON、代码。
  • • 临时表(DB) :结构化结果落库,支持按条件查询。适合结构化数据与需要 SQL 过滤的场景。
  • • 大对象存储(S3/OSS) :超大文件、二进制。
  • • 选择依据:是否需要结构化查询 → DB;是否只需按块取回 → 文件;是否超大/长期 → 对象存储。
  • 2. 写入路径(工具执行后立即卸载) :
  • 工具返回结果
  • → 判断大小(如 > 4KB 或 > 2K token)
  • → 是 → 写入工作区,生成 workspace_id / path
  • → 计算摘要(规则提取 + 可选小模型摘要)
  • → 上下文只注入:
  • { "tool": "query_logs", "status": "ok",
  • "summary": "共 1284 条错误,主要类型:超时(62%),空指针(21%)",
  • "preview": "前 5 行...",
  • "full_result_ref": "ws://session-123/step-7/out.json",
  • "lines": 1284, "bytes": 83012 }
  • → 否 → 直接注入
  • 3. 取回路径(给模型一个检索工具) :
  • • 提供工具: read_workspace(ref, offset, limit) 、 grep_workspace(ref, pattern) 、 query_workspace(sql_field...) 。
  • • 关键:取回要支持「局部取」 (按行范围、按正则、按 JSON path),而不是只能全文取回——否则取回就又把上下文塞满了。
  • • 告诉模型如何用好它 :在工具 description 里写清「当摘要不足以判断时,用 grep 精确定位而不是读全文」。
  • 4. 引用格式要稳定且可解析 :统一前缀(如 ws:// ),上下文里明确标注这是「外部引用,需要时取回」。
  • 5. 生命周期管理 :
  • • TTL 与清理 :会话结束后按策略清理或归档。
  • • 配额 :单会话工作区有容量上限,防止磁盘打满。
  • • 安全 :路径必须由系统生成(不能由模型拼接),防路径穿越;文件权限隔离到会话/租户粒度。
  • 6. 可观测与效果评估 :
  • • 统计卸载率、取回率、取回命中率。
  • • 如果卸载后从不取回 ,说明摘要质量够(好);如果频繁取回同样内容,说明摘要丢了关键信息(需优化摘要规则)。
  • • 对比「卸载 vs 不卸载」的成功率——确认信息损失可接受。
  • 7. 降级与兜底 :
  • • 工作区写失败 → 退回「截断 + 标记」并在上下文里说明信息被截断(诚实优于伪装)。
  • • 取回失败 → 明确告诉模型「引用不可用」,让它换策略。

一个容易忽略的点(加分):卸载不仅是省 token,还提升效果——因为上下文更短、信噪比更高(呼应第 78 题)。同时它让「工具结果的原文」可被审计和回放,这对 Agent 的可观测性和问题定位价值巨大。

14避免任务目标迷失

本节提炼
  • 任务状态区永不压缩只增不删，是防目标迷失的根本
  • 阶段性重申、每轮目标提醒、约束提升到系统提示
  • '无限记忆'是存储层，'舍弃历史'是注意力层，靠检索连接
  • 舍弃过程保留结论，舍弃细节保留引用
  • 把存储容量与注意力容量混为一谈

第一部分:如何避免目标迷失(六个手段):

  • 1. 结构化任务状态区(最核心) :单独维护一个 永不压缩、只增不删 的区域:
  • <task_state>
  • 目标:把 X 服务从 Java 8 升级到 Java 17 并保证接口兼容
  • 约束:不能改对外接口签名;必须保留现有单测;升级期间服务不可中断
  • 已确认事实:依赖 A 是阻塞项(不兼容 Java 17);模块 B 已升级完成
  • 已做决策:采用分支升级方案,分三步灰度
  • 待办:TODO-3 处理依赖 A;TODO-4 跑全量回归
  • 当前进度:第 2 步 / 共 3 步
  • </task_state>

这段内容放在上下文里固定位置(或首尾各一次),任何压缩都不碰它。 这是解决目标迷失的根本手段。

  • 2. 阶段性目标重申(Re-anchor) :每完成一个里程碑,让模型显式复述「目标 + 当前进度 + 下一步」,并把结果写入状态区。相当于定期「对齐罗盘」。
  • 3. 在每轮输入里带目标提醒 :不依赖模型自己记住开头的指令——在每轮的用户消息前缀里附带一句「当前任务:<目标>,当前步骤:<步骤>」。
  • 4. 关键约束提升到系统提示 :硬约束不放对话历史里,放系统提示(固定区),永不被压缩。
  • 5. 检查点与进度追踪 :显式维护子任务列表与状态(done/doing/todo),让「进度」变成外部状态而不是模型的记忆负担。
  • 6. 偏离检测(规划校验 Agent) :在 Supervisor 层定期检查「当前行为是否仍在服务原目标」,发现偏离就纠偏或重规划。

第二部分:如何理解「无限长记忆」和「必须舍弃历史」的矛盾:

这是一个「存储容量 vs 注意力容量」的层次混淆问题,要分层回答:

  • 1. 矛盾的本质是「两个不同的资源」被混为一谈 :
  • • 存储 可以无限(硬盘/向量库),所以「无限长记忆」在存储层是 可行的 。
  • • 注意力(上下文窗口) 才是稀缺项,所以「必须舍弃历史」是在 推理层 的必然。
  • • 结论:不矛盾——「无限记忆」指的是存储,「舍弃历史」指的是单次推理的输入。 后者靠检索从前者取回,这就是记忆系统的意义。
  • 2. 为什么不能全塞进上下文(即使模型宣称支持超长窗口) :
  • • 成本线性增长;
  • • 效果随长度下降(注意力稀释,见第 78 题);
  • • 延迟线性增长;
  • • 且 大部分历史与当前任务无关 ,塞进去是纯噪声。 「能放进去」不等于「该放进去」 。
  • 3. 类比(讲这个最清晰) :人脑就是这样工作的。你不会把一辈子所有经历同时装在意识里(否则无法思考),但你 记得住关键结论和索引 ;需要时你能回忆起相关经验的 要点 ,而不是原始画面。 记忆系统的本质是「索引 + 相关时召回」,不是「全量常驻」。
  • 4. 工程上的正确姿态(三层分离) :
  • • 原始轨迹层 :全量留存(对象存储/ES),用于审计、回放、重新提炼。永不丢。
  • • 结构化记忆层 :提炼出的目标、事实、偏好、结论(向量库 + 关系库), 长期保留但可淘汰 。
  • • 上下文层 :每次只放当前任务所需,大小有硬预算。 「无限记忆」属于第一、二层,「舍弃历史」发生在第三层。
  • 5. 什么该被舍弃(判断标准) :
  • • 可丢:寒暄、重复内容、已被结论替代的中间过程、与当前任务无关的历史。
  • • 不可丢:目标与约束、已确认事实与决策、未完成待办、用户的明确要求、错误的教训。
  • • 原则:舍弃过程,保留结论;舍弃细节,保留引用。

一句话总结:「无限记忆」是存储层的目标,「舍弃历史」是注意力层的必然,两者通过「检索」连接——记忆系统的价值就在于让有限的注意力总能取到最关键的那部分历史。

15上下文污染 vs 工具污染

本节提炼
  • 上下文污染来自上下文误导信息，工具污染来自工具层脏数据/投毒
  • 自下而上排查：先 Observation→再推理→最后怀疑上下文
  • 能定位就修复上下文；扩散/漂移/注入则开新 session 并继承状态摘要
  • 污染扩散后仍原地修复，越修越乱

第一部分:两种污染的区分(定义 + 判别表):

上下文污染(Context Pollution):上下文里存在误导性信息——包括:

  • • 前序步骤的错误结论被当事实;
  • • 相互矛盾的指令并存;
  • • 无关的长文本稀释注意力;
  • • 注入的恶意/错误指令(来自网页、文档);
  • • 过期的信息。

工具污染(Tool Pollution):污染来自工具层——包括:

  • • 工具返回了错误/脏数据(下游系统本身错了);
  • • 工具返回格式异常、字段缺失;
  • • 工具被投毒(description 被注入恶意指令、返回内容里藏指令);
  • • 工具选择本身就错了(选了错误的工具导致后续基于错误前提推理)。

判别方法(实操性最强):

判据上下文污染工具污染
只看轨迹的前半段能否发现问题能(错误来自自己写的内容)不能(前半段看起来正常)
换一个干净上下文重跑同一批工具调用结果正常仍然错误
直接检查原始工具返回正常异常/脏数据
错误首次出现的位置在模型的推理/总结文本里在工具返回的 Observation 里
是否可复现依赖历史,不总复现同一工具稳定复现

排查顺序(可背):「先看 Observation 原文 → 再看模型推理 → 最后怀疑上下文」,即自下而上排查:工具返回是不是本来就错 → 模型对工具结果的解读是不是错 → 上下文里有没有引入外部噪声。

第二部分:继续控制上下文 还是 新开 session?

判断标准不是「问题多严重」,而是「污染是否可定位、可摘除」。

应该「继续并修复上下文」的场景:

  • 1. 污染 可精确定位 (知道是哪几条消息/哪个工具结果引入的)。
  • 2. 污染是 局部的 (少量消息),且 目标是清晰稳定的 。
  • 3. 上下文里有 高价值的已积累状态 (需求细节、用户偏好、长任务进展)——新开 session 会丢掉这些。
  • 4. 用户还在同一任务上, 新开会话会造成对话断裂 (用户体验差)。

修复手段:①删除/标记失效的那几条消息;②注入一条纠正性的系统消息(「注意:第 X 步的结论有误,正确是 Y」);③在状态区更正事实;④压缩掉受污染的历史段。

应该「新开 session」的场景:

  • 1. 污染已扩散 :错误结论已经渗透到多处推理和状态,无法定位剥离(「毒已经扩散」)。
  • 2. 目标已漂移 :模型已经跑偏到一个错误的任务上,且反复纠正无效。 继续纠正的成本已经超过重新开始。
  • 3. 注入攻击 :上下文被外部恶意内容污染, 从安全角度必须隔离 ——继续用可能持续被操纵。
  • 4. 任务实际上已经切换 :用户的真实需求变了,旧历史只会是干扰。
  • 5. 上下文已被压缩到失真 :多次压缩导致关键信息丢失,继续下去是靠不可靠的摘要推理。

新开 session 的正确做法(不是简单地清空):

  • 1. 先提炼「状态摘要」 :从旧会话提取目标、约束、已确认事实、已完成工作、待办、踩过的坑。
  • 2. 在新会话里以结构化形式注入 :让新会话「继承成果但不继承污染」—— 带上结论,丢掉过程 。
  • 3. 告知用户 :「已开启新的处理流程,以下是我们已确认的信息...」——让用户能验证继承的信息是否正确(这是最关键的一道人工校验)。
  • 4. 保留旧会话可回看 :不删除,便于追溯。

一个实用的经验阈值(加分):「同一问题纠正失败 2 次以上,或污染点无法明确指认,就果断开新会话 + 状态继承」。继续在污染的上下文里挣扎通常越修越乱——这是实践中最省时间的判断。

一句话总结:先自下而上区分污染源(工具层 vs 上下文层),能精确定位就修复上下文,污染扩散/目标漂移/被注入就开新 session,并且新会话必须带「结构化状态摘要」而不是从零开始。

16长期记忆持续优化

本节提炼
  • 顺序：先优化写→存→取，最后用评测闭环驱动
  • 多级记忆冷热分离，定期离线固化高层结论
  • 冲突按新>旧、显式>推断、高置信>低置信更新
  • 写优化收益最大：不优化存什么，检索优化都是徒劳
  • 只堆原始对话不做提炼固化，错误记忆长期固化

核心挑战:数据量持续增长,但相关性和时效性持续衰减;错误的记忆会长期固化;成本随存储增长。

六个优化方向:

  • 1. 多级记忆架构(冷热分离) :
  • • 热 :当前会话 + 最近 N 天的高频记忆,常驻/快速检索(Redis)。
  • • 温 :数月内记忆,向量库 + 关系库,正常检索。
  • • 冷 :归档到对象存储 + ES,只在明确需要时深层检索。
  • • 效果 :检索永远先打热温层,延迟和成本可控。
  • 2. 记忆的提炼与升级(而不是无限堆积原始对话) :
  • • 定期离线「记忆固化」任务 :把一段时间的对话提炼成高层结论(如「该用户长期关注性能优化,偏好简洁回答」),用少量高密度记忆替换大量原始对话。
  • • 形成记忆的层次 :原始对话 → 会话摘要 → 事实/偏好条目 → 长期画像。 越上层越抽象,越少,越长寿。
  • • 这是最关键的优化 :不优化「存什么」,任何检索优化都是徒劳。
  • 3. 时效性与衰减机制 :
  • • 每条记忆带 时间戳 + 有效期限 ;时效性强的记忆(如「当前正在做的项目」)到期自动降权/失效。
  • • 时间衰减加权 :检索排序中,新记忆权重更高(但要防止「新即正确」的极端)。
  • • 区分时效型与恒定型 :偏好(恒定)与临时状态(时效)用不同策略。
  • 4. 冲突消解与记忆更新(防固化) :
  • • 新信息与旧记忆冲突时, 按「新 > 旧、显式确认 > 推断、高置信 > 低置信」更新 ,而不是追加矛盾条目。
  • • 支持记忆的修订与撤销 :发现错误记忆能被修正(要能定位到「哪次对话产生了这条记忆」)。
  • • 反向验证 :周期性抽检记忆的准确性(尤其事实类),发现失真就修正。 防止错误记忆被长期当真相比 。
  • 5. 检索优化(规模增长后的必然) :
  • • 混合检索 :结构化过滤 + 向量 + 关键词 + 图关系。
  • • 查询理解 :把用户问题改写成「需要什么类型的记忆」,先按类型缩小范围。
  • • 重排与多样性 :避免召回一堆高度相似的记忆(占位却无信息增量),引入多样性惩罚。
  • • 增量索引与分层索引 :大规模下用两层索引(粗筛 + 精排)。
  • • 缓存高频查询的记忆召回结果 。
  • 6. 治理与评测(保证长期健康) :
  • • 淘汰机制 :长期未被召回/未被使用的记忆降权并淘汰(避免垃圾堆积拖慢检索、拉低准确率)。
  • • 按需删除 :用户可查看/编辑/删除(合规必需)。
  • • 效果度量 :记忆的「被使用率、贡献度(有记忆 vs 无记忆的成功率差)、失真率」。
  • • 成本监控 :存储与检索成本的增长曲线,决定是否要更激进的固化与淘汰。

一句话总结:长期记忆系统的持续优化,顺序是「先优化写(提炼固化,减少低价值记忆)→ 再优化存(冷热分层 + 时效衰减)→ 再优化取(混合检索 + 重排 + 淘汰)→ 最后用评测闭环驱动整个过程」。其中「写」的优化收益最大。

17记忆量化指标与评测

本节提炼
  • 系统指标：Recall@K/Precision@K/MRR/NDCG、失真率、重复率、覆盖率
  • 贡献用 A/B 对照组成功率差与消融实验量化
  • 必须测负面指标：过期误答率、盲信记忆违背率
  • 工程埋点按轮/周监控召回条数、token、失真率
  • 评测只测召回质量，缺少负面指标

有,而且要分「记忆系统自身指标」和「对 Agent 效果的贡献」两层。

第一层:记忆系统自身指标

  • 1. 召回质量 :
  • • Recall@K :该召回的记住了吗?(需要标注「标准记忆集」)
  • • Precision@K :召回的是不是都相关?(防止噪声)
  • • MRR / NDCG :排序质量(相关的排得靠前吗)。
  • 2. 写入质量 :
  • • 提炼准确率 :抽取出的记忆与真实事实的一致率(人工抽检)。
  • • 虚假记忆率 / 失真率 :写入了错误信息的比例( 最关键的风险指标 )。
  • • 重复率 :同一事实被重复写入的比例。
  • • 覆盖率 :该记的关键信息(偏好、约束)有没有漏。
  • 3. 使用与健康度 :
  • • 命中使用率 :召回的记忆有多少真的影响了输出。
  • • 召回频率分布 :是否有记忆从不被召回(淘汰候选)。
  • • 时效健康度 :过期记忆被召回的比例。
  • • 冲突比例 :互相矛盾的记忆占比。

第二层:对 Agent 效果的贡献(最有说服力)

  • 1. A/B 对比(黄金标准) :
  • • 对照组 :关闭记忆;
  • • 实验组 :开启记忆。
  • • 比较任务 成功率、平均轮次、token 消耗、用户满意度 。
  • • 记忆的贡献 = 两组成功率之差 (这是回答「贡献怎么量化」的核心)。
  • 2. 消融实验 :
  • • 只有长期记忆 / 只有短期记忆 / 两者都有 → 分别测,定位各自贡献。
  • • 记忆条数做梯度(0/3/5/10 条)找最优注入量。
  • 3. 长会话专项评测集 :
  • • 构造需要跨会话记忆的任务(如「还记得我上次说的偏好设置吗」),测 跨会话一致性成功率 。
  • • 测「重复提问」(用户重复说了已经说过的事)——记忆到位则无需重复。
  • 4. 负面指标(必须测,最容易被忽略) :
  • • 记忆有没有变差 :召回过期/错误记忆导致的 误答率 ;
  • • 过度依赖 :模型盲信记忆而忽略当前对话的情况(「以当前对话为准」的违背率);
  • • 延迟与成本增量。 只有证明「收益 > 副作用」,记忆才算有效。

第三层:工程埋点(日常监控)

  • • 每轮记录:召回条数、召回来源类型、是否被使用、token 增量、延迟增量。
  • • 按周统计:记忆库增长量、淘汰量、失真率、冲突率。

一句话总结:记忆的评测 = 「召回质量指标(Recall/Precision/失真率)+ 消融与 A/B 的任务成功率差值 + 负面指标(过期/盲信导致的误答率)」,缺少负面指标的评测是不完整的——多召回不等于更好。

18哪些数据写入记忆

本节提炼
  • 四门槛：持久性、复现性、不可再得性、价值密度
  • 长期记忆记偏好/事实/约束/教训/结论；短期记忆记目标计划与中间观察
  • 不该写：原始大块数据、可再查事实、中间过程、寒暄、未验证推测
  • 记结论不记过程，记引用不记全量，带元数据异步降噪
  • 把模型自己的推测当事实写入记忆

判断标准(四个门槛,同时用):

  • 1. 持久性(Persistence) :这条信息 下次还需要吗? 只用一次的过程性数据不记(如中间检索的原始结果、临时计算值)。会跨轮/跨会话用到的才记。
  • 2. 复现性(Reusability) :这条信息 会不会被重复问/重复需要? 用户偏好、账号信息、常用参数、项目约定——高复现性必记。
  • 3. 不可再得性(Non-recoverability) :这条信息 丢了还能不能拿回来? 能从数据库/接口再查到的,可以不记(记个引用即可); 一旦丢失无法复原的(用户的临时决定、口头约束、踩过的坑)必须记 。
  • 4. 价值密度(Value) :这条信息 对后续决策有影响吗? 影响后续动作方向的要记;纯闲聊、情绪表达不记。

具体该记什么(分类清单):

该写入长期记忆:

  • • 用户偏好与习惯 :输出格式偏好、语言、详细程度、常用工具。
  • • 稳定事实 :用户身份、项目背景、技术栈、组织约束。
  • • 关键约束与决定 :「这个接口不能改」「必须用 XX 方案」。
  • • 经验教训 :失败原因、无效方案( 「别再试 XX」比「要试 YY」更省时间 )。
  • • 已完成工作与结论 :长任务的阶段性成果(跨会话续做必需)。

该写入短期记忆(会话内):

  • • 当前任务目标与计划;
  • • 当前步骤的中间观察(工具结果) —— 且大结果要卸载;
  • • 本轮已尝试过的方案(防重复);
  • • 当前的临时参数与上下文。

不该写入(高频错误,答出来加分):

  • • 原始工具返回的大块数据 (落工作区,不写记忆);
  • • 可从源头再查的事实 (如「订单 123 的状态」——记引用比记内容好);
  • • 被结论替代的中间过程 (只记结论);
  • • 寒暄和情绪表达 ;
  • • 模型自己的推测 (未验证的推断写入记忆是最危险的污染源—— 只记有依据的内容,并带来源 )。

四条工程准则:

  • 1. 记结论不记过程,记引用不记全量 。
  • 2. 每条记忆必须带元数据 :来源、时间、置信度、作用域、类型。 没有元数据的记忆无法被正确信任和淘汰 。
  • 3. 写入要异步、要降噪 :写入是额外成本,不能阻塞主链路;必须经过提炼与去重,不要原始对话直灌。
  • 4. 区分「事实」与「推断」 :推断类的记忆必须有更低置信度和更短 TTL, 绝不能与用户明确陈述的事实同等对待 (这是记忆污染最常见的来源)。

一句话总结:判断是否写入用四个门槛——持久、复现、不可再得、有价值;写法上记结论、记引用、带元数据、异步降噪;特别警惕把推测当事实写进去。

19压缩不丢关键内容

本节提炼
  • 五重保障：结构化 prompt、不可压缩区、增量合并、原文可回溯、压缩后校验
  • 失真对症：数字原样引用、结论逐条列举、禁推断、永不二次摘要
  • 治本：尽量别压缩，卸载/隔离/RAG 化/状态区减少需压缩内容
  • 对摘要再次摘要导致逐次衰减

第一部分:如何不丢关键内容(五道保障):

  • 1. 结构化的压缩 Prompt(第一道) :明确要求逐项保留:
  • 压缩时你必须完整保留(逐项检查):
  • 1. 用户的原始目标与所有明确要求(不能改写、不能省略)
  • 2. 已确认的事实、数据、结论(带出处)
  • 3. 已做的决策与其理由
  • 4. 未完成的待办事项与明确的下一步
  • 5. 用户表达的偏好、禁忌、硬约束
  • 6. 失败与踩坑记录(哪些方案已排除)
  • 可以压缩:寒暄、重复内容、已被结论替代的中间过程、无关的细节
  • 禁止:不要推断、不要补充原文没有的信息
  • 2. 不可压缩区(第二道,最有效) : 关键内容根本不进压缩管道 。
  • • 目标、约束、待办维护在 独立的任务状态区 ,永不压缩;
  • • 用户明确的要求放系统提示/固定区;
  • • 原则:能靠「不放进去」解决的,不要靠「压缩时不丢」解决。
  • 3. 增量压缩 + 合并(第三道) :每次只压缩新滑出的部分,并合并进已有摘要。避免「反复压缩同一内容」造成的逐次有损累积(信息每压一次掉一层,是失真的主要来源)。
  • 4. 原文可回溯(第四道,兜底) :被压缩的原文全部落库, 带索引 id ;提供「按 id / 按关键词回溯原文」的工具。 压缩有损时,模型或人都能取回原文核对 。这是唯一能兜住「压缩必然有损」的机制。
  • 5. 压缩后一致性校验(第五道) :压缩完成后,让模型(或规则) 对比摘要与关键事实 :
  • • 用户的原始要求是否都在?
  • • 关键数字/名称/结论是否一致(数字最容易在压缩中被改错)?
  • • 有没有凭空新增的信息(压缩幻觉)? 发现问题就 重压或用原文补齐 。

第二部分:压缩导致失真如何缓解(按原因对症):

失真表现原因缓解手段
关键约束丢失摘要 prompt 没要求保留约束结构化 prompt + 约束移出压缩区
数字/名称被改错LLM 摘要有改写倾向数字与专有名词要求原样引用 ;校验环节专门核对
结论被软化/曲解摘要倾向于「概括」要求「结论按原意逐条列举」,禁止概括性改写
凭空新增信息压缩幻觉明确禁止推断;校验环节反查「摘要中的每条能否在原文找到依据」
反复压缩逐次衰减对摘要再次摘要增量合并,永不二次摘要 ;保留原文
因果关系丢失摘要只留结果不留条件要求保留「结论 + 前提条件」配对
上下文冲突摘要与任务状态区不一致以状态区为准,发现不一致时以原文修正状态区

第三部分:治本的做法(面试官最想听这个):

  • 1. 减少需要压缩的量 :卸载大结果、任务拆分子 Agent、RAG 化历史—— 压缩是最后手段,不是首选方案 。
  • 2. 让「关键信息」不依赖摘要存活 :结构化状态区 + 引用机制。
  • 3. 压缩质量本身可评测 :构造「压缩后能否正确回答关键问题」的测试集(比如压缩后问「用户的三个硬约束是什么」), 把压缩做成可量化的环节 而不是凭感觉。
  • 4. 允许人看和改 :压缩产物在 UI 上可见可编辑(至少可查看),产品层面的兜底。

一句话总结:不丢关键内容靠「结构化压缩指令 + 不可压缩区 + 增量合并 + 原文可回溯 + 压缩后校验」五重保障;治本之道是「尽量别压缩」——卸载、隔离、RAG 化、结构化状态区,让需要压缩的内容本来就少且不重要。
