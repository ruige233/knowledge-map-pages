引言

二面的时候，聊到了 Agent 系统设计这一块。面试官就抛出来一个场景题：

"你的 Agent 去跑长任务，上下文超了，就要去做压缩。但是压缩之后呢，模型会漏掉一部分工具调用的记录，这样就会导致同一个操作被重复执行——这个问题你怎么去解决？"

我的第一反应是："加个缓存呗，把工具调用的结果给存起来，碰到重复调用就直接返回缓存。"

面试官听了摇了摇头："你这只是打了个补丁，不算设计。你有没有想过，它为什么会漏？漏掉的到底是什么？又该怎么从根上去让它不漏？"

我当时愣了一下。说实话，那会儿只想到"打补丁"这一层了，没有往架构设计上去深挖。面完之后，我把这道题彻底地捋了一遍。今天写下来，也算是给自己补的一课。

01为什么会漏

本节提炼
  • 压缩是有损处理，丢信息是必然代价而非 bug。
  • 漏因分三环：摘要生成丢细节、滑动窗口截断、注意力稀释。
  • 模型总结习惯保大意丢细节，粗线条描述替代关键参数。
  • 只答“加缓存”仅缓解注意力稀释的下游影响，未触及摘要与截断两个漏因。

压缩这个东西，本质上是有损处理。会漏东西不是 bug，它是设计上必然要付出的代价。但是漏在哪三个环节，这个值得拆开来看一看：

  • 1. 摘要生成阶段

大部分的压缩方案，是拿另外一次模型调用，把历史"总结"一下。如果说 prompt 里面没有明确去要求保留工具调用的细节，那么模型的总结习惯，就是保大意、丢细节。像是"查询了用户订单"这种粗线条的描述，就会替掉"调用了 query_order(order_id=8823)，返回已发货"这种关键信息。

  • 2. 滑动窗口截断

还有一种更粗暴的方案，就是直接砍掉最早的 N 轮对话。这种方式是整段整段地丢弃，不是浓缩。模型对被砍掉的那部分，完全没有印象。

  • 3. 长历史里的"注意力稀释"

就算技术上信息还留着，但是没有结构化的标记，混在很长的对话里面，模型在决策的时候，也未必能真正"注意到"它。

我当时只答了一个"加缓存"。其实缓存只是解决了第三个问题的下游影响，前面两个环节的漏因，根本就没有碰到。这就是面试官摇头的原因。

02状态与叙事分开

本节提炼
  • 对话历史是给人看的叙事，执行状态是给机器读的结构化数据，不能共用同一套压缩逻辑。
  • Action Ledger 记工具名、参数 hash、结果、时间戳、状态，独立于上下文、不参与压缩。
  • 幂等拦截用函数名加参数 hash 生成签名，命中缓存直接返回，未命中执行并记录。
  • 有副作用操作（发邮件/下单/扣款/写库）必须幂等兜底；只读操作重复执行主要浪费资源。

后来我想明白了一个关键点。对话历史，是给人看的叙事。Agent 的执行状态呢，应该是给机器读的结构化数据。这两者，不应该被同一套压缩逻辑去处理。

如果只在缓存这一层去打补丁，压缩逻辑该丢的还是照样丢。真正的解法，是从架构上把这两条线给分开。

1. 独立维护一份"已执行动作清单"(Action Ledger)

不要去指望压缩后的摘要，能扛得起"记住做过什么"这个责任。更稳妥的做法，是在对话上下文之外，单独去维护一份结构化的记录。这份记录通常包含：

  • ◆ 工具名称
  • ◆ 关键参数（或参数 hash）
  • ◆ 执行结果要点
  • ◆ 时间戳
  • ◆ 执行状态（成功/失败/进行中）

这份清单不参与压缩。每一轮决策之前，它都作为一个独立的片段注入进去。哪怕对话历史被压得只剩下几句话，这份清单依然还是完整的。这就相当于给 Agent 配了一本独立的"操作日志"，跟"聊天记录"是两本账，谁也不影响谁。

2. 工具调用的幂等性拦截（我当时说的"缓存"，其实该这么设计）

这一层是执行层面的兜底。就是说，即便模型真的因为记忆缺失，又发起了重复调用，也不让它造成实际的影响。

具体的做法，是给每一次调用去生成一个签名，也就是函数名加上参数的 hash。然后维护一个已执行签名的集合：

  • ◆ 命中缓存 → 直接返回结果，不重复执行；
  • ◆ 未命中 → 放行执行，执行完记录签名和结果。

这一层对有副作用的操作来说，是硬性需求。像是发邮件、下单、扣款、写库这些。不管上游的记忆管理出不出问题，下游都得有一个安全网。而对只读操作来说，像是查询、搜索，重复执行主要是浪费资源，加缓存更多是为了省时间和成本。

我当初的回答只到了这一步。而且"签名怎么设计"、"跟状态清单怎么配合"这些，都没有讲清楚。所以就显得比较单薄。

03压缩提示词保细节

本节提炼
  • 必须压缩时，摘要 prompt 明确要求保留每次调用的名称、关键参数与结果要点。
  • 模型总结很听指令，明确保留清单能大幅降低关键信息被抹掉概率。

如果确实要用摘要压缩的话，那生成摘要的 prompt 里面，就要明确地写清楚：

"请完整保留每一次工具调用的名称、关键参数和结果要点，不要笼统概括。"

而不是简单的一句"总结一下对话"就完了。模型的总结行为是很听指令的。你给它一份明确的"保留清单"，就能大幅减少关键信息在压缩里面被抹掉的概率。

04外部化存储按需检索

本节提炼
  • 完整记录存数据库/文件/向量库，需要时主动检索而非依赖上下文窗口。
  • 记忆容量天花板不再是上下文窗口大小，上下文只承载当前相关部分。

更彻底的方案，是不让模型去"记住"工具调用的历史，而是让它"查得到"。把完整的记录存到外部去，数据库、文件、向量库都可以。模型需要判断"我是不是做过这件事"的时候，就主动发起一次检索。而不是去依赖上下文窗口里还剩下多少信息。

这样一来，记忆容量的天花板，就不再是上下文窗口的大小了。记忆可以无限地增长，上下文只承载"当前相关"的那一小部分。

05分层滚动摘要

本节提炼
  • 滚动摘要逐段浓缩关键动作，再逐层聚合为高层摘要。
  • 渐进式压缩比一次性砍历史损失更小，关键事实保留概率更高。

长对话的场景，可以考虑"滚动摘要"。每隔一段，就把这一段的关键动作浓缩成几行。然后呢，再把多段小摘要逐层地聚合起来，变成更高层的摘要。相比"攒了很久一次性砍一刀"，这种渐进式的压缩，每一次损失的信息量更小。关键的事实被逐层保留下来的概率，也会更高。

06总结

本节提炼
  • 重答思路：根源是压缩丢工具调用细节，不能只在执行层打补丁。
  • 组合方案：独立动作清单加参数签名幂等拦截加提示词保细节加外部化检索。

如果要重新答一遍的话，大概会是这样：

"重复调用的根源，是压缩丢了工具调用的细节。所以不能只在执行层打补丁，得从架构上把 Agent 的执行状态和对话叙事分开去管理。具体来说，就是去维护一份独立的、不参与压缩的动作清单，把每一次调用的关键信息都记录下来。执行层再加一层基于参数签名的幂等拦截，给有副作用的操作兜个底。如果压缩是不可避免的，那就在摘要的 prompt 里面，明确地要求保留调用的细节，别让模型去笼统地概括。长期来看的话，可以把调用的历史外部化存储，按需去检索，而不是被动地依赖上下文。"
