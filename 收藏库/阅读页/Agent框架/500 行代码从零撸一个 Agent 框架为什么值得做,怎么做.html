前两篇讲了站队、讲了范式。这一篇不讲"选什么框架",讲**"你为什么要自己写一个"**。

01先造小轮子再选框架

本节提炼
  • 后端群里常见"选哪个框架"之争，作者认为这个问题问早了
  • 值得先花两三个周末手写500行最小框架，为回头读主流框架打底

先说个我在几个后端群里反复看到的场景。

有人问:"我要做 XX 场景的 Agent,LangChain / LangGraph / AutoGen / CrewAI / MetaGPT / AgentScope 选哪个?" 底下必然是一屏又一屏的推荐,各有拥趸,吵到最后也没个结论。

我的观点很粗暴:这个问题问早了。

对刚从后端切进 Agent 的工程师来说,在你选任何一个主流框架之前,值得先花两三个周末,自己撸一个 500 行左右的最小 Agent 框架——不是为了替代 LangChain,是为了当你回头再选 LangChain / LangGraph 时,你能看见每一层抽象在解决什么问题、又付出了什么代价。

这一篇讲三件事:

  • 1. 为什么值得造这个轮子 ——不是复读"深入理解",给你 4 个具体到能面试用的收益
  • 2. 500 行里到底该有什么 ——最小骨架的分层,以及每一层为什么长这样
  • 3. 动手时避免的三种"过度设计" ——这也是我读别人手写框架时最常见的坑

02为什么自己写一遍

本节提炼
  • 原书三条收益偏虚，作者换成四个面试可讲的硬收益
  • 能跑的Agent核心就是 while 循环加 tool_registry.execute()
  • 框架里真正的业务逻辑很多藏在 Prompt 里
  • 生产打点位置、trace_id、token 统计都要在写框架时想清

Hello-Agents 第 7 章一上来就问了这个问题,给的答案我很同意,但对后端工程师,我想再翻译一层。原书是这样写的:

构建自己的 Agent 框架,实际上是一个从"使用者"向"构建者"转变的过程。这种转变带来的价值是长远的。

  • • 深度理解 Agent 工作原理 :通过亲手实现每个组件,开发者能够真正理解 Agent 的思考过程、工具调用机制、以及各种设计模式的好坏与区别。
  • • 获得完全的控制权 :自建框架意味着对每一行代码都有完全的掌控,可以根据具体需求进行精确调优,而不受第三方框架设计理念的束缚。
  • • 培养系统设计能力 :框架构建过程涉及模块化设计、接口抽象、错误处理等软件工程核心技能……

—— 引自《Hello-Agents》第 7.1.1 节

上面这段话没错。但对已经写了几年后端的人来说,"培养系统设计能力"这种收益太虚。我想换成四个更硬、更能拿去面试讲的收益:

收益一:你能看见"抽象的成本"

LangChain 有几十个概念:Chain、Runnable、Agent、AgentExecutor、Tool、Toolkit、Memory、Retriever、OutputParser……每一个概念都在解决问题,但也每一个都在加抽象层。

如果你没自己写过,你会本能地以为这些抽象是"必须的"。而当你写过一遍之后你会发现:一个能跑的 Agent,核心逻辑就是一个 while 循环加一个 tool_registry.execute()——就是我们上一篇里 ReAct 那 20 行代码。

所有额外的抽象,都是在解决"如何让这 20 行代码支持更多花样"。理解这一点之后,你选框架的判断依据就变了:不是选"最强大的",是选"抽象层刚好覆盖你的场景、不多不少的"。这是一个后端工程师面对框架时该有的姿态。

收益二:你能看见"Prompt 和代码的边界在哪"

写完一遍你会发现一个反直觉的事实:Agent 框架里,真正的"业务逻辑"很多藏在 Prompt 里,而不是代码里。

比如 Hello-Agents 里 Reflection 那份 Prompt——"你是一位极其严格的代码评审专家,对代码的性能有极致的要求"——这句话不是文档,它是代码的一部分,它决定了整个反思循环能不能给出有价值的批评。

对后端工程师,这是一个心智模型的重塑:过去你写 if-else 决定行为,现在你写 Prompt 决定行为。这两种"控制流"要放在哪一层、如何版本管理、如何测试、如何 diff——你亲手写一遍框架,才能对这几个问题有肌肉记忆。

收益三:你能看见"生产级 Agent 应该在哪打点"

Hello-Agents 那 500 行代码,里面到处是 print("🤖 xxx 开始处理:")、print("🔧 检测到 N 个工具调用")、print("--- 第 N 步 ---")。这些不是给读者看的调试输出——这就是生产环境应该埋的观测点。

亲手写一遍,你就知道 span 应该埋在哪一层、trace_id 应该在哪一层生成、每一轮的 token 消耗要怎么统计。等到用 LangGraph 时,你能一眼看出它的 LangSmith 是在拦截什么——不是黑盒,而是"我知道它在哪一步截的胎"。

收益四:面试时你有硬东西可讲

这是最俗、但也是 2026 年最实用的一条。

我看过太多 Agent 相关简历,写的都是"熟悉 LangChain / LangGraph / Dify,能快速搭建 Agent 应用"。这类描述在面试官看来是中性偏负面的——没法区分你和另外 100 个投同样岗位的人。

但如果简历上写"从零实现了一个 500 行的最小 Agent 框架,支持 ReAct / Plan-and-Solve / Reflection 三种范式,内置工具注册和链式调用",面试官会立刻追问,而你已经想过每一个答案:

  • • "你的 tool_registry 是怎么设计的?" — 一个 Dict[str, Tool] 打底,name 做主键;支持"注册 Tool 对象"和"直接注册函数"两种入口(后者自动包一层适配);对外三个方法: register / get / format_for_prompt ——最后这个是给 Prompt 用的工具描述拼接
  • • "ReAct 循环里 max_steps 兜底逻辑放哪一层?" — 放在 Agent 的 run 主循环里,而不是工具层;触发之后不要直接抛异常或 return None ,而是把已有 history 塞给 LLM 让它做一次"最后一搏"回答(见上一篇 02 里那段)
  • • "为什么选择用字符串匹配来做 Finish 判断?" — 因为它简单、可 diff、可 grep、可测试;OpenAI 原生 function calling 是更"正规"的做法,但它把控制流藏进了 API 响应结构里,失去可读性——教学场景优先字符串协议,生产场景视对模型的信任度选择

这些追问,每一个都是你已经想过、能对答如流的。这就是"造过一次轮子"和"用过 10 个框架"在面试上的差距。

03500行的骨架分层

本节提炼
  • LLM层别发明新抽象，统一在OpenAI协议上，多供应商在其下做兼容
  • Agent基类只保留一个 run(input)->str 抽象方法，历史管理放基类
  • Tool层用注册表加"万物皆工具"，字符串协议与function calling二选一
  • OpenAI协议兼容转换有损：Claude/Gemini字段与function calling差异
  • 万物皆工具带来状态管理、类型安全、调度粒度三方面代价

好,决定要写了。写什么?

Hello-Agents 第 7 章给了一个非常克制的目录结构,我拿过来作为讨论的锚点:

  • hello-agents/
  • ├── hello_agents/
  • │ ├── core/ # 核心框架层
  • │ │ ├── agent.py # Agent 基类
  • │ │ ├── llm.py # HelloAgentsLLM 统一接口
  • │ │ ├── message.py # 消息系统
  • │ │ ├── config.py # 配置管理
  • │ │ └── exceptions.py # 异常体系
  • │ ├── agents/ # Agent 实现层
  • │ │ ├── simple_agent.py # SimpleAgent 实现
  • │ │ ├── react_agent.py # ReActAgent 实现
  • │ │ ├── reflection_agent.py # ReflectionAgent 实现
  • │ │ └── plan_solve_agent.py # PlanAndSolveAgent 实现
  • │ ├── tools/ # 工具系统层
  • │ │ ├── base.py # 工具基类
  • │ │ ├── registry.py # 工具注册机制
  • │ │ ├── chain.py # 工具链管理系统
  • │ │ ├── async_executor.py # 异步工具执行器
  • │ │ └── builtin/ # 内置工具集
  • │ │ ├── calculator.py # 计算工具
  • │ │ └── search.py # 搜索工具
  • └──

这个目录里,我认为最有代表性的三层是:LLM 客户端 / Agent 基类 / Tool 注册表。写好这三层,你就理解了 90% 主流框架在干什么。下面逐层拆。

2.1 LLM 层:统一在"OpenAI 协议"上

Hello-Agents 的第一个选择,我觉得是整章最重要的一个:不发明新接口,直接站在 OpenAI 协议上。原书讲得很直接:

OpenAI 的 API 已经成为了行业标准,几乎所有主流的 LLM 提供商都在努力兼容这套接口。HelloAgents 选择在这个标准之上构建,而不是重新发明一套抽象接口……当你掌握了 HelloAgents 的使用方法后,迁移到其他框架或将其集成到现有项目中时,底层的 API 调用逻辑是完全一致的。

—— 引自《Hello-Agents》第 7.1.2 节

对后端工程师来说,这个决定的含金量在于:你在给自己造一个可移植的抽象,而不是又发明一个 vendor lock-in。

对比一下:如果你自作聪明地定义了 MyLLM.ask() / MyLLM.chat() / MyLLM.generate_with_tools()——恭喜你,你写完这个框架的那一刻就已经和 LangChain 一样"过度抽象"了。第二天你想接一个新模型,就得重写 adapter。

第一条工程判断——不要发明新的 LLM 抽象,你的 HelloAgentsLLM.think(messages) 参数结构应该就是 OpenAI Chat Completions 的 messages 数组。所有的多供应商适配、本地模型(vLLM / Ollama)接入,都在"这个协议之下"做兼容,不在"这个协议之上"再叠一层。

Hello-Agents 后面 7.2.3 节的自动检测机制(优先级依次是"特定服务商环境变量 → base_url 域名/端口 → API 密钥格式")也值得抄——它把"选哪家供应商"从代码问题降级为环境变量问题,这对生产环境的多环境部署非常重要:同一份代码,在开发机上用本地 Ollama,在预发上用 ModelScope,在生产上用 OpenAI,你的应用层代码一行都不用改。

不过要诚实说一下这个决定的代价——它是有 tradeoff 的,不能装作没有:

  • • Anthropic Claude 的原生 API 里 system 是独立字段,不是 messages 数组里 role=system 的元素;硬统一到 OpenAI 协议, system 会被塞进 messages 里,某些边界行为(比如 system 长度限制)会和原生 API 不完全一致
  • • Gemini 的原生格式 用 contents 数组而不是 messages ,字段名是 parts 而不是 content ——落到 HelloAgents 这层是走了"OpenAI 兼容端点",而不是 Gemini 原生端点,某些多模态特性(如 inlineData )可能会丢
  • • Function calling 的字段 各家协议略有差异,比如 Anthropic 用 tool_use / tool_result ,OpenAI 用 tool_calls / tool role;统一在 OpenAI 协议上意味着 要靠各家自己的兼容端点做转换 ——转换有损、有 bug 可能性

结论:教学场景选 OpenAI 协议一统是对的,不然学习成本会爆炸;但生产上如果你的场景重度依赖 Anthropic 或 Gemini 的独有特性(比如 Anthropic 的 prompt caching、Gemini 的原生多模态),就该老老实实用原生 SDK,别指望"兼容层"能给你一切。

2.2 Agent 基类:一个抽象方法就够

Agent 基类要多复杂?看 Hello-Agents 的答案:

  • class Agent(ABC):
  • def__init__(self, name, llm, system_prompt=None, config=None):
  • self.name = name
  • self.llm = llm
  • self.system_prompt = system_prompt
  • self.config = config or Config()
  • self._history: list[Message] = []
  • @abstractmethod
  • defrun(self, input_text: str, **kwargs) -> str:
  • pass
  • defadd_message(self, message): self._history.append(message)
  • defclear_history(self): self._history.clear()
  • defget_history(self): returnself._history.copy()

—— 节选自《Hello-Agents》第 7.3.3 节

就这么点东西。唯一一个抽象方法就是 run(input_text) -> str。

这一层的取舍,是整个框架的性格所在。我给三个观点:

观点一:抽象方法只应该有一个。 你可以看到,ReAct 有 while 循环,Plan-and-Solve 有 plan+execute 两阶段,Reflection 有 execute-reflect-refine 三段。这三种范式内部形状差别很大,但对外都可以被 run(input) -> str 抹平。Agent 基类不需要预判"未来会有什么范式",只需要保证"任何范式都能塞进 run 里"。

观点二:历史管理放在基类里就够了。_history 是一个 list of Message,加、清、拷贝三个方法。别搞什么 ConversationBufferMemory / ConversationSummaryMemory 的多态——那些是后期长在这一层之上的可选组件,不是骨架。

观点三:异步暂时别做。 你会看到 Hello-Agents 里也没在 base Agent 里做 async run。同步 run 能覆盖 95% 的使用场景,而异步会让整个调用链的写法完全变形。等你真的需要并发(比如同时处理多用户请求)时,在服务层做异步,而不是在 Agent 内部做异步。这是后端工程师老生常谈的原则:异步的边界越往外推越好。

2.3 Tool 层:注册表 + "万物皆工具"

Hello-Agents 在这一层做了一个大胆但极其正确的简化,原书叫"万物皆为工具":

为了彻底贯彻轻量级与教学友好的理念,HelloAgents 在架构上做出了一个关键的简化:除了核心的 Agent 类,一切皆为 Tools。在许多其他框架中需要独立学习的 Memory(记忆)、RAG(检索增强生成)、RL(强化学习)、MCP(协议)等模块,在 HelloAgents 中都被统一抽象为一种"工具"。

—— 引自《Hello-Agents》第 7.1.2 节

这一条我要重点标出来——"万物皆工具"这个决定,决定了你的框架 500 行能收得住。

想想 LangChain 有多少个平级概念:Tool、Retriever、Memory、Callback、OutputParser、Runnable……每一个都是一等公民,每一个都有自己的基类、生命周期、抽象方法。这就是为什么它的代码量以 10 万行计。

而 Hello-Agents 说:记忆是工具,RAG 是工具,MCP 客户端也是工具。它们的入口都是 tool.run(parameters: dict) -> str。这在设计上很暴力,但对 500 行框架完全够用。

Tool 基类——两个抽象方法(run + get_parameters)加一个 name / description。就这么多。

ToolRegistry——一个 dict,加、查、执行、format 描述给 Prompt 用。就这么多。

我把 Hello-Agents 里工具调用的 Prompt 格式约定摘一下,这是整个 Tool 层的"总线协议":

当需要使用工具时,请使用以下格式:

[TOOL_CALL:{tool_name}:{parameters}]

例如:[TOOL_CALL:search:Python编程] 或 [TOOL_CALL:memory:recall=用户信息]

—— 引自《Hello-Agents》第 7.4.1 节

你可以用这套字符串协议,也可以用 OpenAI 原生的 function calling(Hello-Agents 在 7.4.5 节的 FunctionCallAgent 里给了做法)。两种选一种,不要两种都做——这一层的复杂度是 500 行框架的头号敌人。

不过"万物皆工具"这个决定,同样有它的代价——不写清楚,读者上生产会翻车:

  • • 状态问题 :工具语义上是"无状态的请求-响应",但记忆(Memory)天生是 有状态 的——它需要持久化、需要读写并发控制、需要 TTL 管理。把 Memory 硬做成 tool,意味着这些状态管理要么放在 tool 内部(每个 tool 自己实现一份,重复)、要么就得在 registry 层再叠一个 lifecycle hook(把这层复杂度拱回来了)
  • • 类型安全丢失 :全部字符串协议意味着 参数类型全部靠 JSON schema 或 Prompt 描述来兜 ;RAG 检索的 top_k 是整数、Memory 的 timestamp 是时间戳、工具执行的 timeout 是浮点数——这些原本可以靠 Python 类型系统兜住的东西,现在全靠 LLM 输出乖一点
  • • 调度粒度粗 :每次 tool 调用都要过一遍 LLM 的决策(该不该调、传什么参数),这在 Memory / RAG 这种"应该由框架直接决定何时调用"的场景里是 浪费的 ——生产级框架里通常会把 Memory 和 RAG 从 tool 里"提出来",做成 pipeline 的固定环节

所以"万物皆工具"是教学阶段的极简策略,不是生产架构。等你的框架长到需要 Memory / RAG 稳定接入时,就该考虑给记忆和检索单独开一层——但那已经是第二次迭代的事了,不影响你先把 500 行搭起来。

04三种过度设计

本节提炼
  • 造轮子阶段一切追求"看得见"，同步单线程阻塞即可
  • 多Agent、记忆、上下文工程都是单Agent骨架之后的可选组件
  • "够用的抽象"优于"正确的抽象"
  • 坑一：在500行里做流式+异步+分布式
  • 坑二：提前抽象多Agent协作
  • 坑三：过早追求正确的抽象

前面讲怎么写。这一节讲别怎么写——这些是我自己写第一版时踩过、以及我读别人写的手写框架时最常见的坑。

坑一:在 500 行里做"流式 + 异步 + 分布式"

我看过一个朋友的第一版手写 Agent 框架,一上来就是 async def run,里面还嵌套了一个 AsyncGenerator 做流式返回,再外面套了个 Celery 任务分发。

我劝他:这三件事(流式、异步、分布式)在造轮子阶段一件都别做。

理由很简单:这三件事都是在"能跑起来"之后的优化。你现在的目标是搞懂 Agent 循环,不是搞一个高可用系统。同步、单线程、阻塞的 500 行代码,才能让你把每一轮里发生了什么看得清清楚楚。等你真需要流式,再在 LLM 客户端加一个 stream_think;等你真需要异步,再在服务层裹一层 FastAPI 的 BackgroundTasks。

造轮子阶段的第一原则:一切追求"看得见"。看得见每一次 LLM 调用、看得见每一次工具执行、看得见每一次状态转移。async 和流式都是"让人看不见"的技术,和造轮子的目的相反。

坑二:提前抽象"多 Agent 协作"

第二个常见坑:一上来就想做多 Agent(A2A、MCP、CrewAI 那套)。

我理解这个冲动——"AI 未来一定是多 Agent 协作嘛"。但在 500 行的框架里塞多 Agent,会导致你把大部分脑力花在"Agent 之间怎么通信"上,而真正核心的"单 Agent 循环"反而写得潦草。

Hello-Agents 的做法值得学:第 7 章就是单 Agent,多 Agent 通信协议(MCP、A2A、ANP)全部放到第 10 章——先把单体的骨架搭结实,后面加通信协议是水到渠成的事情。

同样的道理:记忆系统(第 8 章)、上下文工程(第 9 章)也都是在单 Agent 骨架长好之后再加的可选组件。你的 500 行框架里,记忆就是那个 self._history: list[Message]。够了。

坑三:过早追求"正确的抽象"

最后一个坑,是很多有洁癖的后端工程师会掉的:过早追求"正确的抽象"。

具体表现是:写到一半开始纠结"Tool 和 Function 是不是应该有共同基类"、"Message 是不是应该分 Turn 和 Event 两种"、"ToolRegistry 是不是应该继承一个通用的 Registry 泛型"……

停。这些纠结在 500 行里都是负价值。

一个我常用的自我提醒:造轮子阶段,"够用的抽象"永远优于"正确的抽象"。因为你根本还没有足够的用例,来判断哪种抽象是"正确"的——正确的抽象只可能从大量的实际使用中长出来,不可能在动笔前想出来。

Hello-Agents 在这方面的克制值得学:它的 Message 类就四个字段(content / role / timestamp / metadata);它的 Config 也就那么几个默认值加一个 from_env;它的 ToolRegistry 甚至同时支持"注册 Tool 对象"和"直接注册函数"两种方式——看起来不够优雅,但恰好够用。

05回看 LangChain

本节提炼
  • 回看LangChain：Runnable、AgentExecutor等对应手写代码
  • AgentExecutor的复杂参数是手写时踩过的坑的名字
  • 从使用者变成建造者，不再仰视框架

假设你按上面的路线走完了 500 行的最小框架——现在有意思的事情发生了。

回过头去看 LangChain 的源码,你会开始有"翻译"能力:

  • • 看到 Runnable ,你知道那是把 run(x) -> y 泛化成了"任何可组合的函数"
  • • 看到 RunnableParallel ,你知道那是造了一个"并发执行多个工具"的容器——就是 Hello-Agents 里 AsyncToolExecutor 的那一层
  • • 看到 AgentExecutor ,你知道那是把 ReActAgent 的 while 循环封装成了可配置的 driver
  • • 看到 OutputParser ,你知道那是把上一篇 ReAct 里那个 _parse_output 独立出来的一个可注册组件
  • • 看到 CallbackHandler ,你知道那是把 Hello-Agents 里那些 print 语句抽象成了事件监听器

每一个 LangChain 的复杂抽象,你都能对应回你手写的那 500 行里的某一段。

一个具体的"顿悟时刻"

让我给你举一个我在读源码时印象最深的例子——LangChain 的 AgentExecutor 到底为什么长得那么复杂。

如果你只用 LangChain,你大概只会写:

  • executor = AgentExecutor.from_agent_and_tools(agent=agent, tools=tools, verbose=True)
  • result = executor.invoke({"input": "..."})

看起来轻飘飘一行。但你打开 AgentExecutor 的源码,会发现光是主循环就有几百行,里面到处是各种 handle_parsing_errors、max_iterations、early_stopping_method、return_intermediate_steps、trim_intermediate_steps、intermediate_steps 到底存在哪儿……

没写过 500 行的时候,这些参数看起来是"高级功能"、"最佳实践"、"专业选项",让人一边使用一边心虚。

写过 500 行之后再看,每一个参数你都秒懂:

  • • handle_parsing_errors — 就是我们上一篇里那个"LLM 输出格式错了,把错误塞回去当 Observation"的开关
  • • max_iterations — 就是 while current_step < self.max_steps
  • • early_stopping_method — 就是达到 max_steps 之后"直接 return / force finish 一次"的策略选择
  • • return_intermediate_steps — 就是"要不要把 history 一起返回给调用方"
  • • trim_intermediate_steps — 就是"history 太长的时候怎么截"

每一个参数对应你写 500 行时踩过的一个坑。这一刻你会有一种奇怪的复合情绪:一半是"原来他们和我踩过一样的坑",另一半是"原来我踩的这些坑都是有名字的"。这就是"从使用者变成建造者"的心理转变——你不再仰视框架,你把它看成"另一个自己写的东西,只是他们比我早了几年"。

这种转变的价值,比会用任何一个框架都大得多。

这也是 Hello-Agents 第 7 章为什么值得给后端工程师推荐——它不是要你放弃 LangChain,而是要你带着"读得懂 LangChain"的能力,去用 LangChain。这一步,靠读文档不行,靠看视频不行,只能靠自己在 IDE 里把那 500 行一行一行敲出来。
