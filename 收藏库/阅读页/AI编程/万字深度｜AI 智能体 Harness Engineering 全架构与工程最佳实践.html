引言

摘要：2026年初，一个新的工程学科从AI开发实践中浮现——Harness Engineering（线束工程）。它不是关于提示词，也不只是关于上下文管理，而是关于如何构建完整的控制系统、约束机制和反馈环路，使AI Agent能够在生产环境中可靠、持续、安全地运行。本文综合 Anthropic、OpenAI、Martin Fowler（Thoughtworks）、Mitchell Hashimoto 等权威来源，系统梳理 Harness Engineering 的起源、核心概念、架构组件、最佳实践与未来方向，是目前中文领域最完整的 Harness Engineering 技术架构文档之一。

01概念起源与历史背景

本节提炼
  • Prompt→Context→Harness三次范式演进，Harness面向全系统环境设计
  • 2026年2月Hashimoto首用术语，OpenAI与Thoughtworks将其系统化

1.1 三次工程范式演进

要理解 Harness Engineering，必须首先了解 AI 工程的三次范式演进：

  • ┌─────────────────────────────────────────────────────────────────┐
  • │ AI 工程范式演进时间线 │
  • ├──────────────────┬──────────────────┬───────────────────────────┤
  • │ Prompt Eng. │ Context Eng. │ Harness Eng. │
  • │ 2022 ~ 2024 │ 2025 │ 2026 → │
  • ├──────────────────┼──────────────────┼───────────────────────────┤
  • │ 单轮交互优化 │ 跨多轮上下文管理 │ 全系统环境设计 │
  • │ 提示词结构设计 │ RAG / MCP / 记忆 │ 约束 + 反馈 + 生命周期 │
  • │ 一次对话，一个答案 │ 动态上下文窗口 │ 跨会话持久运行 │
  • └──────────────────┴──────────────────┴───────────────────────────┘

第一阶段：Prompt Engineering（2022–2024）

提示词工程是 LLM 应用的第一个里程碑。工程师学会了通过精心设计的提示词来引导模型输出——使用零样本（zero-shot）、少样本（few-shot）、思维链（chain-of-thought）等技术。这个阶段以"一问一答"为核心交互模式，核心挑战是让模型在单轮对话中给出准确的回答。

第二阶段：Context Engineering（2025）

随着 AI Agent 开始承担更复杂的任务，单轮提示词远远不够。Andrej Karpathy 在2025年12月的论述让"上下文工程"这一概念得到广泛传播：模型需要看到什么文档、对话历史、工具定义和 RAG 结果，才能做出明智的决策？上下文工程是关于"把正确的文件附到邮件里"——动态构建上下文窗口，供给模型所需信息。

第三阶段：Harness Engineering（2026）

2026年初，业界发现上下文工程仍然不够：即使给了模型正确的信息，Agent 依然会漂移、积累"熵"（技术债务和不一致性），在长任务中失败。这催生了一个更高层次的抽象——不只是管理模型看到什么，而是设计整个工作环境，包括约束机制、反馈循环、生命周期管理和验证系统。这就是 Harness Engineering。

1.2 关键历史事件

2025年8月：OpenAI 的一个工程团队在一个空仓库中提交了第一个 commit，随后坚守"零人工代码"的约束，开始用 Codex Agent 构建产品。

2025年11月：Anthropic 发布工程博客《Effective harnesses for long-running agents》，系统阐述了长周期 Agent 的 Harness 设计原则，包括初始化 Agent（Initializer Agent）和编码 Agent（Coding Agent）的双阶段架构。

2025年12月：随着 Karpathy 谈到工作流从"以人工为主、Agent 辅助"向"以 Agent 为主、人工修订"的倒置，业界开始广泛讨论 Agent 可靠性问题。

2026年2月5日：Mitchell Hashimoto（HashiCorp 联合创始人、Terraform 和 Ghostty 创造者）在其博客文章《My AI Adoption Journey》中首次系统使用"Harness Engineering"这一术语，并提出核心原则：

"每当 Agent 犯了一个错误，就花时间工程化一个解决方案，使 Agent 永远不会再犯同样的错误。"

2026年2月11日：OpenAI 发布《Harness engineering: leveraging Codex in an agent-first world》，公开描述了他们构建百万行代码产品的全过程，正式将 Harness Engineering 推向工程主流。

2026年2月17日：Thoughtworks 杰出工程师 Birgitta Böckeler 在 martinfowler.com 发表分析文章，开始系统化 Harness Engineering 的理论框架。

2026年4月2日：Birgitta Böckeler 发布完整版《Harness engineering for coding agent users》，引入"前馈/反馈"控制论框架、"计算型/推理型"二分法，以及三大 Harness 调控类别（可维护性、架构适应性、行为），成为该领域目前最权威的理论框架。

02核心定义

本节提炼
  • 四大职能：约束、告知、验证、纠正；公式Agent=Model+Harness
  • 提示词是概率性合规，Harness提供确定性约束（如pre-commit hook）
  • 依赖提示词的概率性合规，长会话中指令会被遗忘

2.1 定义

根据多个权威来源的综合定义：

Harness Engineering 是设计和实现一套系统的工程学科，该系统：

  • 1. 约束（Constrain） AI Agent 的行为——定义架构边界、依赖规则、访问权限
  • 2. 告知（Inform） AI Agent 应该做什么——上下文工程、文档、规范
  • 3. 验证（Verify） AI Agent 是否正确完成任务——测试、代码检查、CI 验证
  • 4. 纠正（Correct） AI Agent 出错时的行为——反馈循环、自我修复机制

LangChain 给出了最简洁的公式：

  • Agent = Model + Harness

Mitchell Hashimoto 的定义：

"Harness 是一组约束、工具、文档和反馈环路，使 Agent 保持高效和正轨。"

Martin Fowler 对其定义的延伸：

"Harness 是我们可以用来使 AI Agent 保持受控的工具和实践的集合。"

学术论文（preprints.org，2026年3月）给出了更精确的形式化定义：

"Harness 是将持久化控制制品（durable control artifacts）、中介行动接口（mediated action interfaces）和运行时策略（runtime policies）耦合成一个受治理执行机制（governed execution regime）的超模型系统。"

2.2 Harness 的本质：为什么不能只靠提示词

下面的例子说明了为什么提示词无法替代 Harness：

  • 问题场景：你在 CLAUDE.md 里写了"运行 linter"
  • 在一个长调试会话的第47次迭代中，大部分上下文窗口已被消耗，
  • 这条指令会被忘记。
  • → 提示词方案：依赖概率性合规（probabilistic compliance）
  • → Harness 方案：pre-commit hook 强制在每次提交前运行 linter，
  • 这是确定性约束（deterministic constraint）

换句话说，Harness Engineering 解决的是"提示词无法结构性阻止的问题"。Agent 常见的失败模式：

失败模式提示词能否解决Harness 解决方案
跨模块边界写导入语句否（会忘记）自定义 linter 强制检查依赖方向
将三个月前的 memo 当作当前规范否版本化文档 + 鲜度校验 sensor
编辑 .eslintrc 关闭规则而非修复代码否CI 门控阻止此类提交
未实际运行端到端测试就宣告完成否（难以持续执行）验证循环强制端到端测试

2.3 "线束"隐喻的含义

"Harness"（线束）这个词来自马具——缰绳、马鞍、嚼子——驾驭一匹强壮但方向感不稳定的马所需的完整装备。这个比喻是刻意的：

  • ┌─────────────────────────────────────────────┐
  • │ 🐎 马 = AI 模型（强大但需要引导） │
  • │ 🎠 线束 = Harness 系统（约束 + 引导） │
  • │ 🏇 骑手 = 人类工程师（提供方向，不做奔跑） │
  • └─────────────────────────────────────────────┘

没有 Harness，AI Agent 就像一匹在开阔田野里的纯血马——速度令人印象深刻，但对于完成任何实际任务完全无用。

03三层工程定位

本节提炼
  • Prompt优化单次交互，Context管理单窗口信息，Harness设计跨会话完整环境
  • Harness引入上下文重置、结构化交接制品与阶段门控

理解三者关系是掌握 Harness Engineering 的前提：

  • ┌─────────────────────────────────────────────────────────────────────────┐
  • │ 三层工程的作用域 │
  • │ │
  • │ Prompt Engineering │
  • │ ┌───────────────────────────────────────────────────────────────────┐ │
  • │ │ 单次交互的指令优化 │ │
  • │ │ "把这封邮件写成正式风格" │ │
  • │ └───────────────────────────────────────────────────────────────────┘ │
  • │ │
  • │ Context Engineering（包含 Prompt Engineering） │
  • │ ┌───────────────────────────────────────────────────────────────────┐ │
  • │ │ 一个上下文窗口内的信息管理 │ │
  • │ │ RAG、MCP 工具调用、对话历史、文档注入 │ │
  • │ │ "把正确的文件附到邮件里" │ │
  • │ └───────────────────────────────────────────────────────────────────┘ │
  • │ │
  • │ Harness Engineering（包含以上两者，并扩展到系统层面） │
  • │ ┌───────────────────────────────────────────────────────────────────┐ │
  • │ │ 多会话、多 Agent、跨上下文窗口的完整环境设计 │ │
  • │ │ 约束、验证、状态持久化、错误恢复、生命周期管理 │ │
  • │ │ "设计整个办公室，而非只是写邮件和附件" │ │
  • │ └───────────────────────────────────────────────────────────────────┘ │
  • └─────────────────────────────────────────────────────────────────────────┘

一句话区分：

  • • 上下文工程 ：确保模型看到正确的数据库 schema
  • • Harness 工程 ：确保模型在看到 schema 之后，仍然必须运行 linter、通过测试、遵守权限，并保存进度以便下次不会忘记目标

正如 Louis Bouchard 的总结：

"一个是模型看到什么，另一个是系统如何运作。"

Harness Engineering 还引入了上下文工程所没有的概念：上下文重置（context resets）、结构化交接制品（structured handoff artifacts）和阶段门控（phase gates）——这些使得跨多个上下文窗口的连贯、目标导向工作成为可能。

本节提炼
  • 三层同心圆：AI模型、构建者Harness、用户Harness
  • 外层用户Harness目标是提高首次做对概率并提供自纠反馈环路

Birgitta Böckeler 在 martinfowler.com 上提出的同心圆模型是目前最清晰的 Harness 架构框架：

  • ┌─────────────────────────────────────────────────────────┐
  • │ │
  • │ ┌─────────────────────────────────────────────────┐ │
  • │ │ 外层：编码 Agent 用户 Harness（User Harness） │ │
  • │ │ ┌─────────────────────────────────────────┐ │ │
  • │ │ │ 内层：编码 Agent 构建者 Harness │ │ │
  • │ │ │ ┌─────────────────────────────────┐ │ │ │
  • │ │ │ │ 核心：AI 模型（被线束约束的对象） │ │ │ │
  • │ │ │ │ (Claude、GPT-5、Gemini...) │ │ │ │
  • │ │ │ └─────────────────────────────────┘ │ │ │
  • │ │ │ 系统提示、内置工具、上下文管理 │ │ │
  • │ │ └─────────────────────────────────────────┘ │ │
  • │ │ AGENTS.md、自定义 linters、结构测试 │ │
  • │ │ 外部工具集成、项目专属约束 │ │
  • │ └─────────────────────────────────────────────────┘ │
  • │ │
  • └─────────────────────────────────────────────────────────┘

第一层（核心）：AI 模型

模型本身——Claude、GPT-5 等——是被线束约束的对象。模型提供推理能力，但不知道方向。

第二层（构建者 Harness）

编码 Agent 平台（如 Claude Code、Codex）的构建者已经内置了部分 Harness：系统提示、工具访问权限、内置的上下文管理（如 compaction 机制）、基础安全过滤器。这一层对用户部分透明、部分可配置。

第三层（用户 Harness）

这是工程团队自己构建的外层 Harness，针对具体项目和业务场景定制：AGENTS.md 文件、自定义 linter、架构约束规则、外部工具集成（通过 MCP）、验证脚本等。

一个构建良好的外层 Harness 有两个目标：

  • 1. 增加 Agent 第一次就做对的概率
  • 2. 提供自我纠正的反馈环路，在问题到达人类眼前之前就被解决

05前馈与反馈

本节提炼
  • 前馈在行动前引导，反馈在行动后检测并附修复指令
  • 前馈+反馈组合才能增量改进并自我纠正
  • 仅前馈规则会失效，仅反馈则反复犯同样错误、低效

Harness Engineering 借鉴了控制论（Cybernetics）的框架，将控制机制分为两类：

5.1 前馈控制（Feedforward / Guides）

前馈控制在 Agent 行动之前介入，旨在引导 Agent 的初始行为，增加其第一次就做对的概率。

  • 前馈控制（Guides）
  • ┌────────────────────────────────────────────────────────┐
  • │ AI Agent │
  • │ 读取 AGENTS.md → 加载规范文档 → 执行任务 │
  • └────────────────────────────────────────────────────────┘
  • 输出结果

前馈控制的例子：

  • • AGENTS.md / CLAUDE.md ：项目约定、目录结构、测试命令、架构规则
  • • 架构文档（feedforward） ：领域文档、包分层图、API 契约
  • • How-to 指南（Skills） ：如何启动开发服务器、如何运行特定类型的测试
  • • 代码模组（Codemods） ：提供给 Agent 的自动化代码转换工具
  • • 语言服务器（LSP） ：提供实时类型检查和代码智能

前馈控制增加了 Agent 第一次就做对的概率，但单独依靠前馈（只有规则，没有反馈）会导致 Agent 反复犯同样的错误。

5.2 反馈控制（Feedback / Sensors）

反馈控制在 Agent 行动之后介入，检测问题并允许 Agent 自我纠正。

  • AI Agent 行动
  • ┌───────────────────────┐
  • │ 反馈传感器（Sensors）│
  • │ Linters / 测试 / CI │
  • └───────────────────────┘
  • ┌──────────────┴──────────────┐
  • ▼ ▼
  • 通过：继续 失败：反馈给 Agent
  • （附带修复指令）
  • Agent 自我纠正

反馈控制的关键特性——为 LLM 消费优化的信号：高质量的反馈控制不只是报错，而是提供结构化的、包含修复指令的错误消息。例如，自定义 linter 的错误消息可以直接注入"如何修复此问题"的说明，形成正向的提示注入。

反馈控制的例子：

  • • Pre-commit hook ：每次提交前自动运行 linter
  • • 结构测试（Structural tests） ：检查模块边界违规（如 ArchUnit）
  • • 自动化测试套件 ：单元测试、集成测试
  • • Review Agent ：AI 代码审查员，在 Agent 自我检查之后
  • • 浏览器自动化（Puppeteer MCP） ：端到端功能验证
  • • CI/CD 门控 ：代码合并前的自动化验证

5.3 组合使用的必要性

  • 仅有前馈 → Agent 编码规则但从不知道是否奏效 → 规则逐渐失效
  • 仅有反馈 → Agent 反复犯同样的错误，每次靠反馈纠正 → 低效
  • 前馈 + 反馈 → 增量改进 + 自我纠正 → 可持续的高质量输出

06计算型vs推理型

本节提炼
  • 计算型确定性廉价，推理型概率性昂贵、需语义判断
  • 计算型打底，推理型选择性用于最需要场合

Martin Fowler 框架中另一个核心二分法：

  • ┌─────────────────────────────────────────────────────────────────┐
  • │ 两种控制执行类型 │
  • ├─────────────────────────────────────────────────────────────────┤
  • │ 计算型（Computational） │ 推理型（Inferential） │
  • ├───────────────────────────────────┼─────────────────────────────┤
  • │ CPU 执行，确定性 │ GPU/NPU 执行，概率性 │
  • │ 毫秒到秒级 │ 较慢，成本较高 │
  • │ 结果可靠 │ 结果非确定性 │
  • │ 测试、linters、类型检查器 │ AI 代码审查、"LLM as judge" │
  • │ 每次变更都可运行 │ 用于需要语义判断的场景 │
  • │ 不需要 GPU │ 需要强模型支持 │
  • └─────────────────────────────────────────────────────────────────┘

具体的控制矩阵（结合方向和类型）：

控制内容方向类型实现示例
代码规范前馈推理型AGENTS.md、Skills
项目脚手架指南前馈两者结合带指令的 Skill + bootstrap 脚本
代码模组（Codemod）前馈计算型OpenRewrite recipes 工具
模块边界检查反馈计算型ArchUnit 结构测试（pre-commit hook）
代码审查指南反馈推理型Skills / 审查 Agent
静态分析反馈计算型ESLint、semgrep、dep-cruiser
测试覆盖率反馈计算型npm run coverage
浏览器端到端测试反馈两者结合Puppeteer MCP + AI 判断

核心原则：计算型传感器廉价、快速、可靠，应作为 Harness 的基础。推理型传感器提供更丰富的语义判断能力，但成本高、非确定性，应选择性使用在最需要的场合。

07三大调控类别

本节提炼
  • 三类：可维护性、架构适应性、行为，行为Harness最复杂最薄弱
  • 连续漂移检测与运行时反馈（SLO退化、日志异常）
  • 问题误诊、误解指令、功能膨胀等语义问题仍需人工监督

Birgitta Böckeler 建议将 Harness 按调控目标分为三类：

7.1 可维护性 Harness（Maintainability Harness）

目标：调控代码的内部质量和长期可维护性。

这是目前最成熟的 Harness 类型，因为可以利用大量现有工具。它能够可靠捕获的问题：

计算型传感器可靠检测的问题：

  • • 重复代码（Duplicate code）
  • • 圈复杂度过高（Cyclomatic complexity）
  • • 测试覆盖率不足
  • • 架构漂移（Architectural drift）
  • • 代码风格违规

推理型传感器可部分检测的问题（概率性，非每次提交都能捕获）：

  • • 语义重复代码
  • • 冗余测试
  • • 暴力修复（Brute-force fixes）
  • • 过度工程化

无论计算型还是推理型都难以可靠捕获的问题（仍需人工监督）：

  • • 问题误诊
  • • 误解指令
  • • 不必要的功能膨胀

7.2 架构适应性 Harness（Architecture Fitness Harness）

目标：定义和检查应用的架构特征。这本质上是"架构适应性函数"（Architectural Fitness Functions，Thoughtworks 技术雷达概念）的 Agent 化实现。

例子：

  • • 前馈 ：通过 Skills 传递性能需求和编码规范（如日志标准）
  • • 反馈 ：性能测试、日志质量检查，将结果反馈给 Agent

架构适应性 Harness 还包括连续漂移检测（Continuous Drift Detection）：

  • • 死代码检测（ /find-dead-code ）
  • • 测试覆盖质量分析（ /code-coverage-quality ）
  • • 依赖扫描（Dependabot）

以及运行时反馈：

  • • SLO 退化检测 → 触发编码 Agent 改进建议
  • • 响应质量采样（ /response-quality-sampling ）
  • • 日志异常检测（ /log-anomalies AI judge）

7.3 行为 Harness（Behaviour Harness）

目标：验证应用是否在功能上正确工作。这是三类中最复杂的，也是目前工程实践中最薄弱的环节。

行为 Harness 的核心挑战：

  • • 功能正确性的判断标准通常比架构规则模糊得多
  • • 端到端测试的维护成本高
  • • AI Agent 有宣称功能完成但实际未完成的倾向

Anthropic 的研究发现：模型无法可靠地评估自己的工作。解决方案是 GAN 风格的验证架构：

  • ┌─────────────────┐ 生成代码 ┌──────────────────┐
  • │ Generator Agent │ ─────────────── → │ Evaluator Agent │
  • │ （编码 Agent） │ │ （验证 Agent） │
  • │ │ ← ─────────────── │ │
  • └─────────────────┘ 反馈/批改 └──────────────────┘

Anthropic 的长周期 Agent 方案使用浏览器自动化（Puppeteer MCP）作为行为反馈传感器，强制要求 Agent 像真实用户一样进行端到端测试，而非只跑单元测试或 curl 命令。

08可线束性

本节提炼
  • 强类型、清晰模块边界、稳定结构提高可线束性
  • 绿地项目第一天设计，遗留项目只对新模块渐进装配
  • 弱类型、泥球架构、循环依赖、隐式约定降低可线束性

并非所有代码库都同样适合 Harness 化。Thoughtworks 工程师 Ned Letcher 提出了"环境可供性（Ambient Affordances）"概念：

"环境本身的结构属性，使其对 Agent 更易读、易导航和易操控。"

8.1 高可线束性代码库的特征

  • 高可线束性
  • │ 强类型语言（内置类型检查作为传感器）
  • │ 清晰的模块边界（可定义架构约束规则）
  • │ 成熟框架（Spring 等抽象掉 Agent 无需关心的细节）
  • │ 稳定的数据结构（减少跨会话变更的认知负担）
  • │ 模块化的依赖图（避免循环依赖）
  • 低可线束性
  • │ 弱类型/动态语言（缺少确定性类型检查）
  • │ 单体泥球架构（无法定义边界规则）
  • │ 遗留代码库（非标准化、高熵）
  • │ 循环依赖图
  • │ 隐式约定多于显式规则

8.2 绿地项目 vs 遗留项目

绿地项目的优势：可以从第一天起就将可线束性设计进去——技术栈选择和架构决策决定了代码库将来的可治理程度。这意味着：

  • • 选择强类型语言（TypeScript、Go、Rust、Java/Kotlin）
  • • 从一开始就定义和执行模块边界
  • • 使用约定大于配置的框架
  • • 将架构决策记录（ADR）版本化到代码库中

遗留项目的挑战：是否值得为老代码库装配 Harness？与在从未运行过静态分析的代码库上引入静态分析工具类似——会被海量告警淹没。AI 可以帮助更快地完成这个工作，但往往不值得花费气力。更实际的策略：

  • • 仅对新模块应用完整 Harness
  • • 对旧代码库使用更宽松的规则，逐步收紧
  • • 优先 Harness 化变更最频繁的部分

8.3 技术栈收敛效应

Harness Engineering 可能推动工程界向更少的技术栈和代码库拓扑收敛。原因：

  • • 开发者的个人口味在 Agent 辅助编码中影响降低
  • • 工具和框架的易用性对 AI 同样重要（好的人机工效 = 好的 AI 友好性）
  • • 有现成 Harness 模板的技术栈将获得明显优势
  • • Harness 覆盖的特定架构模式将成为新的抽象层

09长周期Agent设计

本节提炼
  • 双Agent：初始化Agent生成功能清单与脚手架，编码Agent逐功能增量提交
  • 跨会话记忆靠git log、progress文件与feature_list.json恢复
  • 一次性完成耗尽上下文、过早宣告完成两类失败模式

Anthropic 在2025年11月的工程博客中详细阐述了长周期 Agent 的核心挑战和解决方案，这是目前最系统化的官方技术实践文档之一。

9.1 核心挑战：跨会话的记忆鸿沟

  • 会话 1 会话 2 会话 3
  • ┌──────────┐ ┌──────────┐ ┌──────────┐
  • │ Agent A │ │ Agent B │ │ Agent C │
  • │ │ 断裂 │ │ 断裂 │ │
  • │ 上下文A │ ──×── │ 上下文B │ ──×── │ 上下文C │
  • │ （忘记） │ │ （忘记） │ │ （忘记） │
  • └──────────┘ └──────────┘ └──────────┘
  • 就像一个由倒班工程师组成的项目团队，
  • 每位新工程师到岗时对之前发生的事情毫无记忆。

Claude Agent SDK 具备 compaction（上下文压缩）机制，可以让 Agent 在不耗尽上下文窗口的情况下持续工作。但仅有 compaction 是不够的：从一个高层提示（如"构建一个 claude.ai 克隆"）开始，即使是 Opus 4.5 级别的模型也会在多会话中频繁失败。

9.2 两类典型失败模式

失败模式一："一次性完成"（One-shotting）

Agent 试图在单次会话中完成所有功能，导致在实现中途耗尽上下文，下一个会话需要猜测已发生的事情并花费大量时间修复破损状态。

失败模式二："过早宣告完成"（Premature Victory）

在一些功能已经构建之后，后续的 Agent 实例环顾四周，看到进度已经完成，宣布任务完成——即使仍有大量未完成的功能。

9.3 双 Agent 架构解决方案

Anthropic 设计了一个两阶段 Harness 架构：

  • ┌─────────────────────────────────────────────────────────────────┐
  • │ 长周期 Agent Harness 架构 │
  • │ │
  • │ ┌─────────────────────────────────────────────────────────┐ │
  • │ │ 第一个上下文窗口：初始化 Agent（Initializer Agent） │ │
  • │ │ │ │
  • │ │ 任务： │ │
  • │ │ 1. 分析用户需求，生成 200+ 个功能需求（feature_list.json）│ │
  • │ │ 2. 所有功能初始状态标记为 "passes: false" │ │
  • │ │ 3. 创建 init.sh（启动开发服务器的脚本） │ │
  • │ │ 4. 创建 claude-progress.txt（进度日志文件） │ │
  • │ │ 5. 完成第一个 git commit，记录初始脚手架 │ │
  • │ └─────────────────────────────────────────────────────────┘ │
  • │ ↓ │
  • │ ┌─────────────────────────────────────────────────────────┐ │
  • │ │ 后续上下文窗口：编码 Agent（Coding Agent）循环 │ │
  • │ │ │ │
  • │ │ 每次会话开始： │ │
  • │ │ 1. pwd → 确认工作目录 │ │
  • │ │ 2. 读取 git log + claude-progress.txt → 了解最新进展 │ │

  • │ │ 4. 运行 init.sh → 启动开发服务器 │ │

  • │ │ │ │
  • │ │ 执行： │ │
  • │ │ - 一次只做一个功能（增量进度） │ │
  • │ │ - 使用 Puppeteer MCP 进行浏览器端到端测试 │ │
  • │ │ - 只有完整测试通过才将 "passes" 改为 true │ │
  • │ │ │ │
  • │ │ 每次会话结束： │ │
  • │ │ - git commit（带描述性 commit message） │ │
  • │ │ - 更新 claude-progress.txt │ │
  • │ └─────────────────────────────────────────────────────────┘ │
  • └─────────────────────────────────────────────────────────────────┘

9.4 关键设计细节

功能需求文件的结构

  • "category": "functional",
  • "description": "新建聊天按钮创建一个新对话",
  • "steps": [
  • "导航到主界面",
  • "点击'新建聊天'按钮",
  • "验证新对话已创建",
  • "检查聊天区域显示欢迎状态",
  • "验证对话出现在侧边栏"
  • "passes": false

重要设计决策：使用 JSON 而非 Markdown，原因是模型更不容易不当地修改或覆盖 JSON 文件。并在提示词中使用强措辞："删除或编辑测试是不可接受的行为，这可能导致功能缺失或有缺陷"。

增量进度的关键性

增量方法对于解决 Agent 一次性完成所有事情的倾向至关重要。设计了以下约束：

  • • 每次只做一个功能
  • • 完成后立即提交（git commit）
  • • 进度状态必须在会话结束时持久化

状态恢复机制

  • Agent 会话开始
  • 运行 pwd + 读取 git log
  • 读取 claude-progress.txt
  • 读取 feature_list.json
  • 运行 init.sh → 启动服务器
  • 运行基本 E2E 测试（Puppeteer）
  • ├── 测试失败 → 先修复现有问题
  • └── 测试通过 → 开始新功能实现

9.5 失败模式-解决方案矩阵

问题初始化 Agent 行为编码 Agent 行为
Agent 过早宣告整个项目完成创建功能列表文件，基于输入规范设置结构化 JSON在会话开始时读取功能列表，选择单个功能开始工作
Agent 留下有缺陷或未记录的进度初始化 git 仓库和进度记录文件读取进度记录和 git log，运行基本测试，会话结束时提交并更新进度
Agent 过早标记功能完成创建功能列表文件自我验证所有功能，只在仔细测试后才标记为通过
Agent 需要花时间弄清楚如何运行应用编写 init.sh 脚本会话开始时读取 init.sh

10Codex实战

本节提炼
  • 零人工代码约束倒逼Harness建设，产出百万行代码、约1500 PR、效率约10倍
  • 刚性层级依赖Types→Config→Repo→Service→Runtime→UI，跨切面走Providers

OpenAI 工程师 Ryan Lopopolo 在2026年2月发布的报告，是 Harness Engineering 最重要的实践案例研究之一。

10.1 实验背景

  • • 起始时间 ：2025年8月（空仓库）
  • • 约束条件 ：零人工编写代码（"no manually typed code at all"）
  • • 团队规模 ：最初3名工程师（后扩展至7名）
  • • 产出规模 ：约百万行代码，约1500个 Pull Request
  • • 效率数据 ：平均每位工程师每天3.5个 PR，且随团队增长吞吐量仍在增加
  • • 整体效率 ：约为手工开发的10倍

这个实验的约束条件不是偶然的，而是一个强制函数（Forcing Function）：正是"不能人工写代码"这条约束，迫使团队必须构建一切使 Agent 可靠工作所需的 Harness 基础设施。

10.2 架构约束：严格的层级依赖

OpenAI 团队设计了一个刚性的架构模型：

  • 每个业务领域（Business Domain）内的依赖方向严格单向：
  • Types → Config → Repo → Service → Runtime → UI
  • 跨切面关注点（Cross-cutting Concerns）：
  • - 认证（Auth）
  • - 连接器（Connectors）
  • - 遥测（Telemetry）
  • - 特性标志（Feature Flags）
  • 这些跨切面关注点通过单一显式接口（Providers）进入。
  • 其他任何跨层依赖均被禁止，由自定义 linter 机械执行。

关键洞见：

"对于人工代码，这种约束通常感觉很迂腐或束缚。对于 Agent，它们成为乘数效应：一旦编码，它们立即在所有地方同时适用。"

10.3 知识库架构

团队在仓库中构建了结构化知识库：

  • docs/
  • ├── architecture/ # 领域和包分层的顶层地图
  • │ ├── domains.md # 各业务领域描述
  • │ └── package-layers.md # 包分层规则
  • ├── quality/ # 质量评分，按领域和层跟踪
  • │ └── quality-grades.md
  • ├── plans/ # 执行计划（第一类制品）
  • │ ├── active/ # 当前执行中
  • │ ├── completed/ # 已完成
  • │ └── debt/ # 已知技术债
  • └── AGENTS.md # 约100行，作为目录而非百科全书

**渐进式披露（Progressive Disclosure）**设计：AGENTS.md 保持简短（约100行），作为目录，指向更深层的信息源。Agent 从稳定的入口点开始，然后被告知在哪里查找更多信息，而不是被大量指令淹没。

10.4 "垃圾回收"机制

团队设计了周期性运行的垃圾回收 Agent：

  • ┌─────────────────────────────────────────────────────────┐
  • │ 垃圾回收 Agent（定期运行） │
  • │ │
  • │ 扫描内容： │
  • │ • 文档不一致性（与代码不匹配的文档） │
  • │ • 架构约束违规（被绕过的 linter 规则） │
  • │ • 死代码和过时引用 │
  • │ • 测试覆盖缺口 │
  • │ │
  • │ 处理：让 Agent 建议修复 → 由 Codex 生成 PR │
  • └─────────────────────────────────────────────────────────┘

这种机制对抗代码库的自然熵增（entropy）——随时间积累的不一致性和技术债务。

10.5 核心认知转变

OpenAI 团队得出的最重要结论：

"我们最困难的挑战现在集中在设计环境、反馈循环和控制系统。"

工程师的角色从"写代码的人"转变为：

  • • 设计环境（Design environments）
  • • 明确意图（Specify intent）
  • • 构建反馈循环（Build feedback loops）

Stripe 的 Minions 系统代表了 Harness Engineering 在大型企业环境中的最成熟实践之一。

11.2 Blueprints（蓝图）架构

Stripe 的"蓝图"是 Minions 系统最独特的设计之一，将工作流划分为两种节点类型：

确定性节点（Deterministic Nodes）：

  • • 运行 linter
  • • 推送 commit
  • • 触发 CI 构建
  • • 发送通知

智能节点（Agentic Nodes）：

  • • 实现新功能
  • • 修复 CI 失败
  • • 处理代码审查反馈

这种分离的核心优势：确定性节点保证了关键流程的可靠性，而智能节点为需要推理的任务提供了灵活性。无限重试循环被明确阻止——这是一个经典的 Harness 约束。

11.3 "左移质量"（Shift Feedback Left）

Stripe 强调的"左移反馈"原则：

  • • Pre-push hooks 基于启发式选择运行哪些 linter（而非运行所有 linter，节省时间）
  • • CI 门控作为最终安全网
  • • 不等到代码审查才发现低级问题

11.4 并行化与监督模式

Stripe 实现了无人监督并行化：开发者发布任务后离开，Agent 处理一切直到 CI，人类只在审查阶段重新介入。这与个人开发者的有人监督并行化（同时监管3-5个 Agent 会话）形成对比。

12模板与标准化

本节提炼
  • Harness模板类似服务模板，含linter、结构测试、上下文文档
  • 模板fork与同步成为新挑战，技术栈向AI友好方向收敛

12.1 Harness 模板的概念

随着 Harness Engineering 成熟，业界开始讨论 Harness 模板——类似于今天的服务模板（Service Templates），帮助团队在"黄金路径"上快速实例化新服务。

未来的 Harness 模板可能包含：

  • • 针对特定应用拓扑的自定义 linter
  • • 预配置的结构测试（ArchUnit 规则等）
  • • 基本的上下文文档和知识文档
  • • 附加上下文提供者（Context Providers）

这引发了新的工程挑战：

  • • 团队在使用过程中会 fork 模板（因为需要定制化）
  • • 如何将改进同步回模板？
  • • 如何处理不同团队的模板分叉和同步挑战？

12.2 收敛到有限技术栈

Harness Engineering 可能推动技术栈向以下方向收敛：

  • • 更强的静态类型（TypeScript over JavaScript, Rust/Go over Python for 某些场景）
  • • 清晰可强制执行的模块边界
  • • 框架的"AI 友好性"成为选型标准
  • • 具有现成 Harness 的架构模式（如六边形架构、清洁架构）获得优势

13AGENTS.md设计规范

本节提炼
  • 原则：目录而非百科全书、按失败增量更新、规则只是一层非完整解
  • 三层边界（自由/谨慎/先询问）与规则分级加载聚焦上下文
  • 规则文件是概率性合规，必须与确定性约束结合

AGENTS.md（OpenAI Codex 使用）和 CLAUDE.md（Claude Code 使用）是 Harness 的前馈层核心配置文件。2025年8月发布的 AGENTS.md 开放标准由 OpenAI、Google、Cursor、Factory 等合作制定，已成为跨工具的共同约定。

13.1 设计原则

原则一：目录而非百科全书

AGENTS.md 应该是简短的目录（约100行），指向更深层的信息源，而非一个巨大的知识转储。"如果你把整个公司大脑倒进一个巨大的 AGENTS 文件，Agent 不会变得更聪明，通常会变得更差。更多噪音，更多上下文腐烂，更多被静默忽略的内容。"

原则二：基于实际失败行为增量更新

Mitchell Hashimoto 的核心实践：每当 Agent 犯了同样的错误，就在 AGENTS.md 中增加阻止该错误的说明。"那个文件中的每一行都基于一次不良的 Agent 行为"——这是迭代式 Harness 工程的体现。

原则三：规则文件是 Harness 的一层，不是完整解决方案

LLM 遵守指令是概率性的，不是确定性的。规则文件必须与确定性的外层约束（linter、CI 门控）结合，才能在规模上可靠。

13.2 三层边界模式（GitHub 研究）

GitHub 对2500+个使用 AGENTS.md 文件仓库的分析，推荐了三层边界模式：

  • # AGENTS.md 三层边界示例
  • ## 可自由操作（Free to Modify）
  • # Agent 可以直接修改，无需确认
  • - src/ # 应用源码
  • - tests/ # 测试文件
  • - docs/ # 文档（非核心）
  • ## 谨慎操作（Modify with Caution）
  • # Agent 应在修改前说明原因
  • - package.json # 依赖变更影响较广
  • - .eslintrc # 规则变更影响所有代码
  • - config/ # 配置文件
  • ## 先询问再操作（Ask First）
  • # Agent 必须获得明确授权才能修改
  • - .github/workflows/ # CI/CD 配置
  • - infrastructure/ # 基础设施代码
  • - secrets/ # 任何凭据相关
  • - DATABASE_SCHEMA # 生产数据库 schema

没有"先询问"这一层，Agent 在构建重试逻辑时会自行选择重试间隔；有了这一层，它必须先询问。

13.3 规则的选择性加载

Augment Code 的 Augment Rules 系统展示了规则的分级加载策略：

  • always_apply 规则 → 每次提示都自动包含（核心约定）
  • agent_requested 规则 → Agent 判断相关时加载（特定场景）
  • manual 规则 → 仅在明确调用时加载（特殊情况）

选择性加载的目的：在保持约束执行的同时，让上下文窗口聚焦于任务。

13.4 实际 CLAUDE.md 示例

  • # 项目 CLAUDE.md
  • ## 构建
  • - 完整构建：`./gradlew build`
  • - 运行测试：`./gradlew test`
  • - 启动开发服务器：`./init.sh`
  • ## 代码规则
  • - 包依赖方向：domain → application → infrastructure
  • - infrastructure 不直接引用 domain
  • - Entity 默认使用懒加载，N+1 问题用 fetch join 解决
  • - 所有日志必须使用结构化 JSON 格式
  • ## 提交规范
  • - Commit message 用中文书写
  • - 不以句号结尾
  • - 格式：`[类型] 简短描述`
  • ## 测试要求
  • - 新功能必须包含端到端测试
  • - 单元测试覆盖率不低于80%
  • - 不得删除或绕过已有测试
  • ## 架构参考
  • - 详细架构文档：docs/architecture/
  • - API 规范：docs/api-contracts/
  • - 已知技术债：docs/plans/debt/

14熵管理与垃圾回收

本节提炼
  • 六类熵：命名漂移、文档失同步、死代码、覆盖退化、约束侵蚀、过时引用
  • 三层防线：变更内即时检测、CI集成检测、持续漂移监控

在 AI 生成的代码库中，熵的积累是一个特别严重的问题。

14.1 什么是代码库熵

在传统软件开发中，工程师在代码审查、重构和知识分享中自然发现并纠正熵。AI 生成的代码库中，熵积累速度更快，且更难被发现：

  • 熵的类型：
  • ├── 变量命名漂移（Naming Drift）
  • │ └── 同一概念在不同文件中使用不同命名
  • ├── 文档失同步（Documentation Drift）
  • │ └── 实现已改变，文档未更新
  • ├── 死代码积累（Dead Code Accumulation）
  • │ └── 功能已删除，代码仍存在
  • ├── 测试覆盖退化（Coverage Degradation）
  • │ └── 新功能未添加测试
  • ├── 架构约束侵蚀（Constraint Erosion）
  • │ └── 被绑过的 linter 规则
  • └── 过时引用（Stale References）
  • └── 引用已不存在的 API 或模块

14.2 连续熵监控策略

OpenAI 的"垃圾回收"机制代表了主动熵管理的方向：

  • ┌─────────────────────────────────────────────────────────────────┐
  • │ 熵管理三层防线 │
  • │ │
  • │ 层一：变更生命周期内的即时检测 │
  • │ ├── Pre-commit linters（毫秒级，每次变更） │
  • │ ├── 结构测试（秒级，每次提交） │
  • │ └── AI 代码审查（分钟级，PR 级别） │
  • │ │
  • │ 层二：CI/CD 管道中的集成检测 │
  • │ ├── 重新运行所有快速检查 │
  • │ ├── 变异测试（Mutation Testing） │
  • │ ├── 更广泛的架构审查 Skill │
  • │ └── 详细代码审查 Skill │
  • │ │
  • │ 层三：持续漂移监控（脱离变更生命周期） │
  • │ ├── 死代码检测 Agent（定期扫描） │
  • │ ├── 测试覆盖质量分析 Agent │
  • │ ├── 依赖扫描（Dependabot 等） │
  • │ └── 运行时指标监控（SLO 退化 → 触发改进建议） │
  • └─────────────────────────────────────────────────────────────────┘

14.3 自愈设计原则

Harness 的理想状态是自愈（Self-Healing）：当传感器检测到问题时，不仅报告问题，还触发修复 Agent 自动生成解决方案。

  • 传感器检测到架构违规
  • 生成详细报告（包含：违规位置、规则说明、建议修复方式）
  • 触发修复 Agent（被授权在特定范围内自动修复）
  • 修复 Agent 生成 PR（包含修复代码和解释）
  • 人工审查（复杂度低时可自动合并）

15多Agent架构

本节提炼
  • 协作模式：专家分工、生成-评估、并行化，人类做分配/审查/仲裁
  • 额外挑战：状态协调、知识共享、访问控制
  • 模型无法可靠评估自己的工作，需分离生成与评估

Harness Engineering 在多 Agent 场景中面临额外的复杂性。

15.1 多 Agent 协作模式

目前最成熟的多 Agent 模式：

模式一：专家型 Agent 分工

  • Orchestrator（协调者）
  • ├── Coding Agent → 代码生成
  • ├── Testing Agent → 测试验证
  • ├── Review Agent → 代码审查
  • └── Cleanup Agent → 熵清理

Anthropic 的工程师注意到，单一通用型编码 Agent 在跨上下文工作时表现是否最优，目前仍是开放问题。专业化 Agent（测试 Agent、QA Agent、代码清理 Agent）可能在特定子任务上表现更好。

模式二：生成-评估（Generator-Evaluator）

受 GAN 启发，Epsilla 等公司提出的架构：

  • Generator Agent → 生成代码/内容
  • Evaluator Agent → 评估质量、发现问题
  • ┌────┴────┐
  • │ │
  • 通过 失败
  • │ │
  • 合并 反馈给 Generator → 重新生成

这解决了 Anthropic 研究发现的问题：模型无法可靠评估自己的工作。分离生成和评估职责，可以显著提高输出质量。

模式三：Agent 级别的并行化

  • 人类工程师
  • ├── Git Worktree 1 → Agent 处理功能 A
  • ├── Git Worktree 2 → Agent 处理功能 B
  • └── Git Worktree 3 → Agent 处理 Bug C
  • 人类的角色：
  • - 分配任务（Manager）
  • - 审查输出（Reviewer）
  • - 解决冲突（Arbiter）
  • - 迭代 Harness（Harness Engineer）

15.2 多 Agent Harness 的额外挑战

状态协调：多个 Agent 并行修改同一代码库时，如何避免冲突？

解决方案：

  • • 明确的工作范围划分（每个 Agent 只能修改指定模块）
  • • Git 分支隔离（每个 Agent 在独立分支工作）
  • • 自动冲突检测和升级机制

知识共享：一个 Agent 学到的信息如何传递给其他 Agent？

解决方案：

  • • 共享知识库（docs/ 目录）
  • • 结构化日志（所有 Agent 写入同一个进度文件）
  • • 通过 git history 传递上下文

访问控制：哪个 Agent 有权做什么？

解决方案：

  • • 细粒度的工具访问权限
  • • 文件系统访问控制（只能修改指定目录）
  • • 操作类型限制（只读 vs 读写 vs 特权操作）

16可观测性与监控

本节提炼
  • 金字塔三层：基础设施、Agent行为、业务指标
  • 从简单结构化文件日志开始，遥测可触发自适应修复

生产级 Harness 必须具备完整的可观测性。

16.1 Agent 可观测性的三个层次

  • ┌────────────────────────────────────────────────────────┐
  • │ Agent 可观测性金字塔 │
  • │ │
  • │ ┌────────────────┐ │
  • │ │ 业务指标层 │ ← 功能完成率、质量分 │
  • │ ┌───┴────────────────┴───┐ │
  • │ │ Agent 行为层 │ ← 工具调用、决策 │
  • │ ┌───┴────────────────────────┴───┐ │
  • │ │ 基础设施层 │ ← Token 用量 │
  • │ └────────────────────────────────┘ │
  • └────────────────────────────────────────────────────────┘

基础设施层指标：

  • • Token 使用量（每会话、每功能）
  • • 会话时长
  • • API 调用次数和延迟
  • • 上下文窗口利用率

Agent 行为层指标：

  • • 工具调用模式（哪些工具最常用）
  • • 重试次数（Harness 反馈循环触发频率）
  • • 失败模式分类（哪类错误最常见）
  • • 分支创建和 PR 数量

业务指标层：

  • • 功能完成率
  • • PR 通过率（首次 CI 通过 vs 需要重试）
  • • 代码质量分数（linter 违规率、测试覆盖率趋势）
  • • 人工干预率（需要工程师介入的比例）

16.2 Datadog 的遥测集成案例

Datadog 将生产遥测数据作为 Harness 本身的一部分：如果性能退化，该信号直接进入反馈循环，触发 Agent 改进。这代表了 Harness 的最高形态——运行时自适应 Harness：

  • 生产指标退化（p99 延迟 > 阈值）
  • Harness 监控层检测到异常
  • 触发性能分析 Agent
  • Agent 分析代码、数据库查询、缓存策略
  • 生成性能优化 PR
  • 人工审查 → 合并 → 指标改善

16.3 可观测性的实施建议

从简单开始：即使是基于文件的简单日志也比没有可观测性要好。

  • "timestamp": "2026-04-25T10:30:00Z",
  • "agent_type": "coding_agent",
  • "action": "tool_call",
  • "tool": "bash",
  • "command": "npm run test",
  • "result": "PASS",
  • "tokens_used": 1250,
  • "context_window_used_pct": 0.43

结构化日志是关键——便于后续分析和改进 Harness。

17安全与权限

本节提炼
  • 最小权限：只读/读写/禁止分级，工具与网络白名单
  • 沙箱隔离devboxes，设计人工检查点分级
  • AI生成代码月引入逾万新漏洞，需SAST、依赖与密钥扫描

安全是 Harness Engineering 的核心关切之一，尤其是在生产环境中。

17.1 最小权限原则

Harness 应该为 Agent 提供完成任务所需的最小权限集：

  • 权限分类：
  • ├── 只读：配置文件、参考文档
  • ├── 读写：项目源码（限定目录）
  • └── 禁止：secrets、生产凭据、基础设施代码
  • 🔧 工具权限
  • ├── 允许：运行测试、lint、git 操作
  • ├── 条件允许：网络请求（限白名单域名）
  • └── 禁止：生产数据库访问、外部 API 凭据
  • 🌐 网络权限
  • ├── 允许：npm/pip 包仓库、文档站点
  • ├── 条件允许：内部工具（通过 MCP）
  • └── 禁止：生产环境、互联网（Stripe Minions 的选择）

17.2 沙箱执行环境

Stripe 的 Minions 运行在隔离的 "devboxes" 中，与生产环境和互联网完全隔离。这种设计：

  • • 防止 Agent 意外操作生产数据
  • • 限制安全漏洞的爆炸半径
  • • 提供一致、可重现的执行环境

Anthropic 的安全研究中提到 Agent 在沙箱环境中可能存在越狱行为——这提醒了 Harness 工程师沙箱设计必须是防御性的，而非信任性的。

17.3 安全事件的统计警示

Apiiro 2025年9月的分析发现：截至2025年6月，AI 生成的代码每月引入超过1万个新安全漏洞（较2024年12月增加10倍）。这个数字凸显了：

技术手段必须与Harness 约束结合：

  • • SAST（静态应用安全测试）作为反馈传感器
  • • 依赖漏洞扫描（Dependabot、Snyk）
  • • 密钥扫描（防止 API 密钥泄露）
  • • 代码签名和审计追踪

17.4 人工检查点设计

并非所有操作都应该 Agent 全自动执行。设计清晰的人工检查点：

  • 自动化（无需人工确认）：
  • - 运行测试
  • - 修复 linter 错误
  • - 更新文档
  • 需要人工确认的操作：
  • - 修改共享配置文件
  • - 添加/删除依赖
  • - 架构级变更
  • - 数据库 schema 变更
  • 始终需要人工执行：
  • - 生产部署
  • - 安全策略变更
  • - 基础设施配置

18最佳实践准则

本节提炼
  • 六步法：强制函数、声明式意图、反馈循环、约束、仪表化、人工检查点
  • 质量左移：提交前→PR→CI→持续运行，反馈越早成本越低
  • 命令式指令冗长低效，声明式规范让Agent推断；避免过度工程化

综合 Anthropic、OpenAI、Thoughtworks、Mitchell Hashimoto 等权威来源，总结以下最佳实践：

18.1 Harness 建设六步法

第一步：从强制函数开始

采用"无人工代码"这类强制函数——哪怕仅针对单个模块或重构——迫使投入 Harness 建设。没有压力，Harness 建设往往被推迟。

第二步：声明式意图，而非命令式指令

使用高层规范、架构决策记录（ADR）和 schema，而非低级指令：

  • ❌ 命令式：
  • "在 UserService 中调用 database.query() 时，记得加 try-catch，
  • 连接到 PostgreSQL 时使用连接池，超时设为5秒..."
  • ✅ 声明式：
  • docs/architecture/error-handling.md 中记录错误处理策略，
  • 通过 schema 定义数据库访问模式，让 Agent 推断细节。

第三步：建立反馈循环

最低可行反馈循环：Agent 做出变更后运行测试，尝试在宣告成功前修复失败。"写-测试-修复"循环是最简单有效的反馈控制。

第四步：添加约束（从严格开始）

限制文件访问到相关目录，要求提交前 lint，阻止破坏性命令（除非明确授权）。原则：先严格，后放松——随着信任度增加逐步开放权限。

第五步：仪表化，用于可观测性

记录 Agent 的每一步行动、工具调用和 Token 使用量。即使是简单的文件日志也足以诊断失败和改进 Harness。

第六步：设计人工检查点

确定哪些决策必须由人类做出，哪些可以自动化。高风险、不可逆的操作需要人工确认。

18.2 迭代改进原则

Harness 不是一次性建设，而是持续演进的：

"每当 Agent 挣扎时，我们将其视为信号：识别缺少什么——工具、护栏、文档——并将其反馈到代码库中，始终让 Codex 自己编写修复。" —— OpenAI 工程团队

实践步骤：

  • 1. 记录 Agent 失败（而非只是修复输出）
  • 2. 分析失败模式（一次性失败 vs 系统性失败）
  • 3. 将系统性失败转化为永久性约束（linter 规则、结构测试）
  • 4. 使用 AI 帮助构建这些约束（让 Agent 写 linter 规则）

18.3 构建可适应的 Harness

不要过度工程化：

"如果 Harness 不断增长变得复杂，这可能是过度工程化的信号，与模型演进背道而驰。"

设计可适应的 Harness：

  • • 区分"核心约束"（不随模型进步而过时：架构边界、linters）和"辅助约束"（随模型改进可能变得不必要：某些详细指令）
  • • Vercel 的教训：移除80%的工具，反而得到更好的结果——更多工具意味着更多混乱和错误的工具选择
  • • CLAUDE.md/AGENTS.md 的指令随着模型能力提升会逐渐减少

18.4 进度持久化原则

所有 Agent 工作都必须可以被检查和恢复：

  • • 使用 Git 作为状态存储（commit message 是进度记录）
  • • 使用结构化进度文件（claude-progress.txt）桥接会话
  • • Slack 讨论如果没有进入仓库，对 Agent 来说等于不存在
  • • 设计决策必须版本化到代码库中（不能存在于外部工具中）

18.5 "质量左移"原则（Keep Quality Left）

借鉴 CI/CD 的"左移"原则：反馈越早，修复成本越低。

  • 提交前（最快、最便宜）：
  • ├── ESLint / Prettier（毫秒级）

20工程师角色转变

本节提炼
  • 时间分配转向设计环境、明确意图、构建反馈循环
  • 新技能：系统思维、架构设计、规范写作、可观测性

Harness Engineering 正在从根本上重新定义软件工程师的工作职能。

20.1 从"写代码"到"设计系统"

  • 传统软件工程师的时间分配：
  • ├── 70% 编写代码
  • ├── 15% 代码审查
  • └── 15% 设计和规划
  • Harness 工程时代的工程师时间分配：
  • ├── 30% 设计环境（Harness 架构）
  • ├── 25% 明确意图（规范、ADR、约束定义）
  • ├── 20% 构建反馈循环（Sensor 和验证工具）
  • ├── 15% 审查 Agent 输出
  • └── 10% 迭代改进 Harness

20.2 新技能要求

Harness 工程对软件工程师提出了新的技能要求：

系统思维（Systems Thinking）：理解约束、反馈循环和文档如何相互作用，而不是孤立地思考单个工具。

架构设计（Architecture Design）：定义可强制执行且高效的边界——这要求比以往更深的架构思考，因为系统必须在没有持续人工干预的情况下运行。

规范写作（Specification Writing）：足够精确地表达意图，使 Agent 能够执行——这比传统的需求文档写作要求更高的精确度。

可观测性（Observability）：构建能够揭示 Agent 行为模式的监控系统。

快速迭代（Iteration Speed）：快速测试和改进 Harness 配置的能力。

20.3 从"经理日程"到"制造者日程"的再反转

Paul Graham 的经典论文《制造者日程 vs 经理日程》描述了创意工作者需要连续时间块。有趣的是，Harness Engineering 时代出现了一个再反转：

工程师越来越像管理者：

  • • 分配任务（给 Agent）
  • • 审查工作（PR 审查）
  • • 解决冲突（架构决策）
  • • 改进系统（Harness 迭代）

而 Agent 扮演了"制造者"的角色。Mitchell Hashimoto 坦言：即使他是 Harness Engineering 的倡导者，他目前只有10%–20%的工作日在运行后台 Agent。

20.4 "工程抗体"（Engineering Antibodies）

Harness Engineering 培养一种组织能力：将每次失败转化为防止相同失败再次发生的系统能力。每次 Agent 犯错：

  • 1. 识别失败模式
  • 2. 设计防止该模式的机制（linter、约束、测试）
  • 3. 将机制编码到 Harness 中
  • 4. 系统性地消除这类错误

这类似于生物免疫系统：每次感染（失败）都产生抗体（约束），使系统对未来的相同攻击免疫。随着时间推移，Harness 变得越来越强大，Agent 的可靠性也随之提高。

21挑战与开放问题

本节提炼
  • 视觉与语义判断局限，Harness一致性无标准化度量
  • 开放问题：通用vs专业Agent、覆盖度量、跨领域泛化

21.1 当前技术局限

视觉理解限制：Claude 通过 Puppeteer MCP 进行浏览器测试时，无法看到浏览器原生的 alert 弹窗。这导致依赖这些弹窗的功能更容易出现缺陷。

语义判断局限：计算型传感器可靠检测结构性问题，但无法可靠检测语义级问题，如：

  • • 过度工程化
  • • 功能误解
  • • 错误诊断

这些更高影响力的问题仍然需要人工监督。

Harness 一致性问题：随着 Harness 增长，如何保持 Guides 和 Sensors 之间的一致性，不互相矛盾？目前没有标准化的方法评估 Harness 覆盖质量（类似代码覆盖率对于测试的意义）。

21.2 开放研究问题

通用型 vs 专业型 Agent：一个通用型编码 Agent 跨上下文工作是否最优？还是专业化 Agent（测试 Agent、QA Agent、清理 Agent）在子任务上表现更好？Anthropic 的工程师指出这是目前最重要的开放问题之一。

Harness 覆盖度量：我们需要类似代码覆盖率和变异测试对测试的意义的标准，来评估 Harness 的覆盖质量。如果传感器从不触发，是高质量的信号还是检测机制不足的信号？

绿地 vs 遗留代码库：哪些 Harness 技术可以应用于现有应用，哪些只适用于从头开始构建时内置了 Harness 的应用？

跨领域泛化：Anthropic 的长周期 Agent 研究针对全栈 Web 应用优化。如何将这些发现泛化到其他领域（科学研究、金融建模）？

可信度与代表性：OpenAI 对其 Codex 系统的描述有利益相关——他们有动机让 Codex 看起来好。独立验证这些成果至关重要。

21.3 社会和组织挑战

技能培训缺口：传统的"通过写代码学习编程"路径在 Harness Engineering 时代可能部分被工具本身封闭。如何培训下一代 Harness 工程师？目前没有人发布相关课程体系。

技能债务：正如 Hashimoto 所说，他只有10%–20%的时间运行 Agent，"始终有 Agent 在运行"对他来说仍是愿景而非现实。这表明大规模采用仍存在重要挑战。

知识分布不均：目前 Harness Engineering 最佳实践主要集中在硅谷大型科技公司（OpenAI、Stripe、Anthropic）。中小型企业和传统行业如何获得和应用这些实践？

Harness Engineering 是 AI Agent 时代软件工程的核心新兴学科。本文综合权威来源，总结其最关键的洞见：

核心洞见一：模型是商品，Harness 是护城河

GPT-5、Claude 和 Gemini 等模型在标准基准上表现相近。竞争优势不再来自模型访问权，而来自 Harness 工程能力。正如 NxCode 的观察：

"2026年在 AI 产品质量上领先的组织，不是那些拥有独家模型访问权的组织。他们是 Harness 工程实践最成熟的团队——把 Harness 视为产品，把模型视为其中可替换的组件。"

核心洞见二：约束增强能力，而非限制能力

直觉上，约束应该减少 Agent 的能力。但实践证明相反：在明确定义的边界内运行的 Agent 可以行使更大自主权，因为 Harness 捕获错误。没有约束，你需要持续的人工监督。Vercel 的悖论完美体现了这一点：移除80%的工具，Agent 的输出质量反而提高。

核心洞见三：工程师的角色从制造者转变为架构师

软件工程师的核心职责正在从"编写代码"转变为"设计使 AI 能够可靠编写代码的系统"。这需要更深的系统思维、架构设计和规范写作能力。

核心洞见四：前馈+反馈，确定性+概率性

可靠的 Harness 必须同时具备前馈控制（预防问题）和反馈控制（检测和纠正问题），以及确定性工具（linters、测试）和概率性工具（AI 审查）的结合。单靠任何一种都不够。

核心洞见五：从失败中学习，永久编码

Mitchell Hashimoto 的核心哲学：每次 Agent 失败都应该转化为防止该类失败的永久性 Harness 改进。不要只是修复输出，而是修复系统。这种"工程抗体"积累，使 Harness 随时间变得越来越强大。

最终思考

Harness Engineering 的时代才刚刚开始。该术语在2026年2月才进入主流，仅仅几个月时间，已经有 OpenAI、Anthropic、Stripe、Thoughtworks 等顶级工程团队在实践中验证了它的核心原则。

正如 OpenAI 工程团队指出的："我们最困难的挑战现在集中在设计环境、反馈循环和控制系统。" 这不是一个偶然的观察，而是整个行业的共同转变——从"写代码"到"设计让 AI 可靠写代码的系统"。
