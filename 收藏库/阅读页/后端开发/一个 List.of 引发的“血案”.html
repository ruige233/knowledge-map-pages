案发现场

案情推理

List.of 触发的离奇现象让我不得不重新审视它，一步步看下它的源码实现。

01List.of 源码

本节提炼
  • List.of() 是 JDK9 之后特性，返回不可修改列表，官方注释明确返回空 List。
  • 底层实现是 ImmutableCollections.emptyList()，ImmutableCollections 是不可变集合容器类。
  • 误以为 List.of() 与普通 ArrayList 一样，忽略其底层不可变容器的差异。
  • public interface List<E> extends Collection<E> {
  • /**
  • * Returns an unmodifiable list containing zero elements.
  • * See <a href="#unmodifiable">Unmodifiable Lists</a> for details.
  • * @param <E> the {@code List}'s element type
  • * @return an empty {@code List}
  • * @since 9
  • static <E> List<E> of() {
  • return ImmutableCollections.emptyList();

从官方注释中得到3点结论：

  • 这是一个 JDK9 之后的特性；
  • 返回的是一个不可修改的数组；
  • 底层实现使用的 ImmutableCollections 的 emptyList 方法，而 ImmutableCollections 这个类是一个不可变集合的容器类；

  • emptyList 做了 List 强转，但按 Java 类型转换原则运行时仍是 ListN 对象。

03Node HSF 泛化调用

本节提炼
  • 陆游平台通过 Node 泛化调用 HSF 接口，默认只解析 List、Map 等基础 Java 类型。
  • ListN 这类特殊类型在序列化/反序列化时走了不同逻辑，导致异常结构。
  • 特殊集合类型经 Node 泛化调用可能被序列化成非预期结构。

陆游平台调取HSF接口走的是node的泛化调用，默认情况下node只能解析一些基础的java类型，例如List和Map。

而遇到这次返回的 ListN，可以确定是这种特殊类型在序列化/反序列化的过程中出现了不同的逻辑导致。

04ListN 序列化代理

本节提炼
  • readObject 直接抛 InvalidObjectException，是保证不可变性的防御措施。
  • writeReplace 把 ListN 替换成内部序列化代理 CollSer，传入 tag=1 与空数组。
  • CollSer 的 array 字段被 transient 修饰忽略，tag=1 就是前端对象里 tag 的来源。
  • 忽略 writeReplace 与 transient 等序列化细节，就解释不了 tag=1 的由来。

05结论与反思

本节提炼
  • 解决办法是把 List.of() 替换成 Lists.newArrayList()。
  • HSF 控制台用 hessian 序列化可正确解析，怀疑与 Node 序列化类型不同。
  • 反思：用新技术前先搞清楚内部实现细节。

综上所述，当后端在HSF接口中使用了 List.of() 做返回，在 node 调用 HSF 序列化获取返回结果时会解析成一个带有tag字段的对象，而不是预期的空数组。这个问题其实想解决很简单，将 List.of() 替换成我们常用的 Lists.newArrayList() 就行，本质上还是对底层实现的不清晰不了解导致了这整个事件。

当然在结尾处，其实还有一个疑点，在 HSF 控制台调试这个接口的时候，我发现它的 json 结构是可以正确解析的：

怀疑可能是序列化类型的问题，hsfops 也是用了泛化调用，序列化类型是 hessian，可能 node 的序列化类型不一样，这个后续研究确定后我再补充一下。

最后的反思与大家共勉：对于新技术（或者新特性）的应用一定要先搞清楚内部的实现细节，不然可能出现使用时的大坑。
