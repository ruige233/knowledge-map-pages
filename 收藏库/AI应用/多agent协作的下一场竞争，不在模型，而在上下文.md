# 多Agent协作的下一场竞争，不在模型，而在上下文

> 一句话定位：多 Agent 协作的胜负手不在模型，而在上下文能否低折损地流动。

## 摘要

文章提出：多 Agent 协作的下一场竞争不在模型，而在上下文管理。协作的本质是上下文的流动，消息只是上下文被压缩、编码后的产物，协作的全部难题本质都是上下文传递中的折损。进入人-人-Agent 时代，折损从加法变乘法——每多一个协作节点就多一层转述，人被卡在链路中间当"传声筒"。真正的解法不是让 Agent 学会转述，而是"不靠通信共享上下文，而是靠共享上下文来通信"，消灭转述。作者介绍司内工具 Siboot 的落地：群（共享上下文的场）、Topic（上下文的聚焦与隔离）、@（接力但不搬运上下文）、以及 Agent 自己的文件系统（横向共享 + 纵向沉淀，让 Agent 会整理、能自迭代）。人从链路中继器里解放出来，回到定目标、做判断、划边界、做验收。结语：模型决定每个节点有多强，上下文管理决定整个网络能不能协同。

## 要点

- 协作本质是上下文流动：消息只是被压缩编码后的产物，全部协作难题=上下文传递中的折损。
- 人-人-Agent 时代折损从加法变乘法：每多一个节点多一层转述，人成了给一群算得比自己快的东西当传声筒。
- 两条路线：让 Agent 学会转述（不触碰根问题）；或「不靠通信共享上下文，而是靠共享上下文来通信」——能直接读的结构化状态，不该被压成聊天记录再逆向解码。
- Siboot 三构件：群=持续在场的上下文容器；Topic=聚焦与隔离（Topic 边界=Agent 注意力边界=成本边界）；@=接力不搬运（被 @ 者直接站进完整现场）。
- 纵向维度：Agent 要有「会自己整理的文件系统」（inbox / notes / 需求与 BUG 档案 / 报告目录 + 定时归档任务），才有连续记忆、能自迭代，且白盒可治理。
- 人的位置反而更清楚：从搬运转述中解放，回到定目标、做判断、划边界、做验收四件事。
- 结语：模型决定节点强度，上下文管理决定网络能否协同——协作工具的下一场竞争在上下文层。

## 提炼

> 多Agent协作的胜负手在上下文层，而非模型能力。

### 分节要点

- **一、先问一个被跳过的问题：协作到底在传递什么？**：消息只是载体，协作真正流动的是上下文；协作的全部难题本质是上下文传递中的折损；会议纪要、文档、复盘、对齐、周报都在搬运和对齐上下文。坑：误把协作当作发消息，忽略背后的上下文折损。
- **二、当 Agent 上桌，折损开始按乘法叠加**：把 Agent 塞进工作流只解决进场，没解决上下文流动；每层转述都是有损压缩，折损按乘法叠加；人被卡成传声筒，越忙链路越堵。坑：让人当中继器。
- **三、两条路：让 Agent 学会转述，还是让大家共享上下文**：让 Agent 学转述不改变习惯但没触及根；第二条路——不靠通信共享上下文，而是靠共享上下文来通信；Agent 的状态本可结构化记录和直读。坑：仍靠总结-转述-再理解，折损依旧。
- **四、Siboot 的答案：群是场，Topic 是焦点，@ 是接力**：群=持续在场的上下文容器；Topic=上下文管理单元，隔离噪音、界定注意力与成本边界；@ 只喊下一棒进场；三者构成低折损流水线。坑：群不隔离噪音会变成一锅粥。
- **五、还差一维：Agent 得会管自己的文件，才谈得上"自迭代"**：协作还有时间维度，热上下文会变冷；靠更大窗口解决记忆既烧钱又低效；Agent 要有会整理的文件系统（inbox/notes/档案/报告+定时归档去重）。坑：把所有历史塞进上下文窗口。
- **六、那人去哪了？——人的位置反而更清楚了**：人从传声筒解放，整条链路人只动两下（确认需求、验收）；剩四件事：定目标、做判断、划边界、做验收。坑：误以为共享上下文会架空人。
- **七、结语：协作工具的下一场竞争，在上下文层**：胜负手在上下文能否低折损流动；模型是算力问题，上下文管理是产品问题；群是场、Topic 是焦点、@ 是接力、文件是记性。坑：小白捏 AI 员工、人机边界仍有模糊地带。

### 知识卡

- **[概念对比] 通信共享 vs 共享上下文**：转述是"我把我知道的告诉你"；共享上下文是"我们看着同一个现场一起干"，后者消灭转述、折损趋零。（→ 三）
- **[概念对比] 加法折损 vs 乘法折损**：单人时代讲一遍损一点；人-人-Agent 时代每多一个节点多一层转述，损耗被继承再叠加。（→ 二）
- **[结论] 群是场，Topic 是焦点，@ 是接力**：上下文在场、聚焦、接力是一条低折损流水线，而非三个功能堆叠。（→ 四）
- **[结论] 文件是记性**：热上下文在群和 Topic 实时共享，冷上下文在文件系统结构化沉淀，Agent 才既活在当下又长着记性。（→ 五）
- **[数据] 一条任务链四次编码-解码**：一份竞品分析经人转述、再转述、再产出，上下文被编码-解码四次，每道都是有损压缩。（→ 二）
- **[数据] 二十人项目大群并行聊三件事**：告警、BUG 复盘、规划全糊在一个消息流里，人靠考古，Agent 被无关信息稀释。（→ 四）
- **[易错点] 只把 Agent 塞进工作流就够了？**：只解决进场，不解决上下文流动，仍停在旧范式。（→ 二）
- **[易错点] 更大上下文窗口≠记忆**：窗口再大也装不下团队几个月信息，应像人一样分类沉淀、按需调取。（→ 五）
- **[易错点] 不会整理的 Agent 只是聊天机器人**：会整理才有连续记忆、越干越熟。（→ 五）
- **[结论] 人只剩四件事**：定目标、做判断、划边界、做验收，全是判断与责任，没有一件是搬运信息。（→ 六）

### 带走三句话

1. 协作的本质是共享上下文：别让人给 Agent 当传声筒，让上下文可看见、可接力、可沉淀。
2. 多 Agent 协作的天花板不在模型而在上下文折损：优化转述不如消灭转述。
3. 群是场、Topic 是焦点、@ 是接力、文件是记性：横向共享加纵向沉淀，协作网络才立得起来。
