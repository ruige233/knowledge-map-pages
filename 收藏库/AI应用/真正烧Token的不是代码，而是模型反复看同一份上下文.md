# 真正烧Token的不是代码，而是模型反复看同一份上下文

> 一句话定位：省 Token 的关键不是代码量，而是别让长上下文被多轮请求反复携带

## 摘要

本文复盘轻量云多 Agent 工作流 DevFlow 的 Token 成本：烧 Token 的不是新增代码，而是长上下文在多轮请求中被反复携带。优化有两条主线：一是治理信息生命周期，代码探索交给短生命周期 Code Explorer、低频模板按需加载；二是合并已确定动作，用响应级批量和向量化 replace_batch 减少往返，以快照与回滚保证事务性。实测 6 个 HTTP 接口需求，Claude Opus 5 与 GLM 5.2 的 Token 分别降 25.69% 和 41.95%。

## 要点

- 真正烧 Token 的不是新增代码，而是长上下文在多轮请求中被反复携带。
- 总输入 Token ≈ Σ（第 i 轮已有上下文 + 第 i 轮新增内容），单轮长度与轮数互相放大。
- 代码探索交给短生命周期 Code Explorer，只回传不超过约 500 字的结构化摘要。
- 低频模板与 Skill 细节按需加载：重点不是内容放在哪，而是何时进入上下文。
- 成功路径直接流转、减少 Main 中转，Main 只兜底异常场景。
- 响应级批量合并已确定的读写验证；replace_batch 用快照、预校验和回滚保证事务性。
- 实测两个模型完整流程 Token 分别下降 25.69% 与 41.95%。

## 提炼

> 一句话定位：省 Token 的关键不是代码量，而是别让长上下文被多轮请求反复携带

### 分节提炼

- **01 背景：先从 DevFlow 说起**：DevFlow 按方案设计、开发、审查、测试、沉淀、汇总分工，各阶段由不同 Agent 负责。；成本痛点不在新增代码，而是 120K 长上下文在四轮请求中被反复携带。；Developer、Test Engineer 是模型调用最频繁、成本放大最重的阶段。
- **02 成本放大机制**：总输入 Token ≈ Σ（第 i 轮已有上下文 + 第 i 轮新增内容）。；成本由单轮上下文长度与调用轮数共同决定，二者互相放大。；优化主线：控制信息进入上下文的时机与驻留范围，合并已确定动作。
- **03 上下文治理**：关键不是内容放在哪，而是内容什么时候进入上下文。；代码探索交给只读的短生命周期 Code Explorer，仅回传不超过约 500 字结构化摘要。；低频模板与 Skill 细节下沉 assets/references，按触发条件加载。；成功路径直接流转，Main 只兜底失败、重试、门禁、协议异常与完成。
- **04 减少模型往返**：响应级批量：一次模型响应表达多个已确定、无数据依赖的操作。；多个独立 replace_in_file 各自匹配落盘，无统一预校验和回滚。；Prompt 只能提高批量概率，不能改变工具能力边界、提供确定性。
- **05 批量编辑选型**：apply_patch 能力完整，但迁移成 CodeBuddy MCP 后调用成功率不理想。；根因是 MCP JSON 转义叠加 Patch 自定义语法，生成负担重。；需求收敛：新文件用 write_to_file，重点是向量化已有文件多处修改。
- **06 replace_batch 设计**：replace_batch 用数组承载多项 old_str/new_str 替换。；所有替换基于调用开始时的原始快照，old_str 需恰好匹配一次。；整批校验、staging、fsync 与失败回滚保证事务性。；批次边界按同一代码状态能否同时确定划分；Hook 探活失败 fail-open。
- **07 优化结果**：完整流程 Token 两模型分别降 25.69% 与 41.95%，高频阶段降幅最明显。；优化对象是信息生命周期与动作表达粒度，没有削减必要分析。；Harness 原则：模型判断做什么，动作确定后由工具与运行时稳定执行。

### 带走三句话

1. 先把信息生命周期管起来：探索结论短驻留、低频模板按需加载、成功路径少中转。
2. 已确定的读写修改尽量同轮提交，并下沉成 replace_batch 这种事务性工具能力。
3. Prompt 只是软约束，涉及成本与稳定性的行为要落到工具协议、Hook 和执行引擎。
