# 多Agent协作的下一场竞争，不在模型，而在上下文

> 一句话定位：协作传递的是上下文，下一场竞争在上下文层而非模型。

## 摘要

腾讯技术工程的协作工具方法论。文章从一个被跳过的问题开始：协作到底在传递什么？答案不是消息，而是**上下文**——说出来的永远比脑子里的少，听者再解码又少一层，所以会议纪要、需求文档、复盘、周报本质上都在搬运和对齐同一件事，协作的全部难题就是上下文传递中的**折损**。当 Agent 上桌，问题不是变简单而是从加法变乘法：一条任务链的上下文可能被编码—解码四次（你的 Agent 产出 → 你转述 → 同事理解 → 同事的 Agent 产出），每多一层就继承前面的损耗再叠一层新的，人被卡在链路中间当中继器——"你越忙，整条链路越堵"。于是有两条路：让 Agent 更像人（把成果打包成总结再 @ 出去），或反过来——**不靠通信共享上下文，而靠共享上下文来通信**，把转述直接消灭掉。作者认为第二条路可行的关键前提是：Agent 做过什么、改了哪个文件、跑到第几步，本就是可实时记录、可被直接读取的结构化状态，而人的想法不说出来没有第二条通路。落地形态是司内协作工具 Siboot 的三件套：**群是场**（持续在场的上下文容器，新任务进来不必重新交代背景）、**Topic 是焦点**（议题独立成线、噪音物理隔离，Agent 窗口不被稀释，Topic 边界就是注意力边界和成本边界）、**@ 是接力**（只喊下一棒进场，不打包前因后果），构成"在场—聚焦—接力"的低折损流水线。还差一维是时间：话题会沉底、上下文会变冷，所以 Agent 得会管自己的文件——云盘分 inbox / notes / 需求与 BUG 档案 / 分层报告四区，定时任务自动拉群消息、判信号、先检索去重再登记，让冷上下文结构化沉淀，对人是"不用当外置硬盘"，对 Agent 之间是可跨时间读取的上下文源，对团队是白盒可治理。人则从中继器被解放：一条需求里人只动两下（开头确认值得做、结尾验收能不能上），剩下的是定目标、做判断、划边界、做验收——全是判断和责任，不是搬运信息。结论是横向共享、纵向沉淀，"别再让人给 Agent 当传声筒"。

## 要点

- 全文的重新定义：协作不是"发消息"，消息只是载体，真正流动的是**会不断折损的上下文**。所有协作工具的竞争因此落在上下文层。
- 折损的机制是编码—解码：脑子里的想法 → 说出口（少一层）→ 对方理解（再少一层）。听懂的人是少数，其余人都在等文档、等转述。
- 一小时会议的真实产出往往只是几个关键决策，但为了让它们流到每个人脑子里，团队还要付写文档、开同步会、反复答疑的代价，每传一手丢一点。
- 把 Agent 塞进旧工作流只解决了"进场"，没解决"上下文进群之后怎么流动"——这是很多 Agent 落地不好用的根因。
- **折损从加法变成乘法**：人-人-Agent 链路上每多一个节点就多一层转述，前面的损耗被继承后再叠一层。竞品分析那条链路被压缩了四次，细节不是被忽略，而是中途根本不存在。
- 人被卡成"中继器"：Agent 算得再快也要等你把上下文翻译给下一个节点，你越忙链路越堵——看起来在协作，其实在当传声筒。
- 第一条路（让 Agent 更像人：总结、@ 人、@ 下一个 Agent）不改任何人的习惯、很顺，但没碰问题的根：只要还靠"总结—转述—再理解"，折损就在，只是搬运从人挪到了 Agent。
- 第二条路的核心句：**不是用通信来共享上下文，而是用共享上下文来通信**。协作从"我把我知道的告诉你"变成"我们看着同一个现场一起干"。
- 这条路成立的技术前提：Agent 的状态天然是结构化、可读、可实时记录的（做过什么、改了哪个文件、跑到第几步），而人的想法不说出来就没有第二条通路——所以"消灭转述"对 Agent 是可行的，对人不是。
- 群＝**场**：一个持续在场的上下文容器。人说的话、Agent 做的事、产生的文件、跑起来的任务都在同一个空间里；新需求进来不用重新交代背景（"一句话就接住"），人和 Agent 都能各自按自己的需要去取上下文。
- Topic＝**焦点**：共享的天敌是噪音。一个群什么都往里装很快变一锅粥，Agent 会把闲聊、跑题、临时插话全当上下文吃进去，判断被污染、Token 白烧。按议题拆成独立 Topic，让上下文可界定、可隔离。
- **Topic 边界就是注意力边界和成本边界**：Topic 内的每个 Token 都花在这件事上。多 Agent 协作为什么会崩，很多时候不是模型不行，而是上下文没切干净。
- @＝**接力**：只负责喊下一棒进场，不打包前因后果——被 @ 的人和 Agent 本就站在同一条 Topic 的完整上下文里。反过来把接力做成"打包 + 转述"，就回到折损的老路。
- 三件套不是三个功能的堆叠，而是同一个协作哲学的三个切面：群回答"上下文在哪"，Topic 回答"哪些上下文属于这件事"，@ 回答"怎么交到下一棒"。整条链路里没有一次"把上下文从一个脑子搬到另一个脑子"。
- 只做横向（此刻共享）还不够，**纵向（时间）**是缺失的一维：群里的话题越聊越深、越往后沉底，Agent 的上下文会变冷——它不记得上周在另一个群里聊过什么。
- 对"更大上下文窗口"要祛魅：把所有历史塞进去既烧钱又低效，窗口再大也装不下团队几个月的全部信息。正解是分门别类写下来、需要时精准取回。
- 文件系统是 Agent 的记忆：云盘分四区——inbox（收件区，新反馈新想法先暂存）、notes（事实与决策记录，避免"忘了上次说过什么"）、reqs/bugs（有编号有来源有状态，可跟踪可检索可去重）、reports（日报周报月报各自归位）。
- 让沉淀自动发生：定时任务每隔一段时间醒来，拉群消息 → 判断有价值的信号 → 检索已有档案 → 命中则补充、否则登记 → 更新决策记录 → 落日报。关键是**登记前先检索去重**。
- 沉淀的三个视角：对人（不用再当 Agent 的"外置硬盘"，天天提醒它上次定了什么、文档在哪）、对 Agent 之间（一个 Agent 沉淀的结构化档案就是另一个 Agent 可直接读取的上下文源，是一次跨越时间的共享上下文）、对团队（文件系统是白盒，整理得对不对、沉淀了什么，人随时能看、能纠正）。
- 人的位置反而更清楚了：中转、搬运、同步这些胶水劳动被系统吃掉后，剩下的四件事——**定目标、做判断、划边界、做验收**——全是判断和责任，没有一件是搬运信息。
- 一条需求里人只动两下：开头确认这件事值得做，结尾验收功能能不能上；中间从"群里一句随口的话"到"测试环境 URL 摆在你面前"，人不需要出现。
- 全文结论：横向共享、纵向沉淀。模型决定每个节点有多强，**上下文管理决定整个网络能不能协同**；只在模型、工具、Agent 数量上内卷而忽略上下文层，是把竞争放错了地方。

## 提炼

- one_liner：协作传递的是上下文，下一场竞争在上下文层而非模型
- 各节要点：
  - 一、协作到底在传递什么：消息是载体，真正流动的是上下文；说出来的比脑子里的少，听者再解码又少一层；纪要/文档/复盘/周报都在搬运对齐上下文；协作的全部难题是上下文折损｜易错点：把协作当成"发消息"，只优化发消息
  - 二、折损按乘法叠加：Agent 塞进旧工作流只解决进场；每层转述继承前损再叠新损；一条链可能编码-解码四次；人被卡成中继器，越忙越堵｜易错点：只让 Agent 进场，不问上下文进群后怎么流动
  - 三、两条路：让 Agent 更像人（总结+@）折损仍在；反过来靠共享上下文来通信；Agent 的状态本身就是可读结构化状态；解法是消灭转述而非优化转述｜易错点：让 Agent 打包总结再转述，只是把搬运从人挪给 Agent
  - 四、Siboot：群=场（持续在场的上下文容器）、Topic=焦点（可界定、噪音隔离、窗口不稀释）、@=接力（只喊下一棒）；群→Topic→@ 是在场-聚焦-接力的低折损流水线｜易错点：一个群什么都装；把接力做成打包转述
  - 五、Agent 管自己的文件：横向是此刻同场，纵向是时间（话题沉底、上下文变冷）；热的在群与 Topic 共享，冷的在文件系统结构化沉淀；云盘四区 inbox/notes/reqs-bugs/reports；定时任务判信号、先检索去重再登记｜易错点：以为更大上下文窗口能解决记忆
  - 六、人的位置：人从中继器被解放，胶水劳动被系统吃掉；一条需求人只动两下（开头确认、结尾验收）；剩下定目标/做判断/划边界/做验收
  - 七、结语：胜负手在上下文能否低折损流动；模型决定节点强弱，上下文管理决定网络协同；群是场、Topic 是焦点、@ 是接力、文件是记性；横向共享、纵向沉淀｜易错点：只在模型/工具/Agent 数量上内卷
- 带走三句话：
  - 能直接读的结构化状态，不该先压成聊天记录再让机器逆向解码。
  - 别再让人给 Agent 当传声筒：横向共享、纵向沉淀，网络才立得起来。
  - 模型决定每个节点有多强，上下文管理决定整个网络能不能协同。
