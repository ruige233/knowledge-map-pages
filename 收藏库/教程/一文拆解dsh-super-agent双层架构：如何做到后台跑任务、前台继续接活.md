# 一文拆解DSH Super-agent双层架构：如何做到后台跑任务、前台继续接活

> 一句话定位：逐层拆开 DeepSeek 的 Super-agent 架构——Router/Worker 双层、事件驱动、存算分离与看门狗，把"多任务"瓶颈从人脑搬到系统。

## 摘要

本文是对 DeepSeek Harness 团队 2026-10-31 长文《Super-agent 设计探索：迈向更自主的 Agent 系统》的架构解读（作者朱进）。作者先厘清性质：这不是产品发布，而是工程实践的架构思路探讨，因此问题定义与系统设计讲得很干净。核心判断是"瓶颈换了位置"——单任务上限取决于模型能力，多任务上限取决于人的注意力（团队观察：一个人通常只能同时跟进 3 到 5 个活跃会话），于是 Super-agent 的目标是把会话管理与上下文同步从人手上移到系统层，人只负责目标与验收。文章给出 Super-agent 的四特征（连续、高效、主动、持久）与五组支撑模块，并依次拆解：Router（全局协调、不执行、甚至不配 Bash）与 Worker（隔离并发、不直接对人说话）的双层职责边界；事件驱动的 Fast Path（代码准入）与 Slow Path（LLM 语义判断）两级过滤，加 Thread 订阅直通与 Mandate 授权限定；存算分离（云端算、库里存、本地 daemon 跑）与独立 Watchdog；两个精巧设计（异步 ReAct 的 start()/stop()、投机执行"静默复现并修复"）；以及初步实验数据（P95 完成时间约快一倍、去掉订阅直通后 Router 决策 +30%、缓存 token +37%、批处理后单决定推理 6.4s→1.6s）。作者收在三点思考：算法无新意、赢在系统工程；职责边界写进结构比写进提示词可靠；主动性的落地路径是灰度。

## 要点

- 瓶颈换了位置：单任务上限取决于模型能力，多任务上限取决于人的注意力；团队观察一个人通常只能同时跟进 3 到 5 个活跃会话，模型越强矛盾越尖锐。Super-agent 的解法是把会话管理与上下文同步从人手上移到系统层。
- 四特征 + 五模块：连续（在 IM/GitHub/邮件里像只有一个 Agent）、高效（并行、不必等上一条命令跑完）、主动（观察环境事件、该动才动）、持久（长期在线、异常自动恢复）；整套设计没发明新理论，而是把调度、缓存、存算分离、看门狗、投机执行这些经典工程思想搬进 Agent 系统。
- 双层架构的职责边界：Router 承接多渠道消息、识别分派任务、维护全局上下文、统一对外回复，但不执行任务、甚至可以不配 Bash；Worker 是相互隔离的会话，挂完整工具链、用最强模型、只向 Router 汇报。职责边界由系统结构承接，不指望模型临场决定要不要委派。
- 事件驱动的两级过滤与订阅直通：Fast Path 用确定性代码做准入（来源、接收范围、准入条件），Slow Path 交给 LLM 按提示词策略判断；已确定归属的后续事件由程序直接发往订阅该 Thread 的 Worker，不再劳烦 Router。Thread 与 Worker 是多对多；订阅只给信息不加权限，超范围仍要重新分派；Mandate 限定授权范围防扩权。
- 持久在线靠三种分离 + 独立看门狗：执行循环在云端、会话状态入库、执行环境留在本地设备（只部署轻量 daemon）；Watchdog 借鉴嵌入式看门狗定时器，独立进程监督其他 Agent，监督者与被监督者分开部署，避免"自己检查自己"。
- 两个精巧设计与上下文管理：异步 ReAct 把耗时工具调用改成 start()/stop()，立即返回 Started、结果作为新事件回流，前台不阻塞（已实现但默认没开）；投机执行在结果未定时先后台尝试，"静默复现并修复"，宁可白干不可打扰；长程记忆靠 Inline & Spill（现在装多少）+ Chain of Recall（过去怎么找回）。
- 数据与代价：约 300 条消息、20 项工作请求的模拟环境各测 5 次，P95 完成时间比单 Session 快约一倍；去掉订阅直通后 Router 决策 +30%、读缓存 token 2323 万→3177 万（+37%）；Router 批处理把单决定推理从 6.4s 降到 1.6s。作者强调是合成负载的初步结果。
- 三点思考：算法上没什么新东西，赢在系统工程（Agent 下一程竞争可能在"操作系统"那一层）；职责边界写进结构比写进提示词可靠（不给 Bash、不对人说话、订阅不给权）；主动性靠灰度落地（先观察模式记录"本来会接什么"，再放开执行）。

## 提炼

- one_liner：用 Router/Worker 双层架构，把会话管理与上下文同步移到系统层
- 各节要点：
  - 瓶颈换了位置：编码场景里人工介入环节越来越少，人的角色上移到定目标、验结果；主流 Agent 的工作单位仍是单次 Session，多任务要人手动开多个会话并记住上下文；人通常只能同时跟进 3 到 5 个活跃会话，这就是多任务的真实上限；单任务上限取决于模型能力，多任务上限取决于人的注意力
  - Super-agent 是什么：定义：打破 Agent 与单次手动会话的绑定，成为跨会话保持上下文的连续实体；四个特征：连续、高效、主动、持久；连续指在 IM、GitHub、邮件里交互，感觉始终只有一个 Agent；没有提出新理论，是把调度、缓存、存算分离、看门狗、投机执行搬进 Agent 系统
  - 双层架构：Router 管协调，Worker 管干活：Router 是持续运行的全局协调节点，承接多渠道消息、识别归属分派、统一对外回复；Worker 是隔离会话，挂完整执行工具链与最强模型，不直接对人说话，可再调 Subagent；职责边界由系统结构承接，不指望模型临场决定要不要委派；开源原型用 Ticket 组织任务，面板集中显示等待回答、等待审查、受阻事项｜易错点：所有消息进同一会话：执行串行阻塞、不同任务细节互相污染；每条消息都新开会话：并发好做，但全局协调与交互一致性丢失
  - 事件驱动：先代码过滤，后模型判断：主要输入从人键入的提示词变成群聊、邮件、评审、CI 等半结构化环境事件（Trigger）；真实环境高噪音低触发率，每条消息都过模型，成本和延迟都撑不住；Fast Path 用确定性代码做准入门槛检查，Slow Path 交给 LLM 按提示词策略判断；已归属事件由程序直发 Worker，Thread 由 Worker 订阅，后续评论与 CI 直达；原型默认观察模式：先记录本来会接什么任务，验证可靠后再放开自动执行｜易错点：把订阅当授权：订阅只提供信息，超范围要求仍要重新分派
  - 持久在线：存算分离加看门狗：始终在线要拆成三件事：计算放哪、状态存哪、环境跑在哪；执行循环在云端，会话状态入库，执行环境留在本地，本地只跑轻量 daemon；合盖后云端任务状态仍在，设备重新上线 daemon 接着跑；Watchdog 由独立进程监督 Agent，检测程序故障与目标偏离并尝试修复｜易错点：监督者与被监督者部署在一起，会留下自己检查自己的盲区
  - 两个精巧的小设计：异步 ReAct：耗时工具调用改成 start()/stop()，启动即返回 Started，结果作为新事件回流；投机执行：结果是否被采用尚未确定就先后台尝试，有价值再交付，否则丢弃；静默复现并修复：确认问题存在且找到简单修法才提交，否则保持安静；长程记忆靠 Inline & Spill（现在装多少）与 Chain of Recall（过去怎么找回）｜易错点：耗时工具调用仍用同步 ReAct，整个会话干等十几分钟
  - 数字说话：实验结果与代价：实验环境约 300 条消息、20 项工作请求，每种配置重复测试 5 次；P95 口径下 Super-agent 完成时间比单 Session 方案快约一倍；去掉订阅直通：Router 决策次数增加约 30%，读缓存 token 从 2323 万涨到 3177 万；Router 批处理把单个决定分摊的推理时间从 6.4 秒降到 1.6 秒；拿更多 token 换时间与稳定性，实验基于合成负载，只是初步参考｜易错点：忽略成本口径：省下的 Router 决策与 token 是真金白银，去掉路由机制代价明显
  - 几点思考：算法上没什么新东西，赢在系统工程：把分布式系统与 OS 的老组件重组进 Agent Runtime；职责边界写进结构比写进提示词可靠：Router 不装 Bash、Worker 不直接对人说话；不确定模型每次选对，就把它物理上做不到的事从能力清单里删掉；主动性落地靠灰度：观察模式验证后再放开，投机执行宁可白干也不打扰；个人助手与商业 Agent 只要持续在线、并发响应事件，底层架构相通｜易错点：指望用提示词约束模型自觉，而不是用架构结构与授权范围约束
  - 结语：Super-agent 没发明新理论，只是把「从把单件事做好到同时管好很多件事」的趋势说清；会话管理、上下文同步、异常恢复这些原本由人脑承担的成本正被系统架构接走；人剩下定目标与验结果，但验收能力可能成为新的瓶颈
- 带走三句话：
  - Agent 的下一程竞争可能不在模型榜单，而在谁先把「操作系统」那一层做扎实。
  - 职责边界写进系统结构比写进提示词可靠；会不会放权不该是模型的发挥题。
  - 主动性的落地押在更保守的交付策略上：先观察再放开，宁可白干也不打扰人。
