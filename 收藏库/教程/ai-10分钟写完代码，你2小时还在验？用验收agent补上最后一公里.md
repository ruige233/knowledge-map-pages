# AI 10分钟写完代码，你2小时还在验？用验收Agent补上最后一公里

> 一句话定位：用验收 Agent 以 L1–L4 多层证据链验证 AI 生成的后端代码。

## 摘要

腾讯医疗业务团队在自建的 OPT（One Person Team）平台上做的实践总结（原创作者：吴思）。问题定义很直接：AI 把"生成代码"变容易之后，人工"需求验收"成了交付链条上的新瓶颈——接口返回 200 只说明调用完成，需求逻辑、边界条件、老数据处理、异步任务、日志与 DB 状态都还没被证明。解法是在需求交付小队里补一个后端验收 Agent，其执行内核是 `api-acceptance` Skill，主流程拆成五个阶段：变更接口分析（用 git diff、需求描述、接口定义反推验收范围与兼容性风险）、编译发布及接口验证（确认"能否验"）、Gherkin 场景设计与执行（用 Given-When-Then 把需求拆成可确认可执行的场景，确认报告必须人工确认）、TAPD 预测试（补充用例来源并做"后端可验"范围分类）、结果输出（用 L1 接口返回 → L2 业务状态 → L3 链路与异步 → L4 静态 Review 的多层证据链下结论）。文中特别强调两种设计：异常分"硬阻塞"与"软失败"，能验证的尽量验证、不能验证的诚实标注；以及"接口 code=0 不等于通过"的四类表面成功假象。落地数据：运行 160+ 次，覆盖 30+ 需求、80+ 入口接口、800+ Gherkin 场景，20+ 条问题在开发阶段被发现并打回；单次验收人工投入从约 2 小时降到 20 分钟（降 80%+）。

## 要点

- 速度差的本质：AI 代码生成速度 >>> 人工需求验收速度。要解决的不是"让 AI 再多写一点代码"，而是让人更快更稳地判断代码是否真可用。
- 验收 ≠ 代码已生成 ≠ 接口能调通。一个 200 只说明当前参数下完成了一次调用，需求逻辑、边界、老数据兼容、异步生效、日志与 DB 状态仍要单独验证。
- `api-acceptance` 五阶段主流程：变更接口分析（验哪里）→ 编译发布及接口验证（能否验）→ Gherkin 场景设计执行（怎么验）→ TAPD 预测试（补充用例与范围分类）→ 结果输出（怎么判）。
- 硬阻塞 vs 软失败：硬阻塞保证 Agent 不越过必要的人机确认与环境前提；软失败让 Agent 在发布失败、spec 缺失、日志不可用等受限情况下继续做变更分析、场景生成、静态 Review 与风险标注。核心原则：能验证的尽量验证，不能验证的诚实标注，不把受限项伪装成通过。
- 变更接口分析决定验收方向：从 git diff、需求描述、分支信息、接口定义反推出测试接口列表，并标注需求契约与兼容性风险（直接影响边界场景覆盖）。
- Gherkin 是需求预期的载体，因此场景确认报告必须人工确认后才进入真实执行——重点看前置条件、接口选择、关键参数与 Then 预期；预期错了，报告只会更有迷惑性。
- 参数构造的来源优先级：真实数据优先，LLM 推理只做兜底；业务测试知识库（鉴权说明、测试账号、数据构造方法、业务字段知识）不全是 Agent 掉进 WARN/SKIP/无法判定的主因。
- 环境选择优先级：Agent 任务专用隔离环境 > 个人开发环境 > 公共测试环境，减少污染、便于复现。
- 多层证据链 L1–L4：L1 接口返回（响应码/字段/契约）→ L2 业务状态（配对查询接口/DB/日志）→ L3 链路与异步（下游调用/消息/消费/日志）→ L4 静态 Review（无法联机时读 handler/service/调用链兜底）。对应四类"表面成功"假象。
- 从单点工具到完整链路：验收 Skill 只是内核，作为后端验收 Agent 被编排进 OPT 需求交付小队（需求分析 → 方案规划 → 编码实现 → 代码验收），Leader 调度、人确认预期与最终结论，验收不通过打回代码实现后复验。
- 四条体会：确定性先于自动化（先定"要验什么、怎么算对"）；事实密度影响可靠性；尽量用证据链支撑结论；边界标注（WARN/SKIP/无法判定）比表面全绿更可信；最终可交付判断仍留在人这一侧。

## 提炼

- one_liner：用验收 Agent 以 L1–L4 多层证据链验证 AI 生成的后端代码
- 各节要点：
  - 业务背景与痛点（生成快、验收慢）：OPT 平台以 CodeBuddy 等 CLI 为运行时，多 Agent 小队完成需求分析、规划与开发；AI 代码生成速度远快于人工需求验收速度，验收成为新瓶颈；接口返回 200 只说明调用完成，需求逻辑、边界、老数据、异步仍需验证｜易错点：把代码已生成或接口能调通直接当成验收通过
  - 解决方案与案例详解（api-acceptance 五阶段）：五阶段=变更接口分析、编译发布及接口验证、Gherkin 测试、TAPD 预测试、结果输出；异常分硬阻塞与软失败——能验证的尽量验证，不能验证的诚实标注；Gherkin 场景确认报告必须人工确认后才能进入真实执行；用 L1–L4 证据链判定，结论分四档并以 HTML 报告呈现｜易错点：接口返回 code=0 就写通过、只让 Agent 按接口定义自行执行而漏掉业务预期
  - 实践效果（提效、提质、规模化）：运行 160+ 次，覆盖 30+ 需求、80+ 入口接口、800+ Gherkin 场景；30+ 需求中 10+ 次验收未通过，20+ 条问题被发现并打回修复；单次人工验收约 2 小时降至 20 分钟，投入下降 80%+；验收步骤沉淀为 Skill，已推广到其他医疗相关业务复用
  - 一些体会（确定性先于自动化）：先明确要验什么、怎么算对，再交给 Agent 执行；事实密度决定可靠性，接口用例、账号、日志、DB、知识库越全越可靠；不可验证部分标注 WARN、SKIP 或无法判定，比表面全绿更有价值；Agent 出初验与证据，最终可交付判断仍由人承担｜易错点：追求表面的全绿，把受限项伪装成通过
- 带走三句话：
  - AI 生成代码越快，人工需求验收越容易成为交付链条上的新瓶颈。
  - 验收结论要建立在接口返回、业务状态、链路异步与静态 Review 的多层证据上。
  - 先明确要验什么、怎么算对，再让 Agent 承担重复执行，并把责任边界留在人这一侧。
