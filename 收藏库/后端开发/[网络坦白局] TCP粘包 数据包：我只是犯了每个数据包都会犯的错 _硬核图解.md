# [网络坦白局] TCP粘包 数据包：我只是犯了每个数据包都会犯的错 _硬核图解

> 一句话定位：图解 TCP 粘包：根因是字节流无边界，解法是发送端自定义消息边界。

## 摘要

本文以漫画图解 TCP 粘包。先从四层模型与 MTU/MSS 讲起：消息逐层加报头，超长需分片，MTU=1500 时 MSS=1460 字节。随后用“李东”“亚健康终结者”被拼成“李东亚”的例子引出粘包，指出 TCP 面向字节流、01 串无边界是根因。Nagle 算法会合并小包省 IO，但关闭它后接收端不及时读 Recv Buffer 仍会粘包。解决思路是发送端加边界信息：特殊标志（0xfffffe）、消息长度（类似 Content-Length）并配校验字段。最后对比 UDP：基于数据报、保留边界不粘包；IP 层只切片运输，也无粘包问题。

## 要点

- 四层网络模型每层加报头，网络接口层以 MTU（一般 1500 字节）限制单次传输，超长消息需分片。
- MSS 是 TCP 交给 IP 层的最大分段（不含 IP/TCP 头），MTU=1500 时 MSS=1460 字节。
- TCP 面向字节流，01 串之间没有边界，接收端拿多拿少就会粘包，根因是消息边界不确定。
- Nagle 算法为省网络 IO 合并小包、延迟发送（约 200ms），但关闭它并不解决粘包。
- 解决粘包要在发送端带边界信息：特殊标志（0xfffffe）、消息长度（类似 Content-Length），并配校验字段。
- UDP 基于数据报、既不合并也不拆分，保留报文边界，因此不会粘包。
- IP 层虽按 MTU 切片重组，但只管运输、不关心内容，所以没有粘包问题。
- 粘包不是 TCP 的问题，是开发者对“面向字节流”理解有误。

## 提炼

> 一句话定位：图解 TCP 粘包：根因是字节流无边界，解法是发送端自定义消息边界。

### 分节提炼

- **01 四层网络模型**：每层各加报头：MAC 头记硬件唯一地址，IP 头记来源与目的地，传输层头记目标进程。；消息发出前层层加报头，接收端再层层还原出原始消息。
- **02 MTU 与 MSS**：MTU 由数据链路层提供给网络层，一般 1500 字节，超过需分片，分片后 IP Header ID 相同。；MSS 只含 TCP Payload，MTU=1500 时 MSS=1460；2000 字节分 1460 + 540 两片。
- **03 粘包现象**：“李东”“亚健康终结者”重组为字节流后被误解析成“李东亚”“健康终结者”，这就是粘包。
- **04 根因：字节流无边界**：TCP 是面向连接的、可靠的、基于字节流的传输层通信协议。；应用层数据以字节流发送，可能被切割和组装，接收端无法还原边界就粘包。
- **05 Nagle 算法**：小包单独发送浪费网络 IO，Nagle 算法合并小包以省开销。；达 MSS/含 Fin 立即发，否则等下一包；超时约 200ms 也立即发送。
- **06 关掉 Nagle 仍粘包**：Nagle 诞生于 1984，如今帮助不大且可能增加调用延时，现在一般关闭（TCP_NODELAY=1）。；关闭 Nagle 后，接收端应用层没及时读 TCP Recv Buffer，仍会粘包。；解决粘包要发送端带边界信息：特殊标志、消息长度，并配校验字段。
- **07 UDP 不粘包**：UDP 面向无连接、不可靠、基于数据报，不合并不拆分，保留报文边界。；UDP 头 16bit 长度字段作数据边界，即便冗余，也在传输层提供边界信息。；TCP 首部无长度信息，按公式算出长度也无法确定完整消息边界。
- **08 IP 层无粘包**：IP 层按 MTU 切片，切片带 offset 与相同 IP 头，终点汇合重组后交上层。；IP 只负责运输、不关心消息内容与边界，因此没有粘包问题。
- **09 总结**：粘包根因是开发者没正确理解 TCP 面向字节流，不是 TCP 的问题。；TCP 粘包与 Nagle 有关，但关闭 Nagle 不解决；UDP、IP 层都不会粘包。

### 带走三句话

1. 粘包的本质是消息边界不确定：TCP 面向字节流，01 串无边无界，接收端拿多拿少都会拼错消息。
2. 解决粘包靠应用层自己定边界：特殊标志 + 消息长度 + 校验字段，别指望关掉 Nagle。
3. 面试可记：TCP 会粘包、UDP 不会、IP 层切片但不粘包，根因是开发者不懂字节流。
