# 微服务架构下网关的技术选型

> 一句话定位：微服务下网关技术选型全景：职责、设计重点与主流网关对比

## 摘要

本文梳理微服务架构下 API 网关的技术选型。单体拆分后微服务直接暴露会带来安全、耦合、API 粒度不匹配、协议不友好与重构困难等问题，网关作为接入层与业务层之间的基础组件，承担请求接入、业务聚合、中介策略与统一管理四大职能。网关设计需具备请求路由、服务注册、负载均衡、弹力设计、安全、灰度发布、API 聚合与编排等能力，并以高性能、高可用、高扩展为设计重点。文章区分流量网关与业务网关，并对比四款主流网关的特点与适用场景，强调按业务场景选型。

## 要点

- 单体拆微服务后直接暴露服务会带来安全、内外耦合与 API 粒度不匹配等问题。
- API 网关是位于接入层与业务服务层之间的基础组件，具备请求接入、业务聚合、中介策略、统一管理四大职能。
- 网关设计应具备请求路由、服务注册、负载均衡、弹力设计、安全、灰度发布、API 聚合与编排等功能。
- 网关设计重点是高性能（异步非阻塞 I/O）、高可用（集群化、服务化、持续化）与高扩展（可二次开发）。
- 流量网关专注全局 API 管理策略，如全局限流、黑白名单、负载均衡；业务网关更靠近业务，负责接口管理、协议适配、熔断限流等。
- OpenResty/Kong 属流量层网关，Kong 基于 OpenResty 插件化扩展；Zuul2 改用 Netty 实现前后端异步模型。
- Spring Cloud Gateway 基于 Spring 5、Spring Boot 2 与 Project Reactor/WebFlux 构建，目标替代 Zuul。
- 技术选型需按业务场景、流量与并发取舍：Kong 适合流量网关，复杂业务系统不建议用 Kong。

## 提炼

> 一句话定位：微服务下网关技术选型全景：职责、设计重点与主流网关对比

### 分节提炼

- **01 简介**：单体应用通过负载均衡分发到同质实例，微服务拆分后不宜全部直接对外暴露。；客户端直连微服务存在 API 粒度不匹配、协议非 Web 友好、服务难以重构三大问题。；网关位于接入层之下、业务服务层之上，四大职能为请求接入、业务聚合、中介策略、统一管理。；网关粒度可细到单实例、粗到整个架构，可用多层 Gateway 组织成星型架构。
- **02 网关设计思路**：网关应具备请求路由、服务注册、负载均衡、弹力设计、安全、灰度发布、API 聚合、API 编排等能力。；弹力设计含异步、重试、幂等、流控、熔断、监视，让应用只关注业务逻辑。；负载均衡可由 Round-Robin 轮询到权重分发再到 session 粘连逐步增强。；API 聚合将多个请求合并为一个，缓解客户端与后端频繁通信的性能问题。
- **03 网关设计重点**：高性能：用 C/C++/Go/Java 等语言，前后端请求采用异步非阻塞 I/O，如 epoll、IOCP、Netty、Spring Reactor。；高可用：集群化（自行同步数据）、服务化（Admin API 运行时改配置）、持续化（优雅重启）。；高扩展：网关需可二次开发，如 Nginx Module 方式。；运维原则：业务松耦合协议紧耦合、应用监视提供分析数据、弹力设计保护后端、引入 DevOps。
- **04 设计注意事项**：聚合服务不应内置在网关核心代码，可用 Plugin 或网关后的 Serverless 实现。；网关应贴近后端同内网部署，静态内容放 CDN 靠近用户。；服务发现可做短时间缓存；简单系统可把服务发现集成进网关。；安全事宜：SSL 证书统一管理、校验用户请求需权衡协议体解析开销、检测异常访问并告警。
- **05 流量网关**：流量网关控制进入集群的流量，拦截非法无效请求，降低集群流量压力。；流量网关专注全局 API 管理策略：全局流量监控、日志、全局限流、黑白名单、负载均衡，类似防火墙。；Kong 是典型流量网关；业务网关部署在流量网关之后、业务系统之前，二者无严格界线。
- **06 业务网关**：微服务拆分后权限、日志、加密、熔断限流等功能重复实现且差异大，维护成本高。；业务网关需具备接口管理、协议适配、熔断限流、安全防护等功能，如 Zuul。；业务网关更靠近业务，处理线程模型、协议适配、熔断限流、服务编排等应用层事项。；较成熟的框架产品有 Zuul1、Zuul2 与 Spring Cloud Gateway。
- **07 常见网关对比**：常见开源网关按语言分类：Nginx+Lua（OpenResty/Kong）、Java（Zuul 系列）、Go、Dotnet、NodeJS。；OpenResty 是基于 Nginx+Lua 的高性能 Web 平台，定位流量网关。；Kong 基于 OpenResty，插件化、可水平扩展，提供认证、流量管制、可视化监控等能力。；Zuul2 用 Netty 替代 Servlet/Http Client 实现前后端异步，Inbound/Endpoint/Outbound Filters 替换旧过滤器。；Spring Cloud Gateway 基于 Spring 5、Spring Boot 2、Project Reactor 与 WebFlux/Netty，目标替代 Zuul。
- **08 几种网关的对比**：不同业务场景应选择不同网关组件，应对不同流量和并发。；Kong 性能好适合做流量网关，但复杂业务系统不建议用 Kong。；Spring Cloud Gateway/Zuul2 对 Java 技术栈方便，但对 Lua 开发不方便。

### 带走三句话

1. 网关是微服务的基础组件，核心在请求路由、聚合、安全与弹力设计，并须保证高性能、高可用、高扩展。
2. 流量网关管全局策略、业务网关管应用层业务事项，二者无严格界线，选型要按业务场景和流量取舍。
3. OpenResty/Kong 适合流量层，Java 栈选 Zuul2 或 Spring Cloud Gateway，复杂业务系统不建议用 Kong。
