# 十行代码让日志存储降低80%

> 一句话定位：三层极简日志分层，堆栈倒打+类名压缩让堆栈存储压缩比达88%

## 摘要

本文复盘履约管理系统日志治理实践。作者指出日志是熵增最快的模块，常见乱象有三：分类之乱、格式之乱、工具之乱。治理方案采用极简设计：日志只分入口、内核、出口三层，入口记流量出入参，出口记第三方调用出入参，内核记业务过程，堆栈单独拎出。格式上遵循人可读与可监控原则，维度因子抽到 ThreadLocal，约定大于配置、固定位置逗号分隔，拒绝大而全 JSON 与自定义格式。堆栈采用倒打，把错误源头置顶，并支持 cause 层数与堆栈层数配置化；堆栈行类名压缩为包路径首字母+类名+方法:行号，压缩比达88%。

## 要点

- 日志是系统中熵增最快的模块，最易被忽视和滥用
- 日志乱象集中在分类、格式、工具三方面
- 日志按职能水平拆分为入口、内核、出口三层，简单且不重不漏
- 格式遵循人可读与可监控，维度因子放 ThreadLocal 传参
- 格式采用约定大于配置，固定位置逗号分隔，拒绝大 JSON 与自定义扩展
- 堆栈倒打把错误源头置顶，并配置化截断 cause 与堆栈层数
- 类名压缩为首字母路径+类名#方法:行号，堆栈压缩比达88%
- 方案需量体裁衣，中台场景有效，富客户端需本土化改造

## 提炼

> 一句话定位：三层极简日志分层，堆栈倒打+类名压缩让堆栈存储压缩比达88%

### 分节提炼

- **01 背景与接手**：履约管理是面向物流商家的OMS工作台，长期无主、野蛮生长；行业共建但不支持行业隔离会加速系统腐化
- **02 三大乱象总览**：打日志门槛低，随手info调用，不确定能否打出、打在哪个文件；格式内容千差万别，LogUtil多达二三十个，破窗效应明显
- **03 分类乱象**：按系统模块分最有层次感，每层对应一个日志文件；按租户身份分一般不单独使用，除非完全租户隔离；意识流分类法违反MECE，分几十个文件，打日志者不知落点
- **04 格式乱象**：复杂分隔符组合与关键词定位增加人脑和计算机解析负担；同一日志文件混入堆栈和正常业务日志
- **05 工具乱象**：不同工具差别在参数类型、业务场景、异常封装；同一类同一方法两行日志可能格式、文件都不同
- **06 三层日志分层**：一级分类采用按职能水平拆分，业务边界难划清；三层：入口记流量出入参、出口记三方调用出入参、内核记业务过程；堆栈日志特殊性大，单独拎出，降本只针对堆栈
- **07 格式设计原则**：设计面向人可读，同时面向可监控；监控维度因子抽出来存ThreadLocal，打印时从上下文取；约定大于配置，每维度固定位置逗号分隔，内容自解释、见名知义
- **08 格式模板**：模板包含时间|线程 级别 logger|维度|业务码等字段
- **09 内容样例**：示例展示维度值、出入参JSON按模板输出的完整效果
- **10 堆栈倒打与压缩**：SLS默认折叠，最底层异常才是错误源头，需点开拉到底；堆栈倒打将最底层异常置顶，瞟一眼即可知原因；cause层数与错误堆栈层数可配置化；类名压缩：类名全打、包路径只打首字母、保留行号
- **11 适用边界**：最佳实践是伪命题，要指明适用范围；方案在中台应用落地，富客户端场景需本土化改造；堆栈降本不等于整体日志降本

### 带走三句话

1. 日志先按职能水平拆成入口、内核、出口三层，简单不重不漏，堆栈单独拎出。
2. 格式面向人可读和可监控，维度存 ThreadLocal，固定位置逗号分隔，拒绝大 JSON。
3. 堆栈倒打置顶错误源头并压缩类名，堆栈压缩比可达88%，整体降本需量体裁衣。
