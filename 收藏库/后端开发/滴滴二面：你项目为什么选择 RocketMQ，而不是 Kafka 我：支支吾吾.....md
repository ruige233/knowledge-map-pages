# 滴滴二面：你项目为什么选择 RocketMQ，而不是 Kafka 我：支支吾吾....

> 一句话定位：业务消息场景，RocketMQ 凭事务消息、延迟消息、同步双写胜过 Kafka。

## 摘要

文章解析“项目为何选 RocketMQ 而非 Kafka”这一面试题。面试考察技术选型能力、消息中间件全局认知与实践结合原理；核心答案是“三高一丰”：高吞吐（单机 TPS 10 万+）、高可靠（同步双写+同步刷盘）、高一致（原生事务消息）、功能丰富（延迟/顺序/回溯/过滤）。正文先横向对比三大 MQ 定位，再展开六大理由：原生事务消息、高可靠、延迟消息、顺序消息、消息过滤、全 Java 技术栈，配关键代码示例。最后给出选型决策树（大数据 Kafka、轻量 RabbitMQ、业务消息 RocketMQ）、高频追问与口诀，强调面试应场景驱动选型、结合项目需求作答。

## 要点

- 面试考察点：技术选型能力、消息中间件全局认知、实践与原理结合。
- 核心答案概括为“三高一丰”：高吞吐、高可靠、高一致、功能丰富。
- 横向对比：Kafka 定位大数据消息流平台，RabbitMQ 轻量低延迟，RocketMQ 面向业务消息。
- 选 RocketMQ 六大理由：原生事务消息、高可靠、延迟消息、顺序消息、消息过滤、全 Java 栈。
- 事务消息靠半消息+本地事务+二次确认+回查保证最终一致性，无需引入 Seata。
- 高可靠靠同步刷盘+同步复制双重保障；Kafka 默认异步刷盘可能丢消息。
- 延迟消息 18 个固定等级（5.0 后任意延迟），Kafka 需借助外部定时任务。
- 选型决策：大数据 Kafka、中小型 RabbitMQ、业务消息 RocketMQ；面试要场景驱动作答。

## 提炼

> 一句话定位：业务消息场景，RocketMQ 凭事务消息、延迟消息、同步双写胜过 Kafka。

### 分节提炼

- **01 主流 MQ 横向对比**：Kafka 定位大数据消息流平台，追求极致吞吐，但业务消息场景可靠性与功能不如 RocketMQ。；RabbitMQ 延迟最低但吞吐仅万级，Erlang 栈难排查；RocketMQ 全 Java、吞吐高一个数量级。
- **02 六大核心理由**：六大理由：原生事务消息、同步双写高可靠、延迟消息、顺序消息、服务端过滤、全 Java 技术栈。；事务消息：半消息→本地事务→二次确认→回查，保证最终一致性，无需引入 Seata。；同步刷盘+同步复制双重保障金融级不丢失；Kafka 默认异步刷盘可能丢消息。；延迟消息 18 个固定等级（5.0 后任意延迟）；顺序消息靠队列路由+单线程消费；Tag/SQL92 过滤。
- **03 选型决策树**：大数据选 Kafka（与 Spark/Flink 深度集成），中小型系统选 RabbitMQ（轻量、路由灵活）。；业务消息场景只要满足事务/延迟/高可靠/Java 栈任一需求，RocketMQ 就是最优解。；消息不丢失：生产同步发送+重试，Broker 同步刷盘+复制，消费手动 ACK+死信队列。；口诀：大数据选 Kafka，轻量选 Rabbit，业务消息选 Rocket。
- **04 总结**：选型核心逻辑：业务消息场景下 RocketMQ 提供事务、延迟、同步双写等 Kafka/RabbitMQ 不具备或不擅长的特性。；面试应场景驱动选型，结合项目实际需求举例，而非泛泛罗列优点。

### 带走三句话

1. 选型别背参数：先判断场景——大数据 Kafka、轻量 RabbitMQ、业务消息 RocketMQ。
2. 事务消息是杀手锏：半消息+回查实现最终一致性，可省掉 Seata 这类分布式事务框架。
3. 面试答法要场景驱动：结合订单超时取消等真实需求说明选型，而非罗列优点。
