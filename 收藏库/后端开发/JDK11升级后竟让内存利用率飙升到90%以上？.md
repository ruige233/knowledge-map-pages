# JDK11升级后竟让内存利用率飙升到90%以上？

> 一句话定位：JDK11 下 G1 分区策略与记忆集占用把堆用满，缩堆即可解决

## 摘要

从 JDK8 升 JDK11 后，上线半月内存利用率超 85%，G1 Old GC 不回收，重启后仍涨到 90% 以上。排查发现根因不是泄漏：G1 分区启发式分配尽量填满堆并更快分配物理内存，CMS 则固定回收阈值、低负载下部分内存不触碰；加上记忆集占用偏大，12g 堆 + 2.25g 记忆集 + 700m 全局内存 + 非堆约 16g，逼近容器上限，缩堆到 8G 解决。随后讲解 GC 算法、G1 回收循环与参数调优，给出堆设为容器一半的经验。

## 要点

- 线上 JDK11 升级后内存利用率超 85%，G1 Old GC 不回收，重启后仍涨到 90% 以上
- 根因是 G1 Region 策略尽量填满堆内存并更快 touch 物理内存，叠加记忆集（RSet）占用
- 12g 堆 + 2.25g 记忆集 + 700m 全局内存 + 非堆 ≈ 16g，逼近容器内存上限
- 解决：堆从 12G 缩到 8G；经验为 8G 容器堆设 4G、16G 容器堆设 8G
- G1 在 Young-only 与 Space-reclamation 两阶段交替，Mixed GC 增量回收老年代防 Full GC
- JDK11+G1 对比 JDK8+CMS：max-jOPS +17%、critical-jOPS +105%，YGC 暂停 311ms→177ms
- 参数调优：删 -Xmn、IHOP 设 40 并关闭自适应、G1HeapWastePercent 降 2、预留堆外开销
- Netty 需加 tryReflectionSetAccessible 与 add-opens 参数，解决堆外内存增 600M

## 提炼

> 一句话定位：JDK11 下 G1 分区策略与记忆集占用把堆用满，缩堆即可解决

### 分节提炼

- **01 升级背景**：7 月通过集团流水线从 JDK8 升级到 JDK11；预发测试通过后上线，GC 次数明显下降
- **02 故障现象**：上线稳定半个月后内存利用率超 85% 告警；现象：内存利用率一天内不降、G1 Old GC 升高不回收；JVM 参数只保留了 -Xms12g -Xmx12g
- **03 临时处置**：保留一台 beta 机器观察，其余批量重启；重启后内存下降，初步认定 G1_OLD 区未触发回收
- **04 持续观察**：beta 机器未重启，内存利用率最终超过 90%；内存随运行时间持续增长，重启只能临时缓解
- **05 解决方案**：将堆内存缩减到 8G 后问题解决；经验：8G 容器堆建议 4G，16G 容器堆建议 8G
- **06 GC 基础**：指针碰撞靠移动空闲指针分配，回收后只能继续往后分配；空闲列表记录空闲块，查找合适大小分配；多线程下 TLAB 每线程独立分配，TLAB 不足才进 Eden
- **07 回收算法与分代**：标记-清除产生碎片；标记-复制内存只能用一半，改进为 8:1:1 三区；标记-整理向一端移动，无碎片但需 STW；新生代用标记-复制，老年代用空闲列表分配回收
- **08 吞吐与延迟**：高吞吐是单位时间回收量，低延迟是暂停时间短；二者权衡：提吞吐可能加长单次回收，降延迟可能增加次数
- **09 策略演进**：演进方向：CMS → G1 → ZGC，逐步优化低延迟；硬件内存提升使更频繁 GC 换取稳定响应成为可能
- **10 CMS 收集器**：CMS 首个关注 STW 停顿，mark-sweep 标记清除；三色标记改进可达性分析，标记清除阶段可与用户线程并行；碎片多时 CMS 触发标记-整理压缩堆
- **11 G1GC 特性**：G1 追求软实时，偶尔超期可接受（如网银场景）；两个功能：设置期望暂停时间与可预测性
- **12 Region 分区**：堆划分为相同大小 Region，类型 Eden/Survivor/Old/Humongous；对象大于 Region 50% 视为大对象，放 Humongous 减少拷贝
- **13 回收循环**：G1 在 Young-only 与 Space-reclamation 两阶段交替；Young-only 逐步用晋升对象填满老年代；空间回收阶段增量回收老年代，不必一次 STW
- **14 Young-only 阶段**：Young-only 主要做 Minor GC，存活对象晋升老年代；老年代达 IHOP 阈值触发并发标记周期；并发标记完成后经 Remark 与 Cleanup 决定是否进入 Mixed GC
- **15 空间回收阶段**：Mixed GC 同时清理年轻代与部分老年代；按回收性价比选 Region，疏散存活对象后释放
- **16 三种 GC 类型**：Young GC 只回收新生代，STW 且 young 区动态调整；Mixed GC 先全局并发标记，再选高收益 Region 回收；Full GC 用 Serial Old 单线程原地压缩，应尽量避免
- **17 G1 vs CMS**：CMS 自 JDK11 正式废弃，不鼓励在 JDK8 使用；G1 自动整理堆内存减少碎片，官方推荐替代 CMS
- **18 性能数据**：JDK11+G1 较 JDK8+CMS：max-jOPS +17%；critical-jOPS 提升 105%，YGC 暂停降至 177ms；吞吐 92.7% 升至 94.7%
- **19 内存复盘**：物理内存按需分配，只有写入虚拟内存才真正分配；G1 Region 启发式尽量填满堆，比 CMS 更快 touch 全部堆内存；G1 每 Region 有 RSet 记录谁引用我，CMS 卡表记录我引用谁；跨区引用经写屏障进 DCQ，由 Refine 线程过滤后写入 RSet
- **20 总结**：12g 堆 + 2.25g 记忆集 + 700m 全局内存 + 非堆 ≈ 16g，逼近容器上限；CMS 固定老年代回收阈值，低负载下部分内存不被触碰
- **21 解决方案**：-XX:+AlwaysPreTouch 启动时预分配物理内存，避免运行时延迟；G1 下缩小堆通常不会 OOM，堆内存约占容器一半较合适
- **22 参数调优**：堆大小建议调低 5-8% 以留出 G1 堆外开销；-Xmn 替换为 -XX:MaxNewSize，G1 不要固定 Xmn；IHOP 建议 40 并关闭自适应，G1HeapWastePercent 可降到 2
- **23 IHOP 详解**：IHOP 是触发初始标记的老年代占用百分比阈值；默认自适应 IHOP 动态调整，默认初始值 45%；关闭自适应后由 InitiatingHeapOccupancyPercent 固定阈值
- **24 Netty 优化**：必须加 tryReflectionSetAccessible 与 add-opens 参数；该设置解决堆外内存增加 600M 的问题
- **25 参考资料**：G1 官方介绍与调优文档；深入理解 JVM、Java 性能权威指南等书籍

### 带走三句话

1. JDK11 默认 G1 会尽量填满堆并更快分配物理内存，12G 堆叠加上记忆集后逼近 16G 容器上限。
2. 升级 G1 后要重配堆参数：堆约为容器一半，删掉 -Xmn，IHOP 设 40 并关闭自适应。
3. G1 的 Full GC 是最后手段、代价极高，调优目标是让 Mixed GC 及时回收老年代。
