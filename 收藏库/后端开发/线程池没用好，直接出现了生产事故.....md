# 线程池没用好，直接出现了生产事故....

> 一句话定位：线程池get不设超时、不分页导致的生产事故复盘

## 摘要

一次事故：DB 查数据做模型转换，并发 RPC 查价，但 e.get() 未设超时，数据大时耗时由最慢任务决定而超时。改进：查询分页、get 设超时。不当用法：多租户/父子任务共池互相影响甚至死锁；@Async 不指定线程池默认 SimpleAsyncTaskExecutor，高 QPS 下线程爆炸；线程复用致 ThreadLocal 脏数据。关键点：队列容量不可动态改、线程数 N+1/2N 与 N×(1+WT/ST)、ParallelStream 非线程安全共用 ForkJoinPool。

## 要点

- e.get() 不设超时，接口耗时取决于线程池中最慢任务，数据量大时引发接口超时。
- 修复要点：DB 查询结果必须分页，Future.get 必须设置超时时间。
- get 超时从调用 get 时刻起算，而非任务提交到线程池的时间。
- 不区分业务共用一个线程池会造成租户互相影响，父子任务同池还可能死锁。
- @Async 不指定线程池时使用 SimpleAsyncTaskExecutor，高 QPS 下会线程爆炸。
- 线程池复用线程会让 ThreadLocal 残留脏数据，应 finally 清理或改用 TransmittableThreadLocal。
- 核心线程数可用 N+1/2N 或 最佳线程数=N×(1+WT/ST) 估算。
- ParallelStream 下往非线程安全容器写数据会丢数据，且默认共用 ForkJoinPool。

## 提炼

> 一句话定位：线程池get不设超时、不分页导致的生产事故复盘

### 分节提炼

- **01 前言：线程池八股文**：线程池面试三大考点：三大核心参数含义、核心线程数制定策略、用 ThreadPoolExecutor 而非 Executors 创建。；八股文背熟不等于实战会用，由此引出真实生产事故。
- **02 事故还原**：从 DB 查大量数据做模型转换并并发 RPC 查价，e.get() 未设超时。；数据量增大时 get 耗时取决于线程池中最慢任务，引发接口超时。；get 超时从调用 get 时起算而非任务入池时间，耗时长的后执行任务可能不超时。
- **03 不当使用举例**：不区分业务共用线程池，租户间互相影响，父子任务同池还会死锁。；@Async 不指定线程池默认 SimpleAsyncTaskExecutor，高 QPS 线程爆炸。；线程池复用线程导致 ThreadLocal 旧值/脏数据，finally 清理也不一定执行。
- **04 关键要点**：ThreadPoolTaskExecutor 队列容量不可动态修改：capacity 是 final，setQueueCapacity 仅首次实例化生效。；线程数可按 N+1/2N 估算，更科学用 最佳线程数=N×(1+WT/ST)。；ParallelStream 写非线程安全容器会丢数据，且默认共用 ForkJoinPool。
- **05 总结**：本文以一次生产事故为例，总结线程池在日常开发中需要注意的要点。；希望这些要点能帮助开发者在实际运用中把线程池用好。

### 带走三句话

1. 并发场景务必给 Future.get 设超时、给 DB 查询分页，否则耗时由最慢任务决定。
2. 线程池按业务分类并显式指定线程池，同时清理 ThreadLocal，避免死锁、线程爆炸与脏数据。
3. 线程数按 N+1/2N 或 N×(1+WT/ST) 估算，慎用 ParallelStream，队列容量不能动态改。
