# 5 种注册中心，如何选型？

> 一句话定位：一文对比 Zookeeper、Eureka、Nacos、Consul、Etcd 五种注册中心及选型思路

## 摘要

本文先讲注册中心三大角色（服务提供者、消费者、注册中心）与必备功能，再介绍 CAP 理论与 Paxos、Raft、ZAB 三种一致性协议。随后逐一剖析五种注册中心：Zookeeper 遵循 CP，靠 Watch 推拉结合，但 leader 选举期间不可用，不适合做注册中心；Eureka 遵循 AP，对等去中心化并有自我保护机制；Nacos 支持 DNS/RPC 发现与动态配置，CP/AP 可切换；Consul 基于 Raft 强一致，提供一站式服务与多数据中心；Etcd 是 Raft 强一致的 KV 存储。最后给出选型建议：服务发现场景可用性优先，倾向 Eureka 或 Nacos，其中 Nacos 做得更多。

## 要点

- 注册中心有服务提供者、服务消费者、注册中心三种角色，消费者本地缓存节点列表并按负载均衡调用。
- CAP 三者只能取其二：一致性、可用性、分区容忍；Paxos、Raft、ZAB 是主流一致性协议。
- Zookeeper 遵循 CP，Watch 推拉结合，但 leader 选举期间集群不可用，不适合做注册中心。
- Eureka 遵循 AP，Peer to Peer 去中心化，靠自我保护机制保障高可用，容忍数据非强一致。
- Nacos 支持 DNS/RPC 服务发现与动态配置，CP/AP 可切换，相当于注册中心加配置中心。
- Consul 与 Etcd 都是 Raft 强一致（CP），Consul 提供一站式服务与多数据中心，Etcd 是强一致 KV 存储。
- 选型上服务发现可用性优先，倾向 Eureka 或 Nacos，其中 Nacos 做得更多。

## 提炼

> 一句话定位：一文对比 Zookeeper、Eureka、Nacos、Consul、Etcd 五种注册中心及选型思路

### 分节提炼

- **01 基本概念**：服务提供者启动时向 Registry 注册并定期心跳汇报存活状态。；服务消费者订阅服务并把节点列表缓存在本地内存。；Registry 保存注册信息并在节点变更时同步，消费者感知后刷新缓存。；消费者从本地缓存按负载均衡算法选一台服务端发起调用。
- **02 基础扫盲**：CAP 指一致性、可用性、分区容忍，三者不可能都取，只能取其中两个。；P 是系统某部分挂掉不影响整体运作，A 是某节点挂了仍能接受或发出请求。；Paxos 超过半数副本在线即可持续可用且数据不丢失。；Raft 是 Paxos 简化版，强调易理解易实现；ZAB 是 ZooKeeper 专为崩溃恢复设计的原子广播协议。
- **03 五种常用注册中心**：Zookeeper 遵循 CP，Watch 机制推拉结合，注册路径形如 /{service}/{version}/{ip:port}。；Eureka 遵循 AP，Peer to Peer 对等去中心化，心跳默认 30s，90s 未收到则注销实例。；Nacos 阿里开源，支持 DNS/RPC 服务发现、动态配置，CP/AP 可通过命令切换。；Consul 是 Go 编写的 CP 一站式方案，Raft 强一致，支持健康检查、KV Store 与多数据中心。；Etcd 是 Raft 强一致 KV 存储，WAL 持久化，支持 gRPC 通信与 watch 机制。
- **04 对比与选型**：健康检查、多数据中心、KV 存储、CAP 取舍、Watch、metrics、Spring Cloud 集成等多维对比。；Eureka 是典型 AP，Nacos 可配置为 AP；Zookeeper、Etcd、Consul 是 CP 类型。；选型倾向 AP：Eureka 与 Nacos 中选谁做的事少，Nacos 帮我们做了更多。

### 带走三句话

1. 注册中心可用性高于一致性：服务发现场景宁要稍旧数据，也不要服务不可用。
2. Zookeeper 强一致适合分布式协调，不适合做注册中心；AP 场景优先 Eureka 或 Nacos。
3. 选型按健康检查、多数据中心、KV 存储、CAP 取舍、metrics 等维度逐项对比后再定。
