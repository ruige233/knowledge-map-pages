# 面试官惊了：“你的 Agent 调用的都是 Claude Opus 5？DeepSeek V4 Flash 不香吗？”，我：“肯定得用最强的！”，他：“回家等通知”

> 一句话定位：系统讲透 LLM 网关：统一治理模型调用入口，先轻量收口再按需演进。

## 摘要

本文系统讲解 LLM Gateway：它是应用层与模型供应商之间的统一治理入口，集中管理模型选择、Token 预算、路由、限流、成本归因、日志与审计。核心观点：大多数单体或单团队项目不必引入独立网关平台，在应用内写轻量网关、先把模型调用收口即可。文章厘清 Gateway 与 Router、RAG、Agent、MCP 的边界，给出是否需要收口的判断与六阶段演进路径，详解统一接入、路由、降级、限流、成本统计、观测审计、缓存等能力，对比自研、LiteLLM、Cloudflare、Kong、Inworld 等主流方案，强调先工程治理、再智能路由，并以路由命中率、Fallback 率、成本、P95 延迟等指标衡量成效。

## 要点

- 轻量 LLM 网关应先把分散的模型调用收口到统一入口，再按需补超时、重试、日志与路由。
- 直连模型会暴露模型名写死、Key 分散、429 重试、成本不可见、日志缺失等七类问题，需 Gateway 对应能力解决。
- Gateway 管请求全生命周期治理，Router 只是其中选模型环节；路由应绑定模型层级而非具体模型名。
- 并非所有任务都该用最强模型：轻量任务走低成本模型，复杂推理任务才上强模型。
- Fallback 要按错误类型分类处理，带副作用请求必须配合幂等，流式输出不能拼接两个模型片段。
- 限流需按用户、租户、模型、供应商、Token 多维控制，走 estimate→reserve→usage→reconcile 预算闭环。
- 成本与观测要把账单落回 request_id、attempt_id、scene、Prompt 版本、模型层级等字段，日志留存与脱敏需按策略配置。
- 选型先轻量自研收口，再按需引入 LiteLLM、Cloudflare、Kong 等，最后才谈学习型智能路由。

## 提炼

> 一句话定位：系统讲透 LLM 网关：统一治理模型调用入口，先轻量收口再按需演进。

### 分节提炼

- **01 网关基础**：Gateway 是应用层与供应商间的治理入口，业务统一发标准请求，由网关决定模型、供应商与降级。；第一版只做统一封装、超时、重试和日志，生产阶段再补路由、预算、限流、审计。；只转发是代理，开始记录选型理由、扣预算、失败兜底才算 Gateway。
- **02 演进路径**：是否收口看一次模型策略修改影响多少服务、一次故障要查多少调用链。；轻量任务走小模型、强推理才上强模型，强模型不应是默认通道。；路由从固定规则起步，逐步演进到成本、语义、学习型策略，并验证收益再升级。
- **03 核心能力**：定义统一请求/响应与 ProviderClient 接口，业务只依赖网关、不依赖供应商 SDK。；OpenAI 兼容只统一入口形状，供应商专属能力需 Provider Adapter 转换。；Fallback 先分错误类型：网络瞬断、5xx 可切换，参数错误、安全拒答不可重试。；缓存只在答案可复用时省钱，带权限、实时状态、私密上下文的请求必须绕过。
- **04 设计方法**：先做统一 API、Provider Adapter 与 usage、成本、错误、延迟日志，再补路由与 Fallback。；请求生命周期：鉴权租户识别→scene→Prompt 渲染→Token 估算与路由→调用→结算。；路由六阶段演进：先可控、再省钱、最后变聪明，保留固定规则作回滚路径。
- **05 方案选型**：别只看支持多少模型，先看技术栈、合规、流量、自托管、已有网关与观测需求。；自研轻量网关适合需求明确团队，LiteLLM 适合快速接入多家供应商，Kong、Cloudflare 适合已有对应设施。；选型顺序：先工程治理，再追求智能路由。
- **06 效果衡量**：不能只看接了多少模型，要看路由命中率、Fallback 率、成本、P95 延迟、TTFT。；路由规则要像代码一样回归测试，防范路由漂移。
- **07 总结**：第一版先验证：请求正确适配、调用可按真实模型和 usage 回放、故障按预期兜底。；配额、成本、缓存由流量推动，分类或学习型路由待评测集与 Trace 具备后再引入。

### 带走三句话

1. 先做应用内轻量网关收口模型调用，再按流量与治理需求逐步补路由、限流、成本与审计。
2. 路由绑模型层级而非模型名，轻量任务走小模型、强推理才上旗舰，别把最强模型当默认。
3. 先工程治理再智能路由：有评测集和线上 Trace 之前，规则路由比复杂算法更稳。
