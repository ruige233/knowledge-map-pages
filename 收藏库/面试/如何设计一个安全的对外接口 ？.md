# 如何设计一个安全的对外接口 ？

> 一句话定位：七类措施设计安全对外接口：加密加签、鉴权限流、黑名单与校验

## 摘要

文章围绕对外接口（尤其与交易订单相关的公网接口）如何保证安全展开，把防护分为传输过程与服务器端识别两个方向，并列出七种常用措施：数据加密、数据加签、时间戳机制、AppId 机制、限流机制、黑名单机制和数据合法性校验。传输侧强调 HTTPS 加密与 MD5 加签防篡改；服务端侧强调时间戳窗口防重放、AppId 加密钥鉴权、令牌桶/漏桶/计数器限流、黑名单拦截和合法性校验。最后逐项给出实现要点，如对称与非对称加密选型、签名拼接规则、超时判断伪代码、ID 生成建议、RateLimiter 与 Redis+Lua 分布式限流。

## 要点

- 对外接口安全分为传输过程与服务器端识别两个方向，共七种常用措施。
- 数据加密：HTTPS 在 http 与 tcp 间加 SSL 层，关键字段可用 md5 加密。
- 数据加签：对参数拼接串加用户密钥后取 MD5，防内网跳转中的数据篡改。
- 时间戳机制：服务器用当前时间减客户端时间，超出窗口（如 5 分钟）视为非法，防重放。
- AppId 机制：后台开通 AppId 并下发密钥做鉴权，AppId 应趋势递增且不连续。
- 限流机制：令牌桶允许突发、漏桶恒定流速、计数器限制总并发；单机 RateLimiter，全局 Redis+Lua。
- 黑名单与合法性校验兜底：非法 AppId 直接返回错误码，数据须过常规性与业务校验。

## 提炼

> 一句话定位：七类措施设计安全对外接口：加密加签、鉴权限流、黑名单与校验

### 分节提炼

- **01 数据加密**：对称加密加解密用同一密钥，速度快，但密钥分发与保管是弱点，常见 DES、AES。；非对称加密公钥可公开、私钥留服务端，更安全但速度慢，广泛使用 RSA。；HTTPS 结合两种加密兼顾安全与性能，实现可直接用 jdk 工具类。
- **02 数据加签**：加签是发送者产生的无法伪造的数字串，保证数据在传输过程中不被篡改。；常用 MD5：对参数拼接串加用户密钥后取 MD5 作为数据包签名。；HTTPS 只加密外网，内网多服务跳转仍可能被篡改，故仍需加签。
- **03 时间戳机制**：请求中携带客户端时间戳，服务器用当前时间与消息时间相减判断是否超时。；超出固定窗口（如 5 分钟）即视为非法请求，防原样重放。；伪代码：interval=5*60*1000，serverTime-clientTime>interval 则拒绝。
- **04 AppId 机制**：对外接口如同登录，需在后台开通 AppId 并向用户下发密钥。；调用接口时携带 appid+密钥，服务器端进行验证。；AppId 建议趋势递增（利索引）且不连续（防猜规律），可用类 snowflake 方式生成。
- **05 限流机制**：真实用户频繁调用接口时，需要对相关 AppId 做限流处理。；常用限流算法有令牌桶和漏桶算法，也可用计数器。
- **06 令牌桶限流**：系统以一定速率向桶中放令牌，满了就丢弃；请求先取令牌，取到才放行。；允许一定程度突发流量，只要有令牌即可处理，支持一次拿多个令牌。
- **07 漏桶限流**：按固定常量速率流出请求，流入速率任意，超出容量则等待或拒绝。；可强制限制数据传输速度。
- **08 计数器限流**：简单粗暴，限制一定时间内的总请求数，超阈值即限流。；主要用于数据库连接池、线程池、秒杀等总并发数控制。；Guava RateLimiter 基于令牌桶实现；单机用它，全局需 redis+lua。
- **09 黑名单机制**：对多次非法操作的 AppId 列入黑名单，所有请求直接返回错误码。；实现：给用户设状态（初始化/正常/中黑/关闭），或用分布式配置中心保存黑名单列表。
- **10 数据合法性校验**：只有数据合法才会进行数据处理。；常规性校验：签名校验、必填校验、长度校验、类型校验、格式校验。；业务校验按实际业务而定，如订单金额不能小于 0。
- **11 总结**：回顾七种措施：数据加密、数据加签、时间戳机制、AppId 机制、限流机制、黑名单机制、数据合法性校验。；作者表示还有其他方式，欢迎补充。

### 带走三句话

1. 把加密、加签、时间戳、AppId、限流、黑名单、合法性校验七类措施组合落地。
2. HTTPS 只保护外网，内网多跳仍可能被篡改，加签不可省。
3. 限流按场景选：突发用令牌桶，恒定流速用漏桶，单机用 RateLimiter，全局上 Redis+Lua。
