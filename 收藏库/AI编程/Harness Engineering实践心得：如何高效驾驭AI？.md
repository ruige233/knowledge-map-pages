# Harness Engineering实践心得：如何高效驾驭AI？

> 一句话定位：从 Prompt 到 Harness：以规则、技能和验证搭好 AI 自主运转环境

## 摘要

本文是游戏客户端工程师的 Harness Engineering 实践心得：不靠更聪明的 Prompt，而是为 AI Agent 搭建能自主运转的环境。作者以 JK Launcher 12 个版本的演进为例，说明如何从单 Agent 走向七角色多 Agent 流水线，并用回退路由防止“发现问题的人自己修”。随后介绍 Rules/Skills/Scripts 三层分离与 verify_all.ps1 的 14 项事后检查。结论：AI 编程的瓶颈不在模型聪明程度，而在是否搭好了发挥的舞台。

## 要点

- Harness Engineering 的本质：不优化 Prompt，而是给 AI 搭建可自主运转的环境（规则、技能、验证、反馈闭环）。
- Prompt→Context→Harness 三时代：知识从人脑和聊天记录逐步迁到仓库里的规则文件与自动化脚本。
- JK Launcher 从 V3.0 到 V3.11 共 12 个版本，是实践 AI 编程方法论的试验田。
- 多 Agent 流水线：7 个角色各管一段，职责分离本身即质量保障，每层都能抓到前一层漏掉的问题。
- 关键规则“发现问题的人不能自己修”：用回退路由防止 Gate/Reviewer 自改自审。
- Rules/Skills/Scripts 三层分离：能用机器查的就别靠 AI 记，解决长上下文里的注意力衰减。
- 事后验证是安全网：编译→测试→14 项自动检查，测试基线只升不降，预防加兜底。
- 人的角色变成元工程：盯翻车、定义“什么算对”，把经验压缩成规则让 AI 秒级吸收。

## 提炼

> 一句话定位：从 Prompt 到 Harness：以规则、技能和验证搭好 AI 自主运转环境

### 分节提炼

- **01 三次跃迁**：给 Agent 套上马具：护栏让它看懂、绕不过才能稳定干活。；Agent 失败时不是“再跑一次”，而是问缺了什么护栏、怎么让它可执行。；三个时代在指挥方式、知识位置、质量保障、可复现性上逐步升级。
- **02 JK Launcher 案例**：Prompt 时代每次从零开始，AI 不知规范、风格不一致、改动易失控。；Context 时代设计文档管“做什么”却管不了“怎么做”，且文档会过时。；Harness 时代用规则文件、技能封装、自动验证、多 Agent、基线管理搭系统。
- **03 搭建 Harness**：单 Agent 有自我确认、上下文过载、无质量门、缺审计四大坑。；七角色流水线的价值是“7 层过滤网”，而非 7 倍工作量。；PM 状态机加回退路由，核心是发现问题的人不能自己修。；Rules/Skills/Scripts 三层分离，把可机器检测的规则迁成脚本。
- **04 事后验证**：规则是预防、会失效；事后验证是兜底，唯一能保证规则被执行。；三步验证：编译、369 个测试全通过、14 项检查零 Error，挂了修后重来。；好验证系统：覆盖高不贪全、误报低、修复闭环硬、基线只升不降、有历史记录。
- **05 人的角色**：人做的是元工程：盯 Agent 翻车并把修复变成规则或检查项，定义“什么算对”。；五类问题对应五类手段：Rule+Script、Skill、SubAgent 定义、MCP、新组件。；正反馈：护栏越多，AI 自主范围越大，人介入越少。
- **06 总结**：瓶颈不在 AI 聪明程度，而在有没有搭好发挥的舞台。；规则是缰绳、验证是刹车、Agent 体系是分工，缺一环都容易跑偏。；AI 犯错先想“Harness 漏了什么”，把每次失误变成改进机会。

### 带走三句话

1. 把“让 AI 别犯错”的规则换成“犯了错一定被抓到”的自动检查，预防加兜底。
2. 拆分多 Agent 并定义回退路由：发现问题的人不能自己修，职责分离即质量保障。
3. 人的工作从写代码转为写规则、搭环境，把经验压缩成护栏让 AI 秒级吸收。
