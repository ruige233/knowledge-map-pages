# 2026 年 AI 编码的“渐进式 Spec”实战指南

> 一句话定位：AI 编码落地框架：渐进式 Spec 驱动的工程化实践

## 摘要

本文分享 AI 编码落地的实践与思考。先对齐三个认知：模型能力梯队决定地基、Agent 是 while 循环加工具使用、评判标准是高效应对本质复杂度并压缩偶然复杂度。再给出渐进式 Spec 框架：三条铁律（No Spec No Code、Spec is Truth、Reverse Sync），按复杂度加载流程，配合 rules/knowledge/changes 目录与 Propose→Apply→Fix→Review→Archive 工作流。工具上采用编排层强模型加执行层编码模型的两层架构，强调透明度与 Git 规范。最后以跨模块迁移案例演示全流程，指出人的角色转向管和验、知识底座才是护城河，并正视心流中断与上下文管理等代价。

## 要点

- 顶级模型能独立完成中等复杂度编码，但仍需人审查；梯队差距在“一次做对的概率”。
- Agent = while 循环 + Tool Use + 工具执行器，工具的边界就是 Agent 的能力边界。
- 软件复杂度分为本质复杂度与偶然复杂度，方法论要高效应对前者、压缩后者。
- Spec Coding 三条铁律：No Spec No Code、Spec is Truth、Reverse Sync。
- 渐进式复杂度：简单需求不承担复杂流程成本，流程按复杂度加载。
- 工作流为 Propose→Apply→Fix→Review→Archive，配合 HARD-GATE 确认门控与 Verification 铁律。
- 编排层（强模型）+ 执行层（编码优化模型）两层架构，透明度是工具选型底线。
- 领域知识（knowledge/）才是 AI 编码的护城河，Spec 不是银弹。

## 提炼

> 一句话定位：AI 编码落地框架：渐进式 Spec 驱动的工程化实践

### 分节提炼

- **01 背景**：顶级模型可完成中等复杂度任务，但无持久记忆、无自主意图，结果仍需人审查；Arena 多轮维度上 Gemini 3.1 Pro 第一，单轮强不等于多轮稳；Agent 循环 = 侦察→思考→行动→验证→自愈；工具的边界就是 Agent 的能力边界；软件复杂度=本质复杂度+偶然复杂度，方法论要高效应对本质、压缩偶然
- **02 渐进式编码框架**：Spec Coding 三条铁律：No Spec No Code / Spec is Truth / Reverse Sync；Code is Cheap, Context is Expensive：好输入能让对话从 20 轮降到 3-5 轮；渐进式复杂度：70% 需求 ≤5 人日，简单需求不承担复杂流程成本；框架自我迭代：prompt/模板/rules 都是 Git 中的普通文件，形成知识飞轮
- **03 工具选型与编排**：编排层（强模型做决策）+ 执行层（编码模型写代码），避免全程贵或质量不够；工具透明度是基础需求：模型版本可见、context 可查、输出不被篡改；Git 规范：禁改 master、一个 task 一个 commit、commit 必须可编译、禁自动 push
- **04 实战案例**：/propose 先 Research 带出处，逐个提问给选项+推荐，待澄清全解决前不编码；tasks 拆分为原子可提交任务，/apply 逐步执行并展示验证证据；Reverse Sync：发现偏差先确认事实、再修 spec、最后改代码
- **05 观点与思考**：人从“全干”变为“管和验”：管控、指挥、评价；Spec 是沟通协议而非自动化流水线输入，代码才是真理；领域知识质量决定 AI 输出上限，knowledge/ 才是护城河；AI 编码引入心流中断与上下文管理隐性成本，框架价值随模型进步放大
- **06 讨论和命令混为一谈**：“帮我看看顺便修了”混着探索与指令，AI 会跳过探索直接改错；一次只给一种意图：探索/决策/指令/审查
- **07 阶段产出搞混**：调研阶段要事实和风险，不要代码；AI 太勤快时要拉住它，明确当前阶段的产出
- **08 自由度给反了**：自由度曲线：调研中、方案高、规划低、执行零、验收中；执行阶段要精确到文件路径与函数签名，偏离必须停下来问

### 带走三句话

1. 先用 Spec 固定意图与约束，再让 AI 编码；简单需求按复杂度裁剪流程，别让流程吃掉效率。
2. 把 AI 当有经验的搭档而非代码生成器：设计者与验收者是你，执行交给 AI，阶段自由度要管住。
3. 护城河不是工具而是高质量结构化领域知识，持续把踩坑与决策沉淀进 knowledge/。
