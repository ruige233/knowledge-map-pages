# AI Agent工程化融合：分享我的实践经验和选型技巧

> 一句话定位：用两个真实业务场景讲清 Agent 与工程如何融合提效

## 摘要

本文分享将 AI Agent 与工程系统融合的实践。作者先用 Agent + MCP 打造智能播报助手：借助 playwright-mcp 让 Agent 操作浏览器定时查看报表，结合钉钉机器人推送异常，并在系统提示词、RAG 检索、SQL 白名单与窗口大小等方面做工程化约束。再用 Agent 批量建任务：起初让 Agent 处理全部新增、对比与暂停逻辑，遭遇 token 成本高、响应慢、准确率差等问题，最终改为工程处理确定性逻辑、Agent 只做基于语义的任务范围匹配。文章对比了 Agent 与工程的能力边界，结论是 Agent 本质是概率游戏，最优策略是与工程结合、扬长避短，而非追求完全替代。

## 要点

- 脱离业务场景的技术创新没有价值，验证 Agent 价值要落到真实场景。
- MCP 用统一协议解决 Function Calling 厂商协议不统一、工具重复开发的问题。
- MCP 三种通讯方式：STDIO 本地安全，SSE/StreamableHttp 需注意暴露风险，SSE 已被弃用。
- 智能播报：Agent + playwright-mcp 操作浏览器 + 钉钉推送，替代人工定时看报表。
- 播报场景需工程化约束：窗口大小、快照最小获取、重试上限、关闭浏览器、白名单强校验。
- 批量建任务教训：把复杂逻辑全交给 Agent 导致 token 成本高、响应慢、准确率差。
- 最终分工：确定性逻辑交给工程，Agent 只做语义匹配等适合的任务。
- 结论：Agent 是概率游戏，最优策略是与工程结合、扬长避短。

## 提炼

> 一句话定位：用两个真实业务场景讲清 Agent 与工程如何融合提效

### 分节提炼

- **01 引言**：验证 Agent 价值必须落到真实业务场景，脱离场景的创新会沦为空中楼阁。；本文结构：两个业务场景的实践历程，结尾给出 agent 与工程的选型总结。
- **02 智能播报助手**：看报表痛点：FBI 无法按异常定向播报、无法取加工数据、无法基于异常做后续动作。；MCP 统一工具调用协议；STDIO 本地安全，SSE/StreamableHttp 暴露有安全风险，SSE 已被弃用。；用 playwright-mcp 操作浏览器 + 钉钉机器人推送，实现定时看报表并播报。；工程化要点：配置类与补充信息类分离、关系库 keywords 做 RAG、SQL 白名单与专用库降风险。
- **03 批量建任务**：全量交给 Agent：token 大、成本高、响应慢、准确率差，无法交付。；解法：拆分任务并发（最多 10 并发）、同步改异步轮询、结果存 redis。；最终分工：工程处理字段转换与对比等确定性工作，Agent 只做任务范围的语义匹配。
- **04 总结**：Agent 本质是概率游戏，不是万能的。；最优策略：Agent 与工程结合、扬长避短；方向不对要及时更换，不死磕。
- **05 参考链接**：给出四个参考链接：MCP StreamableHTTP 协议解析、playwright-mcp 仓库。；另含魔搭社区 MCP 服务与 Cherry Studio 客户端入口。

### 带走三句话

1. 先验证场景再谈价值：脱离业务的技术创新是空中楼阁，Agent 必须落到真实业务上提效。
2. 把确定性、高精度的逻辑交给工程，Agent 只负责语义匹配等概率性工作，扬长避短。
3. 工程化约束决定成败：窗口大小、快照最小化、重试上限、关闭浏览器、白名单校验缺一不可。
