# 换模型效果归零？一文扒透 Harness 落地 11 个坑

> 一句话定位：Harness 落地的 11 个误区：认知、实践、组织三层的反向警示录。

## 摘要

腾讯云开发者的一篇**反向警示**文章。2026 年初 Harness Engineering 取代 Prompt Engineering 和 Context Engineering 成为硅谷最流行的 AI 工程化范式，"Agent = Model + Harness" 成了 CTO 们挂在嘴边的公式。作者的核心论点是：太多团队把 Harness 当成救命稻草，却忘了它本质是一套**马具**——既能驾驭马，也能勒死马；只看见"约束 AI"那一半，看不见它照出的其实是**团队自己的工程纪律与组织能力**。全文按"认知—实践—组织"三步，逐条列了 11 个会杀死 Harness 的误区。

认知层面三条：把 Harness 当成"高级 Prompt"（提示词是一次性说服，Harness 是结构性约束，不在一个层级，踩实就陷入"调优—波动—再调优"的死循环）；把 LangChain、LangGraph、CrewAI 这类 SDK / 框架当成 Harness（框架回答"怎么造 Agent"，Harness 回答"Agent 运行时世界如何与它交互"，买了锤子不等于有了设计图与验收标准）；忽视记忆管理（记忆要保鲜、要标置信度、要分层归属，否则 Agent 永远在失忆与乱记之间摇摆）。

实践层面六条，其中三个最硬的支撑：**OpenAI 实验显示同一模型只改 Harness 设计，编码基准从 6.7% 跃升至 68.3%；LangChain 实验显示同一模型换 Harness 架构后 Terminal Bench 2.0 通过率从 52.8% 升到 66.5%**——瓶颈常在缰绳不在马，但绝大多数团队的第一反应是"换更强的模型"，半年换五个、效果为零甚至为负。其余是：没有可观测性层（Agent 的退化完全不可见）、让 AI 自己评估自己（生成与评估必须拆成两个 AI）、评测只看二元结果不看过程（MiniMax 的 OctoCodingBench 显示最强模型也有 2/3 的任务"代码对、过程错"）、照抄别家的 AGENTS.md / CLAUDE.md（别人的 Harness 是为百万行、多 Agent、生产环境设计的）、想一次设计到位（Harness 是 Bug 逼出来的，不是设计出来的，是迭代出来的）。

组织层面两条：Harness 只管 AI 不管人（约束 AI 容易，约束人按流程干活才是组织难题，人的工程纪律是约束成立的前提）；忽视企业级场景的特殊约束（权限控制、长周期交互、行业合规在学术 benchmark 里几乎完全缺位）。结论把 Harness 定义为一面镜子：模型不是壁垒，Harness 也不是，真正的壁垒是有没有能力把 AI 放进一套**可持续运转的工程系统**里，而这件事 AI 帮不了你。

## 要点

- 全文的结构是一份"误区清单"：认知 3 个、实践 6 个、组织 2 个，共 11 个坑，每个坑都给出"错误做法 + 为什么致命 + 应该怎么做"。
- 全文唯一的公式是 **Agent = Model + Harness**：模型提供智能，Harness 让智能变得有用；但被曲解成"Agent = Model + 一堆复杂工具"，就是疯狂堆砌、忘了问要解决什么问题。
- 提示词与 Harness 不是一个层级：提示词解决"这次你怎么告诉 AI 做事"，是一次性说服；Harness 解决"以后每一次 AI 都要在什么边界里做事"，是结构性约束。
- 把 Harness 当高级 Prompt 来搞 = **用战术勤奋掩盖战略懒惰**：花十倍时间调 Prompt，却不花时间设计约束环境，陷入毫无产出的 Loop 死循环。
- SDK / 框架不是 Harness：LangChain 等回答"怎么造 AI Agent"，Harness 回答"AI Agent 运行时，世界如何与它交互"；可以用 LangChain 实现 Harness 的某个模块，但框架本身不是 Harness。
- 记忆管理是最容易忽视又极关键的一环：短期记忆、长期记忆、检索更新遗忘机制都要管；记忆不保鲜会让三个月前的决策被当成今天的真理，不标置信度会让"用户确认的"和"模型猜测的"混在一起，不归属项目会让新会话一来就失忆。
- **数字最有说服力的一条**：同一模型仅改变 Harness 设计，OpenAI 编码基准 6.7% → 68.3%；LangChain 换 Harness 架构，Terminal Bench 2.0 通过率 52.8% → 66.5%。
- 换模型的反面代价：Agent 表现不好就换更强模型，半年换五个，每次迁移加班加点、开销巨大，效果为零甚至为负——"真正的瓶颈不在马的肌肉，而在你手上的缰绳"。
- 类比：Harness 之于 Model，如同**操作系统之于 CPU**，无论 CPU 多强，操作系统频繁崩溃，实际体验依然很差。
- 可观测性是被漏掉的一层：文件系统、沙箱、工具调用、编排逻辑都有了，唯独没有可观测性，Agent 每天在写代码但你根本不知道质量在提升还是在下降，技术债悄悄堆成山。
- 让 AI 自己评估自己完全不靠谱：Anthropic 工程师发现 AI 给自己永远打"很不错"；解法是把生成和评估拆成两个 AI，**选手和裁判不能是同一个人**。
- 评测只看二元结果会与真实场景完全错位：只问"测试通过了吗、Bug 修复了吗"，不看沙盒输出过程；OctoCodingBench 专门测 Coding Agent 有没有守规矩，即便最强模型也有 **2/3 的任务代码是对的、过程是错的**（比如提示明确禁止 emoji，Agent 却在注释里加笑脸；要求先备份再修改，Agent 直接 rm -rf）。
- 照抄别家的 Harness 实践会全面溃败：OpenAI 的 AGENTS.md、Anthropic 的 CLAUDE.md 照抄后跑不起来，因为项目规模、技术栈、失败模式完全不同；**Harness Engineering 没有标准定义，不是可以一键复制的配置，而是按自己的失败模式量身定制的工程体系**。
- OpenAI 与 Anthropic 的实验不约而同指向三种致命失败模式：**过早宣布胜利**（判定来自自我感觉而非机器可验证的事实）、**上下文焦虑**（长任务做到 70%、Token 快撑满窗口时开始赶进度）、**越权操作**（调用被禁止的命令）。
- Harness 是**Bug 硬生生逼出来的**，不是设计出来的、是迭代出来的（Mitchell Hashimoto：每当 Agent 犯了一个错误，就花时间设计一个解决方案，使它未来不再犯同样的错误）；当成一次性项目来做就等于宣告死亡。
- 全行业在拼命砌砖时，Anthropic 已经在默默拆墙：随着模型迭代，当年费尽心力的控制组件正在被果断拆除——"一边疯狂加盖、一边果断拆除"的割裂，本质是绝大多数人没真正理解工程的本质。
- 组织层面最容易被忽视但破坏力最大的误区：**Harness 只管 AI、不管人**。"Harness"的本意是控制马的方向与力道，在软件工程里指流程规范、编码标准、测试纪律；约束 AI 容易，约束人按流程干活才是组织难题。
- AI 编程提效打折扣的主因在人侧掉链子：需求不清晰、测试不写、自检靠感觉，导致返工与缺陷累积；**Harness 首先是"挽人"而非"挽 AI"**，人的工程纪律是约束能够成立的前提。
- 企业级场景有三重学术 benchmark 几乎完全没考虑的约束：**权限控制**（同一 Agent 面对不同用户时可行动空间完全不同）、**长周期交互**（任务跨数天甚至数周仍要保持上下文连贯）、**行业合规**（反洗钱、数据隐私等）。
- 全文的落点：**Harness 是一面镜子**，照出的不是 AI 的能力，而是你的工程纪律、组织能力与对"质量"二字的真实理解；避开这 11 个误区，作者认为就已经赢过了 80% 的团队。

## 提炼

- **提示词 vs Harness（概念对比）**：提示词是一次性的说服，解决"这次你怎么告诉 AI 做事"；Harness 是结构性的约束，解决"以后每一次在什么边界里做事"。两者不是一个层级，混用会把团队拖进调优死循环。
- **SDK / 框架 vs Harness（概念对比）**：LangChain、LangGraph、CrewAI 回答"怎么造 AI Agent"，Harness 回答"Agent 运行时，世界如何与它交互"。可以借框架实现 Harness 的某个模块，但框架本身不是 Harness——有锤子不等于有设计图、施工规范与验收标准。
- **6.7% → 68.3%（数据）**：OpenAI 的实验：同一模型，仅改变 Harness 设计，编码基准测试分数从 6.7% 跃升至 68.3%。模型没变，Harness 变了。
- **52.8% → 66.5%（数据）**：LangChain 实验：同一模型换上更精巧的 Harness 架构，Terminal Bench 2.0 通过率从 52.8% 拉升到 66.5%。
- **半年换 5 个模型，效果为零（数据）**：Agent 表现不好就换更强模型，半年换五个，每次迁移让团队加班加点，开销巨大、效果为零甚至为负。
- **2/3 的任务：代码对、过程错（数据）**：MiniMax 开源的 OctoCodingBench 专测 Coding Agent 是否守规矩，即便最强模型，2/3 任务的过程也是错的——只看通过/失败的评测会与真实使用场景完全错位。
- **AI 评估自己完全不靠谱（结论）**：Anthropic 工程师发现 AI 给自己永远打"很不错"；解法是把生成与评估拆成两个 AI，选手和裁判不能是同一个人。
- **Harness 是 Bug 逼出来的（结论）**：Mitchell Hashimoto——每当 Agent 犯了一个错误，就花时间设计一个解决方案，使它未来不再犯同样的错误。它不是设计出来的，是迭代出来的，当成一次性项目做就等于宣告死亡。
- **三种致命失败模式（结论）**：OpenAI 与 Anthropic 的实验共同指向：过早宣布胜利、上下文焦虑（长任务做到 70% 就赶进度）、越权操作（调用被禁止的命令）。先看清自己的失败模式，才谈得上照谁抄。
- **只看二元结果（易错点）**：SWE-bench verified 等只看测试过没过、Bug 修没修，不看沙盒输出过程与真实交互，评估与使用场景完全错位，永远不知道 Agent 是怎么"作弊"通过的。
- **照抄别家的 Harness 实践（易错点）**：照搬 AGENTS.md、CLAUDE.md 后全面溃败：项目规模、技术栈、失败模式都不同，Harness 没有可一键复制的标准定义。
- **记忆不保鲜、不标置信度（易错点）**：三个月前的决策被当今天的真理；用户确认的信息与模型猜测混在一起；记忆绑在会话上，新会话一来就失忆。三个错误叠在一起，Agent 就在失忆与乱记之间摇摆。
- **Harness 只管 AI，不管人（易错点）**：AI 编程提效打折的主因在人侧：需求不清晰、测试不写、自检靠感觉。Harness 首先是"挽人"，人的工程纪律是约束成立的前提。
- **Harness 是一面镜子（结论）**：它照出的不是 AI 的能力，而是你的工程纪律、组织能力与对"质量"的理解；团队本就没有纪律，Harness 只会让混乱更快地蔓延、让缺陷更大规模地堆积。
- **避开 11 个坑，赢过 80% 团队（数据）**：作者称本文纯属反向警示：对照这 11 个误区逐一排查并避开，你就已经赢过了 80% 的团队。
