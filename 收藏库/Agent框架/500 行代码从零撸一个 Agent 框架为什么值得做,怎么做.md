# 500 行代码从零撸一个 Agent 框架为什么值得做,怎么做

> 一句话定位：后端工程师选型前，先手写一个500行最小Agent框架，再回头读框架源码

## 摘要

本文是《Agent 工程实践》系列第03期，主张后端工程师在选型主流框架前，先花两三个周末从零写一个约500行的最小Agent框架，不为替代它们，而是看清抽象成本、Prompt与代码的边界、生产打点，并拿到面试可讲的硬经验。作者以 Hello-Agents 第7章为素材，拆解最小骨架三层：LLM层统一在OpenAI协议上、Agent基类只留一个run抽象方法、Tool层用注册表加"万物皆工具"，并点明三种要避免的过度设计。写完后回头看LangChain，复杂抽象都能对应回自己500行的某一段。

## 要点

- 选型前先手写一个约500行的最小Agent框架，是后端工程师看清框架抽象成本的最短路径。
- 能跑的Agent核心逻辑就是 while 循环加 tool_registry.execute()，其余抽象都是为支持更多花样。
- 框架里真正的业务逻辑很多藏在Prompt里，Prompt是代码的一部分，需要版本管理与测试。
- 最小骨架三层：LLM层统一在OpenAI协议上、Agent基类只留一个run抽象方法、Tool层"万物皆工具"。
- "万物皆工具"是教学阶段的极简策略，生产上记忆/检索有状态、类型与调度粒度代价，需单独分层。
- 造轮子阶段避免三种过度设计：流式+异步+分布式、提前做多Agent、过早追求"正确的抽象"。
- 写完后回头看LangChain，Runnable、AgentExecutor、OutputParser等都能对应回手写代码的某一段。

## 提炼

> 一句话定位：后端工程师选型前，先手写一个500行最小Agent框架，再回头读框架源码

### 分节提炼

- **01 先造小轮子再选框架**：后端群里常见"选哪个框架"之争，作者认为这个问题问早了；值得先花两三个周末手写500行最小框架，为回头读主流框架打底
- **02 为什么自己写一遍**：原书三条收益偏虚，作者换成四个面试可讲的硬收益；能跑的Agent核心就是 while 循环加 tool_registry.execute()；框架里真正的业务逻辑很多藏在 Prompt 里；生产打点位置、trace_id、token 统计都要在写框架时想清
- **03 500行的骨架分层**：LLM层别发明新抽象，统一在OpenAI协议上，多供应商在其下做兼容；Agent基类只保留一个 run(input)->str 抽象方法，历史管理放基类；Tool层用注册表加"万物皆工具"，字符串协议与function calling二选一
- **04 三种过度设计**：造轮子阶段一切追求"看得见"，同步单线程阻塞即可；多Agent、记忆、上下文工程都是单Agent骨架之后的可选组件；"够用的抽象"优于"正确的抽象"
- **05 回看 LangChain**：回看LangChain：Runnable、AgentExecutor等对应手写代码；AgentExecutor的复杂参数是手写时踩过的坑的名字；从使用者变成建造者，不再仰视框架
- **06 下一篇预告**：下一篇讲记忆：短期、长期、RAG检索、分层记忆架构；上下文如何流动是从 Demo 到可用的最大分水岭
- **07 参考与致谢**：素材引自 Datawhale Hello-Agents 第7章，遵循 CC BY-NC-SA 4.0；项目地址 github.com/datawhalechina/hello-agents

### 带走三句话

1. 先动手把500行敲出来，再回头看LangChain每个抽象都有对应，这步读文档替代不了。
2. 最小骨架只三层：LLM层站在OpenAI协议上、Agent基类一个run、Tool层万物皆工具。
3. 造轮子阶段一切追求"看得见"：同步阻塞、单Agent、够用抽象，别碰流式异步分布式。
