# 【AI 创新实践】“架构师 Agent” 系统化落地

> 一句话定位：让存量分布式系统成为 AI 可理解、可推理、可验证的工程系统

## 摘要

本文系统阐述“架构师 Agent”的落地路径：AI 难以理解复杂存量系统的根源不在代码生成能力，而在业务、架构、服务、工程四类知识彼此断裂。作者提出先建设面向领域的强结构知识库，再以“技术方案设计”为核心落点，把需求准入、知识库、架构图谱、代码回源与证据验证串成可执行的 Agent Runtime。知识库强调先对齐领域、不首推 RAG、渐进式披露与持续维护；方案设计由 AI 沿最短认知路径完成调研、Gap 分析与方案生成，覆盖度目标 95%。该体系还能复用于线上排查，方案设计只是起点。

## 要点

- AI 在存量复杂系统上最典型的错误是“局部正确、整体错误”，根因是业务、架构、服务内部、工程组织四类知识彼此断裂。
- 新系统如白纸、存量系统如旧城：对 AI 的挑战差别核心在历史上下文的认知与生效方式，而非系统规模。
- 业界有 Spec-Driven Development、长程 Agent Harness、Agent-friendly Repository 三条路线，但多偏单微服务内部实践。
- 知识库建设应先对齐领域做强结构化设计，不首推 RAG；RAG 只负责长尾发现与补证。
- 业务知识库以领域为边界，由 meta、principle、scenario、practice、reference 五类内容蒸馏架构师隐性知识。
- 技术方案设计 Agent 按“需求准入→业务元语→架构图谱→服务知识→代码回源→Gap 分析→方案生成”推进，并渐进式加载上下文。
- 知识正确性依赖维护机制：代码变更触发候选更新，高风险知识由人工确认语义，辅以日常增量与周期性校准。
- 知识库体系是多场景 Agent 的共同底座，技术方案设计只是“架构师 Agent”的第一个落点。

## 提炼

> 一句话定位：让存量分布式系统成为 AI 可理解、可推理、可验证的工程系统

### 分节提炼

- **01 AI 难懂复杂系统**：小系统惊艳、大系统不稳，AI 不知从哪开始、哪里绝不能动；根因不是模型能力，而是关键知识散落在方案、复盘、配置与经验中；典型错误是“局部正确、整体错误”，会放大方案错误传播；技术方案设计仍是人工介入最深、最需架构师强力的环节
- **02 白纸与旧城**：新系统像白纸，存量系统像运行多年的城市，不能只看局部；影响方案设计的四类知识：业务、架构、服务内部、工程与组织；难点不在“代码太多”，而在知识彼此断裂、无机制组织
- **03 行业三条路线**：三条路线：Spec-Driven Development、长程 Agent Harness、Agent-friendly Repository；这些实践多偏单微服务内部，跨复杂多系统的工业实践仍缺细节；目标：让 AI 完成跨多系统、多终端的技术方案设计与推理
- **04 从方案设计切入**：从架构师核心职能“技术方案设计”切入，避免空泛化与发散；抓手：需求质量、分层知识库、LLM 基模、技术方案产出规范；关键不是更长 Prompt，而是持续演进的知识工程与 Agent 迭代
- **05 知识库系统建设**：知识库先对齐领域：把 AI 当聪明实习生，用强结构文档层层引导；不首推 RAG：颗粒度不一致、语义相似≠工程相关、Top K 结构无保证；业务知识库以领域为边界，含 meta、principle、scenario、practice、reference；知识维护需日常增量+周期性校准，避免过期文档误导 AI
- **06 方案设计 Agent 落地**：PRD 准入是 AI 技术方案设计的第一个输入转换器，减少返工；六步流程+渐进式披露：按需加载知识，沿最短认知路径完成任务；可执行方案需回答改哪里/为什么改/影响谁/如何验证/未确认什么；完备度以 95% 覆盖为目标，拆成需求、系统、证据、风险、验证、不确定性六维
- **07 多场景 Agent 基建**：方案设计与线上排查底层能力接近，同一知识体系可复用；知识库成为研发调研、方案、排查、复盘、新人理解的共同底座
- **08 迈向架构师 Agent**：技术方案设计是架构师最核心、最能体现系统性判断的工作；创新是把需求准入、知识、图谱、约束、回源与验证连成可演进生产线；同一系统理解能力可扩展至需求增强、架构评审、线上排查等

### 带走三句话

1. 架构师 Agent 的起点不是更强模型，而是把断裂的业务、架构、服务、工程知识显性化并结构化。
2. 知识库先对齐领域再谈检索：RAG 只做长尾补证，骨架未立，检索再快也难稳定理解系统。
3. 方案设计由 AI 沿渐进披露路径完成，但高风险决策仍由人裁决：人从知识检索器变为质量与决策负责人。
