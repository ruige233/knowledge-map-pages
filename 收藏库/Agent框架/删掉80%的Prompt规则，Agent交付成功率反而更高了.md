# 删掉80%的Prompt规则，Agent交付成功率反而更高了

> 一句话定位：删 Prompt 规则不是目的：把工程检查接入 Agent 必经路径，交付才可靠。

## 摘要

本文讨论 Coding Agent 时代交付链为何仍会断：代码是中间产物而非交付结果，Agent 说“测试全部通过”只能说明它自认实现结束，真正完成还需确认读了当前生效契约、测试跑对目录、拿得出报告与回读证据。因此需要三件事——可信上下文：让 Agent 沿证据链找到可追溯、可验证的事实，知识库像地图而非百科全书；可执行约束：规则能否生效取决于违反后能否继续，把可机械判断的要求写成检查、门禁与动作前拦截；可恢复流程：用文档、Workflow 与 State 让任务不依赖某一次会话。落地从真实任务最小闭环开始，按运行证据 Add 或 Thin，不照搬他项目 Harness。

## 要点

- 代码是中间产物，不是交付结果；会写代码解决实现问题，能否交付取决于工程环境。
- Agent 说“测试全部通过”不可直接采信，需确认它读了当前生效契约、测试跑对目录、有报告与线上回读等证据。
- 可信上下文不是塞资料，而是沿可追溯证据链裁剪出当前任务的工作集；知识库是地图，不是百科全书。
- 规则能否形成约束取决于违反后会发生什么：条件不满足任务仍能继续，就只是提醒。
- 把可明确判断的要求写成确定性检查：阶段门禁保证证据不足不推进，动作前检查拦住高风险操作。
- 可恢复流程由文档维护、工作流推进、状态存档三部分组成；State 是书签，文档才是任务正文。
- Harness 从真实任务最小闭环长出来，观测执行链后按 Add/Thin 增删，不照搬他项目实现。

## 提炼

> 一句话定位：删 Prompt 规则不是目的：把工程检查接入 Agent 必经路径，交付才可靠。

### 分节提炼

- **01 代码≠交付**：“代码已修改，测试全部通过”只能说明 Agent 自认实现结束，不代表任务完成。；交付需确认：读的是否当前生效代码/契约、测试是否覆盖并跑对目录、有无报告/Review/回执/回读证据。；把实现交给 Agent 不等于把人的经验、习惯和流程能力自动转移过去。；影响交付的三件事：读对东西、规则能拦错、断了能接着做。
- **02 可信上下文**：可信上下文是沿可追溯证据链找到当前任务需要、可信、可验证的信息，而非把资料都塞给模型。；知识库像地图，Context 只是当前任务的工作集，应沿任务路径逐步裁剪，而不是一次塞满。；找到不等于可信：要确认来源、版本与适用范围，区分代码现场与运行现场。；隐性知识显式化是第一步；重复路径先写 Runbook，稳定后沉淀为 Skill/脚本/Gate。
- **03 可执行约束**：规则能否形成约束不取决于措辞强弱，而取决于违反后会发生什么。；Prompt/Rule 可能变成“自己执行、自己验收、自己宣布完成”，能明确判断的要求要接进必经路径。；阶段门禁解决“上一步证据不够就不能进入下一阶段”。；高风险动作要在发生前检查，不能先做后补。
- **04 可恢复流程**：可恢复流程三部分：文档维护、工作流推进、状态存档，三者组合才能跨会话继续。；Workflow 是交接协议：输入来自已确认事实或上一步产物，输出落到文档/代码现场/报告。；State 是书签，文档才是任务正文；恢复任务靠项目持久化信息，不是找回上一段对话。
- **05 Harness 生长与修剪**：落地不先设计平台，先跑最小 MVP 建立基线，保留自然产生的运行证据。；观测整个执行链：先问出错时能否看见在哪一层出问题，复用问题类型而非固定阶段字段。；出错后别急着改 Prompt，基于任务轨迹和运行证据做四步根因诊断。
- **06 结语**：Harness 组件隐含对当前模型能力的判断，不应被当成永久资产。；Add/Thin 由真实任务观测决定：重复失败、缺证据、无法恢复→Add；无人消费、误伤、负收益→Thin。；相对稳定的是原则：权威来源、可恢复、权限边界不自行放宽、完成有物理证据。
- **07 参考资料**：列出 Harness 工程相关官方资料：OpenAI Harness engineering、Anthropic effective harnesses 与 context engineering 等。

### 带走三句话

1. 可信上下文让 Agent 读对事实，可执行约束让偏离不能继续，可恢复流程让任务不依赖单次会话。
2. 把能明确判断、出错代价又高的要求写成确定性检查，放到 Agent 无法绕开的必经之路上。
3. Harness 从真实任务的最小闭环长出来：先观测运行证据，再按 Add/Thin 增删，不照搬他项目实现。
